# 爱团代码架构设计（Stage 1）

## 1. 设计目标

本文档仅定义**代码架构**，不直接约束最终 UI 视觉稿与数据库细节实现。

本架构遵循以下原则：

1. **高内聚低耦合**：按业务域拆分，而不是按技术层堆在一起。
2. **单文件尽量不超过 200 行**：复杂页面、复杂服务、复杂状态机都必须拆分。
3. **先 P0，兼容 P1/P2 扩展**：先满足消费闭环、商家闭环、后台治理闭环，再平滑扩展团购、票券、预约、AI 能力。
4. **统一交易模型，差异能力内聚到子模块**：外卖、团购、酒店、票务、预约都归入统一交易域，但通过子模块隔离差异规则。
5. **配送模拟从简**：配送模拟不单独做成独立服务，只作为后端订单域下的一个轻量模块实现。
6. **各端独立演进**：用户端 APP、商家 Web、平台后台 Web 各自独立构建；后端提供统一 REST API。

## 2. 总体架构结论

建议采用 **单仓多应用（Monorepo）+ 后端模块化单体（Modular Monolith）**：

- **用户端**：Flutter，优先 Android / iOS。
- **商家端**：Vue 3 + TypeScript。
- **平台后台**：Vue 3 + TypeScript。
- **后端**：Spring Boot + MySQL。
- **配送模拟**：后端内部 `order/delivery` 小模块。
- **AI Agent / Skills**：后端内部 `ai` 模块，通过 Provider + Skill 注册表实现，可 Mock、可降级。

这样做的好处：

- 比微服务更适合课程项目，部署简单，联调成本低。
- 比“大一统单包结构”更清晰，每个业务域都可以独立拆文件、拆测试、拆文档。
- 后续如果某个模块做大，例如 AI、搜索、营销，再单独拆服务也容易。

#### features 设计原则

`features/` 下每个业务模块统一采用 **data / domain / presentation** 三层：

- `data`：只处理接口、DTO、仓储实现。
- `domain`：只放仓储抽象和用例，不写 UI。
- `presentation`：只放页面、控制器、状态、局部组件。

### 7.2 后端拆分规则

为控制单文件规模，后端必须遵守以下拆分策略：

1. **Controller 不写业务细节**：只收参、鉴权、调 Service、返回结果。
2. **Service 按动作拆分**：查询与命令分开，例如 `OrderQueryService`、`OrderCommandService`。
3. **DTO/Entity 分离**：接口对象不要直接复用数据库实体。
4. **状态机单独拆文件**：订单、支付、退款、配送状态都不要写死在一个大类里。
5. **定时任务单独拆文件**：自动关单、配送推进、券码过期处理分别拆 Job。
6. **复杂表单规则单独抽校验器**：如果后续逻辑增大，可新增 `validator/` 包，而不是把判断堆进 Service。

### 7.3 配送模拟模块简化建议

配送模拟建议只保留以下最小能力：

1. 创建外卖订单后生成一条配送轨迹记录。
2. 通过 `DeliveryTickJob.java` 定时推进：`待接单 -> 备餐中 -> 待配送 -> 配送中 -> 已送达`。
3. `DeliveryEstimateCalculator.java` 只做简单预计送达时间估算。
4. 地图不可用时只返回文字时间线。
5. 不做骑手分配、不做实时路线规划、不做复杂调度。

这样能满足课程项目展示，又不会把配送模块做重。

## 10. 单文件不超过 200 行的落地规则

为避免单文件失控，建议统一执行以下规则：

1. **Flutter 页面**：
   - 页面主体超过 150 行就把局部块拆到 `presentation/widgets/`。
   - 页面状态复杂时，`controller.dart`、`state.dart` 分离。
2. **Vue 页面**：
   - 一个 `.vue` 页面只保留页面骨架。
   - 查询栏、表格、弹窗、表单拆到 `components/`。
   - 请求逻辑超过 80 行，抽到 `api.ts` 或 `composables/`。
3. **Java 后端**：
   - Controller 尽量控制在 100 行以内。
   - 一个 Service 只负责一类动作。
   - DTO、Entity、StateMachine、Job、Assembler 分文件。
4. **SQL**：
   - 每个迁移脚本只做一个领域或一个批次的表变更。

## 12. 实施顺序建议

建议按下面顺序建骨架：

1. 先建仓库根目录、三端应用目录、后端目录、数据库目录。
2. 先完成后端 `common/auth/user/merchant/catalog/cart/order` 核心骨架。

4. 商家端先做 `auth/onboarding/store_manage/catalog/order`。
5. 后台先做 `auth/dashboard/merchant_audit/order_ops/review_moderation/system_config`。
6. 再补 `member/marketing/support/ai` 等增强模块。

## 13. 最终结论

本架构的核心思想是：

- **前端按业务切片**，避免所有页面堆在 `pages/`。
- **后端按业务域分包**，避免所有逻辑堆在一个 `service` 包。
- **配送模拟留在订单域内部**，只做轻量状态推进。
- **AI 作为增强模块接入**，不影响核心交易闭环。
- **任何模块变复杂时，优先拆文件，不优先加抽象。**

如果后续进入真正编码阶段，我建议下一步先输出：

1. `docs/stage1/数据库表设计.md`
2. `docs/stage1/API 分组设计.md`
3. `docs/stage1/页面与路由清单.md`

这样就可以直接进入分模块开发。
