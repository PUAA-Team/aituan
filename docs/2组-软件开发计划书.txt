1 引言
 
1.1 标识
 
本计划书适用于“爱团本地生活服务综合平台”的开发活动。爱团是一款面向城市居民的综合生活助手平台，目标是将
外卖订餐、到店消费、休闲娱乐、生活服务、上门按摩预约、在线下单、支付模拟、评价互动和平台运营管理集成到
统一系统中。本期面向普通消费者的用户端实现形式仅包含 Android APP 和 iOS APP；HarmonyOS 与 Web/H5 作为
后续可能移植方向。商家端和平台管理后台属于管理支撑系统，可采用 Web 管理端实现。

1.2 系统概述
 
1.2.1 系统定位
 
为满足城市居民日益增长的本地生活服务需求，爱团计划建设一个连接用户和本地商家的综合平台，使用户能够一键
触达“吃、喝、玩、乐、购、服务”等场景。系统应支持商家搜索与推荐、外卖点餐、到店团购、上门按摩等生活服务
预约、用户评价、在线下单与支付模拟等功能，并重点关注商家信息准确性、配送时效稳定性、预约履约可靠性和用
户评价真实性。
项目对标美团、淘宝闪购/饿了么、大众点评等真实系统的产品形态和业务逻辑。本文档以课程题目要求和项目范围基
线作为范围依据。

1.2.2 核心业务模块
 
爱团系统核心业务模块按本地生活业务方向划分，而不是按前端页面或后端接口划分。各模块在功能设计上尽量选择
课程阶段易实现、易演示的能力，重点保证浏览、下单、支付模拟、订单状态和评价闭环。
其中，外卖到餐作为独立履约链路展示配送状态；到店团购、酒店民宿、休闲娱乐、电影演出、丽人医美、景点门票
和上门按摩等模块在功能层面重点体现套餐/服务浏览、下单支付、预约或核销、订单评价。
会员体系参考成熟本地生活平台的等级成长机制，但采用爱团自有等级名称和规则。用户通过完成订单、发布真实有
效评价、上传图文评价、评价被点赞或被标记为有帮助、持续活跃等行为获得烟火值；退款、异常评价、违规刷单等
行为不计入烟火值或触发扣减。会员等级暂定六级，等级越高可获得更多优惠券、专属活动、生日权益、客服优先处
理、推荐加权展示等权益。课程阶段可先实现烟火值累计、等级展示、权益说明和优惠券发放模拟。

1.5 基线
 
本项目的初始基线如下：
1. 需求基线：以课程题目要求和项目范围基线为基础。
2. 范围基线：本期优先完成用户消费闭环、商家经营闭环、平台审核与配置闭环、配送模拟展示。
3. 技术基线：采用前后端分离架构，用户端以 Android / iOS APP 为主，商家端和平台后台采用 Web 管理端，后
端采用 Spring Boot，数据库采用 MySQL。
4. 质量基线：P0 核心功能必须可演示、可测试、可追踪；P1/P2 功能根据时间增量完成。
5. 进度基线：2026年4月20日启动，2026年6月20日最终交付。
6. 分工基线：团队按业务模块端到端分工，每名成员负责若干模块的前端页面、后端接口、数据库设计、测试用
例和文档说明，避免只负责前端、只负责后端、只负责文档或只负责编码的割裂式分工。

4.4 计划/采购策略
 
4.4.1 计划策略
 
本项目采用敏捷迭代策略，以一周为基本开发周期，以两周为阶段评审周期。优先级原则如下：
1. P0：用户消费闭环、商家订单处理、后台审核配置、配送模拟。
2. P1：到店团购、酒店民宿、休闲娱乐、电影演出、丽人医美、景点门票、上门按摩预约、评价互动、商家客
服、优惠券、消息、烟火会员等级、数据看板、爱团智能生活规划 Agent、AI 辅助搜索。
3. P2：复杂营销、HarmonyOS / Web 移植评估、真实配送、更多 AI Skills。
4.4.2 采购策略
 
项目尽量使用开源软件、工具和免费资源，采用VS Code、Jetbrains、MySQL、JDK、Flutter等软件进行开发部署。
本产品依赖的云服务，如服务器采用阿里云2C4G香港服务器，降低备案成本与时间开销，图片等资源依赖阿里云OSS
对象存储，AI模型接入OpenAI、Anthropic等主流顶级模型平台API。
其他如地图、短信等外部服务优先采用免费额度或本地模拟。若确需外部服务，需评估成本、账号安全、可用性和替
代方案。

5 实施整个软件开发活动的计划
 
5.1 软件开发过程
 
本项目采用简化 Scrum 敏捷过程：
1. 建立产品待办列表，按 P0/P1/P2 排序。
2. 每周召开迭代计划会，确定任务和负责人。
3. 按业务模块端到端开发，每个模块负责人同步完成页面、接口、数据表、测试用例和模块文档。
4. 每两到三天同步进展、问题和阻塞。
5. 每周进行一次演示或检查。
6. 测试阶段集中缺陷修复和回归测试。
7. 每个阶段同步更新文档。
项目处于计划和需求基线阶段。已明确项目定位、角色、模块、优先级和技术方向，后续将进入原型设计、数据库设
计、接口设计和编码实现。
5.2 软件开发方法
 
采用敏捷开发方法的原因如下：
1. 爱团涉及用户、商家、平台三类角色，适合按业务链路分步实现。
2. 学生团队时间有限，需要通过短周期持续检查进度。
3. AI、数据看板、营销等增强功能可在核心闭环完成后增量加入。
4. 课程答辩强调可演示成果，敏捷方式便于及时调整重点。

5.3 软件产品标准
 
需求表达与设计
 
1. 需求采用用户故事、功能列表、流程图和状态表表达。
2. 设计文档必须说明模块边界、接口输入输出、数据库表结构和异常处理。
3. 订单状态、配送状态、评价审核等关键流程需单独说明。
4. 需求变更需记录原因、影响范围和处理结论。
编码标准
 
1. 用户端采用 Flutter 和移动端组件化开发方式；商家端和平台后台采用 Vue 3 和组件化开发方式。
2. 后端采用 Java、Spring Boot 和分层架构。
3. 接口采用 RESTful 风格，统一响应格式和错误码。
4. 数据库表名、字段名语义明确，重要字段添加注释。
5. 不提交密码、密钥、真实证件和隐私数据。
6. 合并代码前完成自测，确保核心路径不报错。
测试标准
 
1. 测试用例覆盖 P0 功能、边界条件和主要异常路径。
2. 接口测试覆盖登录鉴权、查询、创建、更新、状态变更。
3. 前端测试覆盖 Android / iOS APP 与管理端页面跳转、表单校验、错误提示和按钮状态。
4. 集成测试覆盖用户下单、商家接单、配送模拟、评价和后台审核。
5.4 可重用的软件产品
 
5.4.1 吸纳可重用的软件产品
 
项目可吸纳移动端组件库、管理端前端组件库、后端通用权限模块、数据库通用设计模式、图表组件、地图组件和 AI 
调用封装模板。选型时需考虑学习成本、兼容性、开源协议、稳定性和文档完整性。
5.4.2 开发可重用的软件产品
 
项目内部计划沉淀统一登录鉴权模块、分页查询组件、搜索筛选组件、订单状态机、配送状态机、后台表格模板、文
件上传组件和 AI Skill 统一调用接口。

4. 前后端均进行输入校验。

例；后端接口先通过接口测试，再交付前端联调；联调完成后由非本模块开发成员进行交叉复测。
系统测试按完整业务场景执行：用户注册登录、搜索商家、查看详情、发起商家咨询、商家回复咨询、加入购物车、
提交订单、支付模拟、商家接单、配送模拟、确认完成、发布评价、累计烟火值、查看烟火会员等级与权益、后台审
核和查看数据看板。交付前至少进行两次完整演练，所有影响演示的 P0、P1 缺陷必须修复并回归测试。

码、部署说明、演示账号、测试报告、用户手册和答辩材料。移交前需整理源代码目录，删除临时文件和本地私密配
置，确认数据库脚本、演示数据和启动步骤可复现。
配置项包括源代码、数据库脚本、文档、测试用例、演示数据和发布包。main 分支保存可演示版本，dev 分支用于集

记录实现功能、已知问题、运行环境和启动步骤。
6.9 质量保证与评审
 
质量保证从需求、设计、编码、测试和文档五个方面执行，重点检查核心流程、接口稳定性、状态流转、权限控制、
异常提示和演示稳定性。质量记录包括代码评审记录、测试用例、缺陷报告、修复记录、版本说明和验收检查表。
项目评审分为技术评审和管理评审。技术评审关注需求、架构、数据库、接口和测试用例；管理评审关注进度、风
险、资源、分工和交付准备。尽量由非本模块开发成员执行交叉检查，减少只验证自己模块导致的遗漏。

8.1 项目组织
 
本项目采用“业务模块负责人制”，不按单纯前端、后端或文档岗位划分。每名成员均需对自己负责的模块进行端到端
交付，包括需求细化、页面实现、后端接口、数据库表或字段、测试用例、缺陷修复和文档说明。测试与文档由全体
成员共同承担，成员E只负责统筹，不作为唯一文档负责人。
8.1.1 模块分工原则
 
1. 每名成员至少负责一个核心需求。
2. 每名成员至少负责四个业务模块。
3. 每个业务模块至少包含五个主要功能。
4. 每名成员均承担编码、测试、文档和答辩讲解任务。
5. 计划权重保持均衡，原则上不低于 0.9；最终权重可按实际贡献微调，但不得低于课程要求下限 0.8。

项目需要五台 Windows 游戏本、一台 MacBook Air、一台 MacBook Pro、JDK、Flutter SDK、Android Studio、
Xcode、Node.js、MySQL、Git、现代浏览器、校园网络、Android / iOS 模拟器和演示设备支持。移动端真机测试使
用三台 iPhone、三台 Android 手机；一台 HarmonyOS 手机用于后续移植兼容性观察，不作为本期交付验收设备。
若部署到云端演示环境，计划使用 2C4G 香港服务器，操作系统为 Ubuntu，部署后端服务、管理端前端静态资源、
数据库或数据库连接配置。
12.2 需要需方承担的工作和提供的条件
 
课程需方需提供项目题目、模板文档、提交格式、阶段检查时间、最终答辩安排和评分反馈。若要求部署到指定平
台，应提供平台信息和账号权限。
12.3 需要承包方承担的工作和提供的条件
 
开发团队需完成计划、需求、设计、开发、测试、文档、部署和答辩工作，提供可运行系统、源代码、数据库脚本、
演示数据和完整文档。
