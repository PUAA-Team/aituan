# 组内分工与大模型使用说明

> 用途：用于答辩静态 PPT 和老师追问“谁做了什么、AI 做了什么、怎么人工检查”时统一口径。该内容不录入 4 分钟现场演示视频。
> 原则：只陈述真实发生的工作。录制前每名成员需确认自己的工具名和职责，不要把大模型生成内容说成未经检查的个人原创，也不要虚构未使用的模型。

| 李明 | B：商家与商品服务 | 商家、门店、商品、SKU、库存、搜索、履约规则；B 独立库与测试 | 核对 B 只能访问 `aituan_merchant`；验证商品、库存和故障注入目标 |
| 李旭 | C：交易与履约服务、公共集成 | 购物车、试算、订单、支付、退款、配送；Gateway、CI/CD、Kubernetes 集成 | 核对跨服务事务、状态机、同 SHA 发布、生产 rollout 与恢复 |
| 匡威 | D：互动与平台服务 | 评价、投诉、客服、AI、公告、审计和看板；D 独立库与测试 | 核对 D 只能访问 `aituan_platform`；验证评价治理、客服和降级 |

公共工作按“主责人实现、依赖方复核、集成人最终验收”完成：

- Gateway 路由由各服务负责人核对自己的 API 归属，集成人统一检查 `/internal/**` 不对外暴露。
- 数据库迁移由各服务负责人维护，四账号跨库拒绝由统一脚本复核。
- Dockerfile、Kubernetes Deployment/Service 和健康检查由服务负责人自检，流水线再做清单和镜像门禁。
- E2E 按业务场景认领，最终从 Gateway 对四库五服务和三端统一回归。

如果团队最终登记的成员主责与上表不同，以实际 commit、看板和站会记录为准，在录制前同步修改 PPT 和本文件。

## 3. 大模型使用情况

### 3.1 推荐真实口径

本项目开发环境中可见 Claude 配置和 Codex 辅助开发痕迹，本次演示文档也由 Codex 辅助整理。若团队实际还使用 ChatGPT、GitHub Copilot 或其他模型，可在下表增加；未实际使用的名称必须删除。

| 工具 | 用来做什么 | 不允许替代什么 | 人工检查方法 |
| --- | --- | --- | --- |
| Codex | 阅读仓库、梳理微服务边界、补充测试/实验脚本、分析失败日志、整理文档和演示稿 | 不代替需求确认、生产变更审批、最终合并和验收结论 | 负责人阅读 diff；逐文件核对接口/表归属；运行目标测试和完整 CI；在 k3s 重现实验 |
| Claude | 需求和文档初稿、代码思路讨论、局部实现或重构建议、问题排查 | 不直接把建议合并到主分支，不凭回答宣称测试通过 | 对照需求/UML/接口清单；审查生成代码；用 Maven、Playwright 等执行工具验证 |
| 其他实际使用模型 | 录制前填入真实名称和用途 | 不使用模糊的“AI 自动完成全部项目”描述 | 附一个真实例子及其人工修改、测试证据 |

最稳妥的答辩说法是“AI 辅助了哪些环节”，而不是报生成代码行数。行数难以可靠统计，也不能证明质量。

### 3.2 具体使用环节

| 环节 | 大模型作用 | 人工最终判断 |
| --- | --- | --- |
| 需求与架构 | 从 UC01—UC13 中整理领域概念、候选服务边界和接口清单 | 团队按高内聚、低耦合、数据所有权和现有业务流程确定 A/B/C/D |
| 编码 | 生成样板、局部实现建议、异常分支和重构草案 | 模块负责人检查业务状态、权限、事务、幂等、超时和数据归属 |
| 测试 | 根据用例生成单元、集成、契约和 E2E 初稿，补充边界场景 | 人工对照需求逐条检查断言，运行测试，确认失败时确实能拦截流水线 |
| CI/CD 与 Kubernetes | 帮助整理 workflow、Dockerfile、Deployment、HPA 和诊断命令 | 集成人核对 Secrets 边界、镜像 SHA、依赖顺序、资源限制，并在生产 k3s 实测 |
| HPA 与故障处理 | 辅助设计负载、断言、证据采集和恢复保护 | 人工确认压力是真实业务请求、B 确实下线、C 无部分写入、其他服务可用、最终恢复 |
| 文档与答辩 | 汇总原始报告、生成表格、润色解说和字幕 | 负责人对照代码、Actions run 和原始 JSON/TSV 校正数字，不让模型凭空补结果 |

### 3.3 人工检查闭环

所有大模型产出至少经过下面一条链路；影响生产的内容需要全部经过：

```text
成员提出任务和约束
  → 大模型给出初稿/诊断
  → 成员阅读 diff 和引用来源
  → 运行目标模块测试
  → 依赖方检查接口契约与数据所有权
  → Pull Request / 同伴评审
  → 完整微服务 CI
  → 同 SHA CD 与 Kubernetes smoke
  → HPA/故障等专项实验
  → 保存原始证据并人工复核结论
```

重点检查项：

- 需求：测试步骤是否真的对应 UC 和三层模型，不能只看测试名。
- 边界：每个服务是否只连接自己的 schema，跨服务是否走内部 HTTP 契约。
- 安全：模型输出中是否混入真实密码、token、kubeconfig、个人信息或危险命令。
- 代码：异常分支、超时、幂等、事务顺序、状态转换是否与业务一致。
- 测试：断言是否能失败，不能只有“HTTP 200”；报告是否来自本次 SHA。
- 部署：镜像 tag 是否为不可变 SHA，健康端点是否来自真实 Pod。
- 实验：开始、变化、恢复是否都保存，失败的一轮不能挑片段包装为成功。
- 结论：性能收益必须同时报告测试条件和内存代价；故障降级必须区分 API 已实现与 UI 已实现。

## 6. 老师追问的统一回答

### Q1：拆成微服务后还要测试吗？报告是哪一阶段的？

要。当前展示的是第二阶段微服务版测试：五服务模块测试、四 schema 迁移与权限隔离、跨服务契约、Gateway E2E、镜像和 Kubernetes 部署验证。第一阶段单体测试只作为兼容基线，不能代替第二阶段报告。

### Q2：为什么没有现场演示所有用例？

老师要求核心场景即可，所以现场选择 UC04 下单支付、UC05 商家履约、UC09 评价治理，三者能串成同一订单并覆盖三端和 A/B/C/D。全部 UC01—UC13 共 15 条自动化场景由本次 CI 日志和报告证明。

### Q3：HPA 为什么不放在 CI/CD 里？

CI/CD 负责代码质量、制品和部署，部署后会检查 HPA 配置和指标有效。真实压力扩缩容是独立环境实验，因为它持续占用集群资源并需要观察冷却窗口。我们单独展示从触发负载、Pod 增加，到负载停止和 Pod 回落的全过程。

### Q4：压力测试到底证明了什么？

压力 Job 经 Gateway 对 A/B/C/D 的真实业务接口发请求；CPU 超过 50% 后，对应微服务 Pod 增加，压力结束后经过稳定窗口回到 1。脚本同时保存请求、错误率、延迟、HPA 和 Pod 资源时间线，并自动判断实验是否通过。

### Q5：故障处理到底证明了什么？

我们真实停止 B 商品服务。C 仍能从自己的数据库返回购物车快照，并明确提示商品服务不可用；依赖实时价格和库存的新增/改数量快速失败且不产生部分写入，移除/清空仍可用。A 用户资料、C 订单、D 评价和 Gateway 继续健康；B 恢复后 C 无需重启就能恢复实时校验。

### Q6：怎么证明不是大模型编造的结果？

每个结论都有可复核证据：commit 和 Actions run ID、同 SHA 镜像、JUnit/JSON/HTML 报告、Kubernetes 状态、HPA TSV、故障前中后响应和自动断言。模型只帮助整理方案和诊断，测试命令与集群实际输出才是验收依据。
