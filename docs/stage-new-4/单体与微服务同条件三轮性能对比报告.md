# 单体与微服务同条件三轮性能对比报告

> 测试日期：2026-09-02  
> 代码基线：`65ddbf8e2fa0b4149552c4223d68f60a1ef9d468`  
> 测试服务器：`aituan-new`，阿里云单节点 k3s，4 vCPU / 14.717 GiB 可见内存  
> 原始证据：`tests/performance/results/aituan-performance-comparison-20260902-server-final.tar.gz`

## 1. 结论

在同一服务器、同一 MySQL 实例、同一业务数据、同一组 3 个接口、并发 50、每轮 15000 请求、各 3 轮且固定 1 副本的条件下：

| 指标（三轮均值） | 单体 | 微服务 | 微服务相对变化 |
| --- | ---: | ---: | ---: |
| 吞吐量 | 318.409 req/s | 463.943 req/s | **+45.707%** |
| 平均响应时间 | 159.643 ms | 107.765 ms | **-32.496%** |
| P95 响应时间 | 324.870 ms | 238.821 ms | **-26.487%** |
| P99 响应时间 | 439.406 ms | 328.356 ms | **-25.273%** |
| 错误率 | 0% | 0% | 相同 |
| 平均 CPU（100%=1 个逻辑核） | 148.887% | 172.079% | +15.577% |
| 平均常驻内存 | 545.113 MiB | 1433.684 MiB | +163.007% |
| 峰值常驻内存 | 556.922 MiB | 1444.840 MiB | +159.432% |

本次可以写“当前微服务验收版在这三个只读主要接口上性能更高”，但不能写成“微服务天然比单体快”。主要收益来自 Gateway 与 B 服务分担了单体一个 JVM/一个 CPU cgroup 的热点，代价是多 JVM 带来的约 2.63 倍常驻内存。单体三轮仍有明显 JIT/缓存升温；即使只取双方第 3 轮成熟样本，微服务吞吐仍高 27.695%，平均响应时间低 21.700%，P95 低 18.873%，因此优势不只来自第一轮冷启动。

## 2. 课程要求与测试口径

课程要求选择 2–3 个主要接口，单体与微服务使用同一台机器、同一批数据、同一份压力脚本，各运行至少 3 次，并记录并发、吞吐、平均/P95、错误率、CPU 和内存。本次逐项落实如下：

| 要求 | 本次做法 |
| --- | --- |
| 主要接口 | 首页、推荐列表、门店搜索，共 3 个只读接口 |
| 同一机器 | 两套服务均位于 `aituan-new` 同一 k3s 节点 |
| 同一数据库条件 | 共用同一个 MySQL Pod、镜像和运行参数；单体使用隔离 schema，避免改动生产四库 |
| 同一批数据 | 将微服务默认 `R__seed_merchant_catalog_demo.sql` 原样复制到单体隔离 schema；两端均为 10 门店、11 商品、7 推荐 |
| 同一业务响应 | 删除动态 `requestId`、`timestamp` 后，三个接口响应 JSON 的 SHA-256 分别完全相同 |
| 同一压力 | 并发 50，每轮 15000 正式请求，正式请求总数 90000；每端先预热 1000 请求 |
| 多次测试 | 单体 3 轮、微服务 3 轮，轮间冷却 10 秒 |
| 固定容量 | 正式测试期间 5 个 HPA 的最大副本临时设为 1；结束后恢复 1–4 Pod |
| 网络路径 | 压测器在 K3s 内通过 ClusterIP Service 请求；单体和微服务都不经过公网、TLS 或 Web Nginx |
| 资源口径 | 单体统计单体 Java + MySQL；微服务统计 Gateway + A/B/C/D + MySQL；前端未计入两边 |
| 原始结果 | 保存每请求 JSONL、每 500 ms 的进程资源 JSONL、机器/测试配置及 JSON/CSV 汇总 |

旧文件 `monolith-20260901-final.zip` 是 Apple M5 + H2 的单体历史结果，机器和数据库均不同，只可证明脚本当时可运行，不能用于本报告的改造前后结论。本报告重新在服务器 MySQL 环境构建并测试了单体版本。

## 3. 环境与公平性检查

### 3.1 服务资源配置

| 组件 | CPU request / limit | 内存 request / limit | JVM 堆 |
| --- | --- | --- | --- |
| 单体 | 200m / 1000m | 256 MiB / 768 MiB | 128–512 MiB |
| Gateway | 50m / 500m | 96 MiB / 384 MiB | 64–256 MiB |
| A/B/C/D（每个） | 75m / 750m | 128 MiB / 384 MiB | 64–256 MiB |
| MySQL（双方共用） | 250m / 750m | 256 MiB / 512 MiB | 不适用 |

三个接口的微服务热链路仅为 `Gateway -> B 商家商品服务 -> MySQL`。该热链路两个 Java 进程合计 CPU 上限为 1.25 核、堆上限为 512 MiB；单体 Java 为 1 核、512 MiB。因此堆上限相同，但微服务热链路可使用的 CPU 上限高 25%。A/C/D 虽不参与请求，仍纳入微服务整套架构的内存统计。

### 3.2 数据和响应等价

| 校验项 | 单体 | 微服务 | 结果 |
| --- | ---: | ---: | --- |
| `merchant_store` | 10 | 10 | 相同 |
| `catalog_item` | 11 | 11 | 相同 |
| `member_recommend_config` | 7 | 7 | 相同 |
| 首页响应体 | 7856 B | 7857 B | 业务 JSON 相同；1 B 差异来自动态时间精度 |
| 推荐响应体 | 6874 B | 6874 B | 业务 JSON 相同 |
| 搜索响应体 | 2540 B | 2540 B | 业务 JSON 相同 |

具体哈希见 `experiments/performance-comparison-65ddbf8/payload-equivalence.txt`。这排除了“微服务 seed 更少、返回更短所以更快”的伪结论。

### 3.3 资源采样方法

压测器每 500 ms 从宿主机只读 `/proc/<pid>/stat` 与 `/proc/<pid>/status`。CPU 使用相邻样本的用户态+内核态时钟增量计算，而不是使用 Linux `ps %CPU` 的进程生命周期平均值；内存使用 `VmRSS`。`100% CPU` 表示一个逻辑核完全占用，多个进程之和可以超过 100%。

测试前曾发现临时单体 liveness 路径误配为受保护的 `/actuator/health/liveness`，导致 Pod 被重启；该组样本已判为无效并从最终结果排除。清单改回旧单体使用的 `/actuator/health` 后，Pod 连续稳定且重启数为 0，随后从预热开始重新完成本报告的六轮有效测试。

## 6. 为什么微服务更快，以及屏障点在哪里

### 6.1 进程级 CPU 与内存

| 进程 | 三轮平均 CPU | 三轮平均 RSS MiB | 峰值 RSS MiB |
| --- | ---: | ---: | ---: |
| 单体 Java | 99.730% | 271.402 | 283.211 |
| 单体测试时 MySQL | 49.157% | 273.711 | 273.711 |
| Gateway | 33.259% | 231.442 | 238.605 |
| A 身份资产 | 0.296% | 229.195 | 229.195 |
| B 商家商品 | 74.241% | 269.633 | 273.586 |
| C 交易履约 | 0.193% | 202.762 | 202.773 |
| D 互动平台 | 0.280% | 226.940 | 226.969 |
| 微服务测试时 MySQL | 63.810% | 273.711 | 273.711 |

### 6.2 有证据支持的原因

1. **单体首先撞到单 JVM CPU 上限。** 单体 Java 三轮平均为 99.730%，几乎持续占满其 1 核 CPU limit；这就是本场景下最明确的单体屏障点。
2. **微服务把请求处理拆到两个可独立调度的 JVM。** Gateway 平均 33.259%，B 平均 74.241%，热链路 Java 合计约 107.5% CPU；额外网络跳转确实存在，但没有把收益抵消。
3. **微服务单位请求 CPU 也更低。** 按整套被测进程估算，单体每请求消耗约 4.676 ms CPU 时间，微服务约 3.709 ms，下降 20.678%；仅看应用 Java，约从 3.132 ms 降至 2.334 ms。业务数据、响应和核心 SQL/排序逻辑已对齐，因此该差异更可能来自较小的服务运行上下文、Gateway 的非阻塞网络转发以及两个 JVM 更充分的并发调度。这一条是结合代码与采样做出的推断，不是单独做过 profiler 后的确定归因。
4. **MySQL CPU 增长主要是吞吐增长的结果。** 微服务测试时 MySQL 从 49.157% 升到 63.810%，增幅低于吞吐增幅；数据库尚未达到 75% CPU limit，但已接近下一阶段瓶颈。
5. **微服务当前屏障点转移到 B。** B 平均 74.241%，接近自身 750m limit，Gateway 仍有余量。继续加压时应优先扩 B 或优化推荐/搜索 SQL；生产 HPA 已能将 Gateway 与 B 扩到最多 4 副本，但本次为公平比较主动锁定 1 副本。

### 6.3 代价

微服务整套平均 RSS 为 1433.684 MiB，比单体多 888.571 MiB。A/C/D 在本场景几乎不耗 CPU，但仍各自保留约 203–229 MiB RSS。微服务适合用独立伸缩、故障隔离和团队边界换取资源开销；如果服务器内存紧张，应先调整非热点服务 JVM 堆、Class Data Sharing 或按业务时段缩容，而不是只看吞吐结论。

## 7. 局限与后续优化

- 本报告覆盖课程要求的 3 个只读主接口，不代表下单、库存扣减、支付和跨服务补偿等写链路也更快。
- 两套服务位于单节点，未测跨节点网络延迟；公网 TLS/Nginx 也被有意排除。
- 目标按单体后微服务的顺序执行。单体升温更明显，因此同时给出了第 3 轮成熟态的保守比较。
- HPA 在正式样本中锁为 1，扩缩容能力由 `HPA与依赖故障实验说明.md` 的独立生产实压证明，不能与固定容量对比混在一起。
- 若继续优化，应优先对 B 的门店搜索做 SQL 次数/执行计划分析，并用 JFR 或 async-profiler 分解 Java CPU；之后再用更大数据集和写接口复测。
