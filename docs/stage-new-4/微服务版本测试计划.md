## 1. 测试目标

本测试计划面向爱团本地生活服务综合平台的微服务版本，测试目标是验证系统是否满足软件工程基础实践中关于“测试补齐、容器化、CI/CD、Kubernetes 部署、微服务拆分、自动扩缩容、故障处理、改造前后性能对比”的要求。

测试不只验证页面是否可点击，而是围绕以下目标建立可复验依据：

1. 验证 Gateway + A/B/C/D 四个业务微服务能够独立构建、独立测试、独立启动和协同运行；
2. 验证 13 个正式业务用例在微服务 Gateway 入口下仍可完整回归；
3. 验证服务划分、接口路由、内部接口隔离、数据库归属和跨库访问边界符合微服务设计；
4. 验证容器化、Kubernetes、CI/CD 和健康检查链路满足自动交付要求；
5. 验证 HPA 自动扩缩容、依赖故障隔离和恢复机制具备真实运行证据；
6. 验证单体与微服务版本在同条件下完成性能对比，并保留原始数据和分析结论。

### 2.3 数据库范围

微服务版本采用四个逻辑库：

```text
aituan_identity
aituan_merchant
aituan_trade
aituan_platform
```

数据库测试范围包括：

- 各服务 Flyway 空库迁移；
- repeatable seed 数据幂等；
- 四个数据库账号只拥有本服务 schema 权限；
- 跨 schema 外键数量为 0；
- SQL 边界扫描无跨服务表访问；
- 业务历史展示所需字段保存为快照，不依赖跨库 JOIN。

## 4. 测试类型与策略

### 4.1 单元测试

目标：验证单个服务内部业务规则正确，不依赖其他服务真实进程。

| 服务 | 单元测试重点 |
| --- | --- |
| A | 登录校验、用户状态、优惠券报价/占用/释放、成长值、消息写入幂等 |
| B | 搜索筛选、商品上下架、库存扣减/恢复、履约规则、商家状态校验 |
| C | 购物车、结算、订单状态机、支付、退款补偿、预约取消、配送推进 |
| D | 评价资格处理、投诉流转、客服会话、AI 降级、文件元数据、审计记录 |
| Gateway | 路由归属、内部路径封锁、请求 ID、外部伪造内部头清理 |

准则：服务内部单元测试允许使用 stub/mock 替代下游服务，但不能直接访问其他服务数据库。

### 4.2 Controller / API 测试

目标：验证服务对外 API 的请求参数、权限、响应格式和错误码。

测试重点：

- 统一响应结构；
- 登录态和角色权限；
- 参数边界和非法状态；
- 业务错误码不泄露数据库表名、SQL、Repository 或堆栈细节；
- `/internal/**` 只允许内部调用，不允许从 Gateway 对外暴露。

### 4.3 内部契约测试

目标：验证跨服务接口的请求头、DTO、超时、幂等和错误处理保持稳定。

提供方测试：

- A 提供用户摘要、地址快照、优惠券报价/使用/释放、成长值和消息接口；
- B 提供门店快照、商家账号映射、商品快照、履约规则、结算报价、库存扣减/恢复接口；
- C 提供订单快照、评价资格、订单已评价标记、购买信号和订单指标接口；
- D 提供评价摘要、门店互动指标、平台治理指标和审计接口。

调用方测试：

- 所有内部调用携带 `X-Request-Id`、`X-Caller-Service`、`X-Service-Token`；
- 内部写接口必须携带稳定 `Idempotency-Key`；
- 写接口默认不自动重试，补偿按相同幂等键重试；
- 下游超时要在有界时间内失败或降级，不得无限阻塞。

### 4.4 数据库迁移与边界测试

目标：验证微服务数据归属成立。

测试项：

1. 四库空库 Flyway 迁移全部成功；
2. repeatable seed 可重复执行且不产生重复数据；
3. A/B/C/D 分别使用独立账号连接本服务库；
4. 每个账号访问其他 schema 被 MySQL 权限拒绝；
5. 跨 schema 外键数量为 0；
6. SQL 扫描不出现跨服务表访问；
7. 订单、评价、投诉、客服、收藏等跨服务历史展示保存必要快照。

### 4.5 端到端测试

目标：通过 Gateway 和三端生产构建产物验证业务闭环。

正式业务用例为 UC01–UC13，测试场景对应如下：

| 用例 | 测试重点 | 主责服务 |
| --- | --- | --- |
| UC01 登录注册 | 三角色登录、受保护资源访问 | A / Gateway |
| UC02 搜索和详情 | 首页、推荐、搜索、门店和商品详情 | B |
| UC03 资料地址收藏 | 用户资料、地址、收藏资产 | A / B |
| UC04 外卖下单支付 | 购物车、结算、优惠、库存、订单、支付 | C / A / B |
| UC05 商家履约配送 | 接单、备餐、配送、完成、消息 | C / A / B |
| UC06 非外卖券码 | 服务订单、券码生成、凭证查询 | C |
| UC07 预约核销 | 预约、商家核销、订单完成 | C / B |
| UC08 取消退款 | 退款、优惠券恢复、库存恢复、预约取消 | C / A / B |
| UC09 评价治理 | 评价、回复、举报、审核 | D / C / B / A |
| UC10 投诉处理 | 投诉工单、商家/平台处理、状态闭环 | D / C / A |
| UC11 客服与 AI | 客服会话、AI 回复、人工处理、降级 | D / A |
| UC12 会员优惠券 | 成长值、领券、用券、资产变化 | A / C |
| UC13 商家目录 | 门店、商品、SKU、库存、上下架 | B |

要求：端到端测试必须经 Gateway 发起，不允许绕过 Gateway 直接调用单个服务。

### 4.6 容器化与部署测试

目标：验证微服务版本可以用容器和 Kubernetes 启动。

测试项：

- 每个服务 Dockerfile 可独立构建；
- 应用镜像使用 Java 17，运行时不包含真实密码；
- MySQL 初始化脚本可以创建四 schema 和授权；
- Compose 或等价容器环境可启动 MySQL、Gateway、A/B/C/D；
- Kubernetes Deployment、Service、Secret、ConfigMap、PVC、Ingress、HPA 可渲染和应用；
- startup/readiness/liveness 探针配置合理；
- D 文件存储使用持久化卷，避免 Pod 重启后文件丢失；
- 发布后检查 `/actuator/health`、版本端点、三端页面、APK 下载和默认账号登录。

### 4.7 CI/CD 测试

目标：验证自动化流水线不能绕过质量门禁。

计划验证：

1. 服务矩阵执行 Gateway、A/B/C/D 的 Maven 测试；
2. 真实 MySQL 8 初始化四库、四账号；
3. 执行 acceptance smoke 和数据库边界检查；
4. 执行三端测试与生产构建；
5. 执行 UC01–UC13 端到端测试；
6. 前序成功后才构建并发布镜像；
7. CD 只部署与通过 CI 相同的提交 SHA；
8. 部署失败时输出 `kubectl get/describe/logs/events` 诊断；
9. 成功和失败均保留原始流水线报告。

### 4.8 HPA 自动扩缩容测试

目标：验证 Gateway、A/B/C/D 五个 Java Deployment 均具备独立 HPA。

测试方法：

- 在生产或验收 k3s 集群中通过 Gateway 发起真实业务请求；
- 负载按比例覆盖 A 用户资料、B 首页、C 订单列表、D 门店评价；
- 持续采集 HPA 副本数、Pod CPU/内存、节点资源和事件；
- 验证压力阶段至少两个业务服务副本数大于 1；
- 验证压力结束后 Gateway 与 A/B/C/D 最终全部恢复为 1 个副本；
- 整体错误率不超过 5%，容器重启数为 0。

### 4.9 依赖故障测试

目标：验证下游依赖故障时系统具备隔离、降级和恢复能力。

选定场景：商家与商品服务 B 不可用时，交易与履约服务 C 的购物车处理。

验证点：

- B 不可用时，公开商品接口失败；
- C 查询购物车返回最近持久化商品快照，并标记 `catalogAvailable=false`；
- C 新增商品和修改数量快速失败，且数据库无部分写入；
- C 移除商品和清空购物车仍可用；
- Gateway、A、C、D 健康状态不因 B 故障而联动失败；
- B 恢复后，商品接口和 C 购物车正常写入恢复，无需重启 C。

### 4.10 性能测试

目标：满足改造前后性能对比要求。

计划口径：

| 项目 | 要求 |
| --- | --- |
| 被测版本 | 单体版本与微服务版本 |
| 机器 | 同一服务器或同一硬件环境 |
| 数据库 | 同一 MySQL 实例或等价 MySQL 配置 |
| 数据 | 同一批业务数据，响应业务 JSON 等价 |
| 接口 | 选择 2–3 个主要接口，本项目采用首页、推荐列表、门店搜索 |
| 压力 | 同一脚本、同一并发、同一轮次和同一预热策略 |
| 轮次 | 单体与微服务各至少 3 轮 |
| 指标 | 吞吐、平均响应、P95/P99、错误率、CPU、内存 |
| 证据 | 每请求 JSONL、资源采样、汇总 JSON/CSV、机器配置和响应等价哈希 |

结论必须限定在实测接口和实测环境内，不能泛化为“微服务天然更快”。

## 6. 测试数据策略

1. 默认演示数据由各服务 repeatable seed 提供，正常启动不得依赖人工导入；
2. 测试账号覆盖用户、商家和管理员三类角色；
3. E2E 测试数据要能重复执行，必要时按测试前缀或固定 ID 清理；

## 8. 缺陷管理

缺陷按严重程度分为四级：

| 等级 | 定义 | 示例 | 处理要求 |
| --- | --- | --- | --- |
| S1 阻塞 | 系统无法启动、核心链路不可用、数据错乱或安全边界失效 | Gateway 无法路由、跨库权限放开、下单产生错误订单 | 立即停止发布，修复后全量回归 |
| S2 严重 | 主要业务不可用或结果错误，但可局部绕过 | 退款未释放预约、评价权限误判、库存幂等失效 | 修复后执行相关集成和 E2E 回归 |
| S3 一般 | 非核心功能异常或体验问题 | 页面提示不准确、报告 artifact 缺少某项日志 | 修复后执行定向回归 |
| S4 轻微 | 文档、格式、日志或展示问题 | 文档路径过期、非关键告警 | 纳入收尾清单 |

所有 S1/S2 缺陷必须有复现步骤、修复记录和回归结果。

## 9. 风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 文档完成态与当前分支文件不一致 | 验收材料失真 | 测试报告明确区分“当前工作树可见文件”和“生产验收证据”，以最终同 SHA 记录为准 |
| 跨服务调用超时或补偿不完整 | 订单、优惠券、库存状态不一致 | 增加幂等键、补偿记录和故障注入回归 |
| 四库 seed 不一致 | E2E 或性能测试不稳定 | 固化默认账号、门店、商品、订单和券码 ID，并在测试前校验 |
| HPA 依赖 metrics-server | 不能证明自动扩缩容 | CD 或实验脚本检查 HPA target 与 CPU 指标可用性 |
| 单节点资源不足 | 扩容和性能测试受限 | 记录 CPU/内存、限制 HPA 副本和并发，结论限定在当前环境 |
| 测试报告泄露敏感信息 | 安全风险 | 上传前扫描令牌、密码、手机号、邮箱和配置文件内容 |

## 11. 结论

本测试计划以课程要求为主线，以最新微服务验收材料为依据，覆盖从服务内测试、跨服务契约、数据库边界、三端端到端、容器化部署、CI/CD、Kubernetes、HPA、故障隔离到性能对比的完整测试范围。执行时应坚持“所有公开业务流量经 Gateway、所有跨服务写入有幂等、所有测试结果可追溯、所有部署失败可诊断、所有性能结论有原始数据”的原则。
