> 验收依据：`docs/stage-new-1/软工小学期.md`、`docs/stage-new-3/微服务并行拆分分工与统一标准.md`、当前仓库代码、GitHub Actions 和生产 k3s 实测结果

## 1. 结论

第二阶段的“业务微服务拆分”和“微服务 CI/CD”主体已完成。当前系统是 Gateway + A/B/C/D 四个业务微服务，具备独立构建、独立测试、独立镜像和独立 Kubernetes Workload；四个服务使用四个独立 schema 和四个不同数据库账号，全部 12 项跨库访问都由真实 MySQL 权限拒绝。

自动交付主链路是：

```text
main push
  -> aituan-microservices-ci（全量测试与 7 镜像可构建验证）
  -> aituan-microservices-deploy（校验同一 SHA）
  -> 复跑质量门禁
  -> 发布 7 个不可变 SHA 镜像
  -> k3s 滚动部署
  -> 5 服务版本/健康、7 镜像、三端、三角色登录、APK 复验
```

因此，“合拢后能否启动、能否对接、是否有完整微服务 CI/CD”已经具备通过条件。课程 Part 2 还有三类实验证据需要单独完成：HPA 加压扩缩容、依赖故障注入与恢复记录、微服务与单体在同条件下的三轮性能对比。这三项不是合拢或生产启动缺陷，但是课程第二阶段验收材料的剩余项。

## 3. 已完成的工程内容

### 3.1 代码、接口与数据

- 已将 A/B/C/D 四个分工分支合拢到同一可交付基线，共享面由集成版统一，不依赖分支名称。
- Gateway 是唯一公开 API 入口，`/internal/**` 不对外暴露，外部伪造的内部调用头会被清理。
- C 的下单、支付、商家接单、配送、完成与 D 的评价、A 的成长值/消息、B 的库存扣减已串成真实跨服务链路。
- 四库 Flyway 迁移和默认 seed 归属各自服务；正常启动使用课程默认演示数据，不包含压测或验收临时数据。
- 仓库仍只使用 README 原有的两份用户配置：`.config` 对应 `.config.example`，`deploy/.env` 对应 `deploy/.env.example`；真实密码不入库。

### 3.2 测试与质量门禁

`aituan-microservices-ci` 包含：

- 旧单体静态回归、Java 测试/JaCoCo 门禁和 MySQL 8 迁移 smoke；
- Gateway、A/B/C/D 五个 Java 模块独立 `clean verify`；
- Merchant/Admin 的 Vitest 覆盖率测试与生产构建；
- Flutter `analyze`、测试/覆盖率和 Web 生产构建；
- 离线消费者契约、真实 Provider 契约和跨服务 acceptance smoke；
- MySQL 8.4 四 schema 迁移、四账号所有权、12 项跨库拒绝和跨 schema FK 检查；
- 三端生产产物通过 Gateway 执行 UC01–UC13，实际为 15 条 Playwright 场景；
- Compose/Kubernetes 合约和 7 个生产镜像可构建验证；
- 无论成功或失败都生成可下载的原始流水线报告。

本次整理前的最新完整 CI 证据为 GitHub Actions run `33609028904`，对应提交 `472655592c9bc899ccb42a2e4d825ec54b3cfcaa`，结果成功。最终合入 `main` 后仍必须由新的同 SHA CI 成功记录触发下游 CD，不使用旧 run 绕过门禁。

### 3.3 CD 是否包含全部测试和微服务

包含，但要按两段式流程理解：

1. 第一段 `aituan-microservices-ci` 运行上一节的完整测试，特别是真实 MySQL 四库、跨服务链路和 UC01–UC13。
2. 第二段 `aituan-microservices-deploy` 仅接受第一段成功的精确 `head_sha`，再次运行静态检查、全部 Java `clean verify`、两个 Vue 端覆盖率测试、Flutter analyze/test 和三端生产构建。
3. 质量门禁通过后，CD 发布 `api-gateway`、`identity-asset-service`、`merchant-catalog-service`、`trade-fulfillment-service`、`engagement-platform-service`、`mysql`、`web` 共 7 个镜像。
4. k3s 部署后，CD 等待 MySQL StatefulSet 与 6 个 Deployment 滚动完成，检查 5 个 Java 健康/版本端点、7 个实际镜像标签、用户/商家/管理三端、三角色默认账号登录和 APK 下载。

真实 MySQL + 15 条 E2E 不在 deployment job 里重复跑，而是作为同 SHA 的必经上游门禁。如果它们失败，CD 不会发布或部署。这仍是完整 CD，同时避免在部署 job 中再启动一套重复集成环境。

### 3.4 生产部署

- 生产服务器为 `aituan-new`（4C16G），运行单节点 k3s，namespace 为 `aituan`。
- GitHub Repository Variables 保持 `AUTO_DEPLOY_PRODUCTION=true`、`DEPLOY_TARGET=k8s`、`K8S_NAMESPACE=aituan`。
- Production Environment 已使用新服务器的 SSH、known_hosts、kubeconfig、应用配置和四库密码；配置和密码不写入仓库。
- `aituan.2b.gs` 已指向新服务器，80/443 可达，Let's Encrypt 证书和续期后同步 k3s Secret 的 hook 已配置。
- 手工基线已验证公网健康、三端页面、三角色登录、APK 和四库隔离；本文档提交后还要以 `main` 的真实自动 CD 再次证明同一结论。

## 5. 还需完成的课程验收工作

### 5.1 HPA 自动扩缩容实验

1. 确认 `metrics-server` 可用，保存 `kubectl top pod` 和初始 `kubectl get hpa -w` 输出。
2. 对 B 的搜索或首页读接口持续加压，记录 Pod 从 1 扩容到 2–4 的时间线。
3. 记录加压期间吞吐、平均/P95、错误率、CPU/内存和 Pod 数量。
4. 停止压力，等待 300 秒稳定窗口，保存缩容回 1 的证据。

### 5.2 依赖故障处理实验

1. 记录基线请求和全部服务健康状态。
2. 将 B 缩容到 0 或注入超时，记录新下单的明确错误，确认未错误扣减优惠券和库存。
3. 检查 A/C/D 仍健康，已有订单快照仍可查询，保存用户可见响应、相关日志和 requestId。
4. 恢复 B，记录 rollout 和恢复耗时，再次运行核心请求。

### 5.3 改造前后性能对比

1. 解压 `tests/performance/results/monolith-20260901-final.zip` 作为单体原始证据。
2. 在与单体一致的机器、seed、预热、并发 50、每轮 15000 请求和场景下，微服务版至少运行 3 轮。
3. 保存每请求 JSONL、资源采样 JSONL、机器配置、测试配置、JSON/CSV 汇总。
4. 基于实测结果解释吞吐、平均/P95/P99、错误率和 CPU/内存差异；不预设微服务一定更快。
