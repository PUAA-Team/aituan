# 微服务测试三分类与课程要求对照

## 1. 课程要求应该怎么理解

课程按测试目的分为三类，而不是按 Java、Vue、Flutter 分：

1. **单元测试**：测试关键类、方法、业务规则和异常分支，必须有断言。
2. **集成/API 测试**：测试模块调用、数据库访问和外部接口，覆盖主要成功、备选和异常路径。
3. **端到端测试**：从页面或接口入口走完整业务流程，覆盖确认清单中的全部用例。

第二阶段还单独要求“所有后端公开接口都有 API 测试、全部业务用例都做 E2E 回归”。因此后端测试是检查重点；Vue/Flutter 测试属于有价值的补充，但不能代替后端 API 和业务用例测试，也不应删除。

## 2. 当前测试按三类放在哪里

### 2.1 单元测试

| 服务 | 当前较明确的单元测试 | 内容 |
| --- | --- | --- |
| Gateway | `GatewaySecurityFilterTest` | 内部路径阻断、Request ID 生成与透传 |
| A 身份资产 | `InternalIdentityServiceTest` | 商家账号幂等开通、缺配置失败、成长值幂等 |
| B 商家商品 | `MerchantCatalogServiceUnitTest` | 库存扣减/回滚、幂等、结算报价、库存和上下架异常，共 12 条 |
| C 交易履约 | `InternalTradeServiceUnitTest` | 评价资格规则、已评价/未支付/退款异常、并发关联冲突、订单不存在，共 6 条 |
| D 互动平台 | `FileStorageServiceTest`、`StationMessageClientTest`、`ReviewOrderMarkCompensationTest` | 文件边界、通知失败隔离、评价同步补偿 |

Vue 两端各有 12 条 Vitest，Flutter 测试位于 `apps/user_app/test/`；它们也属于单元/组件测试，但答辩讲“后端单元测试”时应优先展示上表的 Java 类。

### 2.2 集成/API 测试

所有微服务 Java 测试都位于 `services/<服务名>/src/test/`。CI 的 `microservice-integration-api` 通过 `scripts/verify/test_microservices_integration_api.sh` 单独执行这一类；原 `service-test` 五服务矩阵仍执行 Maven `clean verify` 作为重复兜底。当前重点包括：

- A：`AuthControllerTest`、`AccountAssetControllerTest`、`UserAssetFeatureControllerTest`、`AdminControllerTest`、`InternalIdentityControllerTest`；
- B：`MerchantCatalogServiceIntegrationTest`、`InternalServiceClientContractTest`、Flyway 迁移测试；
- C：购物车、结算预览、订单动作、履约状态、权限、退款、券码预约、内部契约和商品故障隔离等大量 `*ApiIntegrationTest`；
- D：`PlatformInternalContractTest`、`SupportRepositoryTest`、远程客户端与应用上下文测试；
- Gateway：`GatewayRouteContractTest`。

CI 的 `mysql-four-schema-smoke` 是更高一级的真实集成测试：启动 MySQL 8、四个独立 schema、Gateway 和 A/B/C/D，执行 Flyway、跨服务 acceptance smoke、12 项跨库拒绝检查以及真实提供者契约。

需要注意：四个 `PublicEndpointInventoryTest` 只验证“代码暴露的路由与接口文档一致”，覆盖 A/B/C/D 共 47+65+56+59=227 个操作；它们不是逐个调用接口并验证成功/异常结果的 API 行为测试。

### 2.3 端到端测试

E2E 位于 `tests/e2e/specs/`，UC01—UC13 共 13 个文件、15 条 Playwright 场景。CI 会先构建用户端、商家端和管理端，再从 18080 Gateway 进入真实微服务和四库环境执行完整业务流程。

最新 `main` 提交 `6c8a06c` 的 `aituan-microservices-ci #14` 中，`MySQL 8 four-schema migration, isolation and gateway E2E` 成功，日志为 `15 passed (39.2s)`。

## 3. 现在是否满足课程要求

| 要求 | 判断 | 依据或缺口 |
| --- | --- | --- |
| 三类测试都有独立脚本并实际运行 | 满足 | 单元、集成/API、E2E 分别有 `test_microservices_*.sh`；CI 分别调用，CD 复跑前两类并校验含 E2E 的同 SHA CI |
| 测试有有效断言 | 满足 | JUnit/AssertJ/MockMvc、Vitest、Flutter、Playwright 均使用结果断言 |
| 测试失败阻断镜像和部署 | 满足 | 7 个 CI 镜像构建依赖全部测试；CD 又要求同一 SHA 的完整 CI 成功 |
| 全部 UC01—UC13 自动回归 | 满足 | 最新 CI 明确为 15 passed |
| 所有公开接口都有 API 行为测试 | **尚不能严格判定满足** | 227 个操作已做接口清单一致性检查，但存在只进清单、没有请求和业务断言的接口，例如 D 的公告、平台配置、配送设置等接口 |
| 各服务都有清晰单元测试 | 满足 | Gateway 与 A/B/C/D 均有明确隔离单元测试；C 已补 `InternalTradeServiceUnitTest` |
| 测试报告完整 | 基本满足 | 最新 CI 成功并保留 23 个 artifact，包含五服务 Surefire/JaCoCo、前端覆盖率、契约、E2E 和启动日志；答辩材料仍应再给出一张三分类总数汇总表 |
| 微服务 CI/CD | 满足 | 最新 CI `#14` 与同 SHA CD `#11` 均成功，7 个镜像发布并完成 k3s 部署验证 |

结论：**流水线结构、三类独立测试入口、五服务单元测试和自动部署门禁已经满足课程检查形式；若目标是严格按评分文字拿满“所有公开接口用例回归”，仍需补齐公开接口行为测试证据。** Vue/Flutter 测试不是主要缺口，不应把补测时间优先花在继续堆前端覆盖率上。

## 4. 最小补强顺序

1. 先生成“227 个公开操作 → API 测试类/方法”的追溯表，对没有真实请求断言的接口补 MockMvc/API 测试，优先处理 D，再检查 A/B/C。
2. 最终测试报告列出三类测试的总数、通过数、失败数、跳过原因和运行环境，并链接到 Actions 原始 artifact。

本次分类脚本本地验证结果：单元测试 30/30 通过；集成/API 测试共记录 92 条，其中 90 通过、0 失败、2 条真实 MySQL smoke 按条件跳过；E2E 脚本正确枚举 UC01—UC13 的 13 个文件、15 条场景。两条 MySQL smoke 会在 CI 四库环境验证。上述是本地分类结果；提交后仍应从新 Actions artifact 汇总最终流水线证据。
