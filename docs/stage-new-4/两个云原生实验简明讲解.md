# 两个云原生实验简明讲解

## 实验一：多服务 HPA 实压扩缩容

Gateway 与 A/B/C/D 共 5 个 Java Deployment 都配置了 `autoscaling/v2` HPA：CPU 目标 50%，副本范围 1—4。扩容立即生效，降容有 120 秒稳定窗口，避免流量抖动。

实验脚本在 k3s 内创建临时 Node.js Job，以 40 并发持续 180 秒，等比例请求 A 用户资料、B 首页、C 订单列表和 D 门店评价，全部经过 Gateway。脚本每 10 秒记录 HPA 副本和 Pod CPU/内存，并自动断言：错误率不超过 5%、至少两个业务服务扩到 2 个以上、停止压力后 5 个 HPA 全部回到 1 个副本。

手动演示时使用两个终端：

```bash
# 终端一：确认上下文后启动实验
kubectl config current-context
kubectl -n aituan get hpa,pods
HPA_LOAD_DURATION_SECONDS=180 HPA_LOAD_CONCURRENCY=40 \
  bash scripts/experiments/run_hpa_experiment.sh

# 终端二：观察 CPU、期望副本和实际 Pod 数变化
watch kubectl -n aituan get hpa,pods
```

应看到 5 个服务从 1 个 Pod 扩容，压力结束并经过稳定窗口后再缩回 1。正式实测中 20,726 个请求、吞吐 114.89 req/s、错误率 0.936%；Gateway 和 A/B/C/D 均由 1 扩到 4，最后全部回到 1，容器重启数为 0。

## 实验二：商品服务故障隔离与恢复

B 拥有商品实时价格和库存，C 拥有购物车。正常加入购物车时，C 把商品名称、价格等展示字段持久化到自己的数据库作为快照；因此 B 故障时，C 不跨库，也不随 B 一起崩溃。

故障策略是：查询购物车返回 C 的快照并标记 `catalogAvailable=false`；新增和改数量在数据库修改前快速失败，避免错误价格和部分写入；删除、清空只操作 C 自己的数据，仍可使用；Gateway、A、C、D 的独立功能继续工作。B 恢复后，C 下一次请求自动恢复实时校验，不需要重启。

推荐直接运行带自动恢复保护的完整演示：

```bash
kubectl config current-context
bash scripts/experiments/run_catalog_fault_experiment.sh
```

脚本会自动执行“正常加入商品 → 暂停 B 的 HPA 并把 B 缩为 0 → 验证购物车降级、写入拒绝且数据未变化、A/C/D 仍健康 → B 恢复为 1 → 再次加入成功 → 清理购物车”。即使失败或中断，`trap` 也会尝试恢复 B 和 HPA。

答辩时可同时观察：

```bash
watch kubectl -n aituan get deploy,pods,hpa
```

正式实测中，B 停止后上述断言全部通过，恢复 B 后 33 秒内商品接口和购物车写入恢复，五个服务最终均健康。

实现与证据：`scripts/experiments/run_hpa_experiment.sh`、`scripts/experiments/run_catalog_fault_experiment.sh`、`docs/stage-new-4/experiments/hpa-b8660d3-pass1/`、`docs/stage-new-4/experiments/catalog-fault-b8660d3-pass4/`。实验会真实改变生产副本，演示前必须确认 Kubernetes 上下文，且不要同时执行两个实验。
