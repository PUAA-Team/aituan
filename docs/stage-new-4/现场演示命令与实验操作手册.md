# 现场演示命令与实验操作手册

> 本手册按实际仓库入口编写。默认生产域名为 `https://aituan.2b.gs`，Kubernetes namespace 为 `aituan`。
> HPA 和故障实验会真实改变验收集群副本，必须先确认上下文；两项实验禁止同时运行。

> 本文件是录制准备和应急手册，不要求把所有命令拍进视频。4 分钟成片只使用“CI/CD 与 Kubernetes、UC04→UC05 及两条测试、HPA、依赖故障”四部分，详细排期见 `现场演示视频方案与逐段脚本.md`。

## 1. 录制前一天：一次性准备

### 1.1 工具

录制机器需要：Git、Bash、JDK 17、Maven、Node.js 24、npm、kubectl、jq、curl，以及能访问仓库 Actions 和验收 k3s 的权限。Playwright 浏览器应提前安装，不要在正式录制时下载：

```bash
cd tests/e2e
npm ci
npx playwright install chromium
```

Windows 建议使用 WSL 或 Git Bash 运行 `scripts/experiments/*.sh`。PowerShell 可以承担观察窗口，但不要直接用 PowerShell 解释 Bash 脚本。

### 1.2 录制目录和文件名

在仓库外准备原始录屏目录，避免把大视频误提交到 Git：

```text
recording/
├─ raw/
├─ edited/
├─ subtitles/
└─ screenshots/
```

成片统一命名：

```text
01-CICD与Kubernetes.mp4
02-核心业务与自动化测试.mp4
03-HPA扩缩容.mp4
04-依赖故障隔离.mp4
```

### 1.3 集群只读预检

在仓库根目录执行。以下命令不修改集群：

```bash
kubectl config current-context
kubectl cluster-info
kubectl get nodes -o wide
kubectl -n aituan get deployments,statefulsets,pods,svc,hpa -o wide
kubectl top nodes
kubectl -n aituan top pods
curl -fsS https://aituan.2b.gs/actuator/health | jq .
```

通过条件：

- 当前上下文明确指向验收集群，节点为 `Ready`；
- `api-gateway`、A/B/C/D、`aituan-web` 可用，MySQL StatefulSet Ready；
- 5 个 HPA 都有 CPU `TARGETS`，不能是 `<unknown>`；
- 公网健康返回 `UP`；
- 没有不明的压力 Job 或正在进行的故障实验。

再检查实验所需权限：

```bash
kubectl auth can-i create jobs -n aituan
kubectl auth can-i create secrets -n aituan
kubectl auth can-i patch horizontalpodautoscalers -n aituan
kubectl auth can-i patch deployments -n aituan
```

四项都应输出 `yes`。如果不是，不要使用更高权限账号硬闯，应由集群负责人配置最小必要权限。

### 1.4 服务恢复基线

```bash
kubectl -n aituan get hpa/merchant-catalog-service \
  -o jsonpath='{.spec.scaleTargetRef.name}{"\n"}'
kubectl -n aituan get deployment/merchant-catalog-service \
  -o jsonpath='{.status.readyReplicas}{"\n"}'
```

第一条必须是 `merchant-catalog-service`，第二条至少是 `1`。否则说明上一次故障实验没有恢复，应先按第 8.3 节恢复。

## 2. 视频 01：真实提交和 CI/CD

### 2.1 选择演示改动

本次推荐使用一个肉眼可见、且不参与业务逻辑的首页卡片标题改动：

```diff
- Text('爱团服务', style: Theme.of(context).textTheme.titleMedium),
+ Text('生活服务', style: Theme.of(context).textTheme.titleMedium),
```

只修改这一个文件：

```text
apps/user_app/lib/features/home/presentation/widgets/home_module_grid.dart
```

这行文字只负责展示，不参与点击、路由、接口参数或业务判断；仓库中的 E2E 和 Flutter 测试也没有使用“爱团服务”定位元素。因此不需要同步改测试，录屏时可以明确说“本次只修改一行纯展示文案”。

不要只改 `docs/**`，因为微服务 CI 的 `paths` 不包含文档目录。不要使用空提交或无意义格式化冒充代码提交。

### 2.2 提交前

若采用“直接推送 main”的演示方式，应在开始修改前从干净工作区同步 main：

```bash
git fetch origin
git switch main
git pull --ff-only origin main
```

如果团队使用分支保护，则留在功能分支并走 PR，不要为了录制临时关闭保护规则。

先确认没有混入他人的工作：

```bash
git status --short
git branch --show-current
git diff --check
git diff --stat
```

如果工作区还有与演示无关的文件，停止并由对应成员处理，不要执行 `git reset --hard` 或整目录暂存。

先确认提交中只有这一行预期改动：

```bash
git diff -- apps/user_app/lib/features/home/presentation/widgets/home_module_grid.dart
rg -n '生活服务' \
  apps/user_app/lib/features/home/presentation/widgets/home_module_grid.dart
```

这个改动不需要调整测试代码，提交前运行 Flutter 静态检查；完整测试仍由本次 CI 执行：

```bash
cd apps/user_app
flutter analyze
cd ../..
```

其他改动可根据类型选择一条针对性测试：

```bash
# Java 服务示例，把模块名替换为实际模块
mvn -B -f services/pom.xml -pl trade-fulfillment-service -am test

# 跨服务离线契约
node tests/contracts/contract-test.mjs \
  --output /tmp/aituan-demo-offline-contract-report.json

# 单个 Playwright 场景
cd tests/e2e
npx playwright test uc04-takeaway-order-flow
```

### 2.3 暂存、提交、推送

只暂存本次一个前端文件：

```bash
git add -- apps/user_app/lib/features/home/presentation/widgets/home_module_grid.dart
git diff --cached --check
git diff --cached --stat
git commit -m "fix: refine home service heading"
git rev-parse HEAD
git push origin main
```

`git push origin main` 会触发生产发布链路，录制前必须由项目负责人确认。若团队规定只能走 PR，则录制“功能分支 commit/push → PR CI → 合并 main → main CI → 自动 CD”，不要直接绕过分支保护。

复制 `git rev-parse HEAD` 的完整 SHA，后续四处核对：

1. `aituan-microservices-ci` 的 commit；
2. `aituan-microservices-deploy` 的 `DEPLOY_SHA` / image tag；
3. Kubernetes 运行镜像 `sha-<完整 SHA>`；
4. `/actuator/info` 中的 image tag。

### 2.4 GitHub Actions 页面操作顺序

1. 打开仓库 → `Actions` → `aituan-microservices-ci`。
2. 打开刚刚由 `push` 创建的 run，核对 `main`、提交标题、触发时间和 SHA。
3. 打开 Job `Classified microservice unit tests`。
4. 展开 Step `Run isolated Gateway and A/B/C/D unit tests`，滚到日志末尾附近，展示实际的 `Tests run: N, Failures: 0, Errors: 0` 和 `BUILD SUCCESS`。
5. 返回 Job 列表，打开 `Classified microservice integration and API tests`。
6. 展开 Step `Run controller, API, contract, migration, and boundary tests`，展示实际 `Tests run: N`、零失败、零错误以及 `BUILD SUCCESS`。
7. 打开 `MySQL 8 four-schema migration, isolation and gateway E2E`，展开 `Run gateway-backed E2E scenarios`，展示 Playwright 结尾的 `15 passed`。
8. 快速扫过 `Test api-gateway` 与 A/B/C/D、Web/Flutter、离线契约、Kubernetes 合约等 Job 均为绿色；无需逐一展开。
9. CI 全绿后，回到 Actions，打开自动出现的 `aituan-microservices-deploy`。
10. 展开 `Require successful full microservice CI for this exact SHA`，显示 `Verified full CI run ... for <SHA>`。
11. 展示 `Publish ... image` 七镜像矩阵为绿色。
12. 打开 Job `Migrate, deploy, and verify Kubernetes`，展开 `Wait for every workload rollout`，展示各 `deployment/... successfully rolled out`。
13. 可展开 `Verify all internal services and public three-end site`，证明五个内部服务、三端入口和镜像标签检查通过。
14. 页面底部展示 `microservices-k8s-deployment-sha-...` artifact；其中 `resources.txt` 是部署后的 Pod/Service/HPA/PVC 表，`images-after.txt` 是部署后的镜像 SHA。

流水线等待可以加速，但开头、job 状态变化、成功结尾和两个 run ID 必须保留。由于 CI 对同一 ref 设置了 `cancel-in-progress: true`，录制期间不要让其他成员再推送 `main`。

注意：Maven 单元与 API 测试按测试类和模块分别打印 `Tests run: N`，没有单个汇总的 `N passed`。画面使用本轮真实日志数字即可。Playwright E2E 会直接打印 `15 passed`，可以在字幕中明确写出。

## 3. 视频 01 后半：Kubernetes 部署和 Pod

Actions 的 `Wait for every workload rollout` 会在日志中显示 rollout 成功，但命令把完整资源表写入 artifact，并不会把整张 Pod 表直接打印在该 Step 页面。因此视频中采用两层证据：先展示 CD Step 成功，再切到终端实时展示 Pod、HPA 和镜像 SHA。

### 3.1 工作负载与 Pod

```bash
kubectl config current-context
kubectl get nodes
kubectl -n aituan get deployments,statefulsets,pods,hpa -o wide
```

画面应能读到：

- 6 个 Deployment：`api-gateway`、A/B/C/D、`aituan-web`；
- 1 个 StatefulSet：`mysql`；
- Pod 的 `READY`、`STATUS`、`RESTARTS`；
- 5 个 HPA 的 `TARGETS`、`MINPODS=1`、`MAXPODS=4` 和副本数。

### 3.2 镜像 SHA

```bash
kubectl -n aituan get deployments \
  -o custom-columns='KIND:.kind,NAME:.metadata.name,IMAGE:.spec.template.spec.containers[*].image'
kubectl -n aituan get statefulset/mysql \
  -o custom-columns='KIND:.kind,NAME:.metadata.name,IMAGE:.spec.template.spec.containers[*].image'
```

所有镜像应使用同一个 `sha-<提交 SHA>` 标签。不要只展示 `latest` 或 `microservices` 浮动标签。

### 3.3 Rollout、健康和版本

```bash
kubectl -n aituan rollout status statefulset/mysql --timeout=600s
kubectl -n aituan rollout status deployment/api-gateway --timeout=600s
kubectl -n aituan rollout status deployment/identity-asset-service --timeout=600s
kubectl -n aituan rollout status deployment/merchant-catalog-service --timeout=600s
kubectl -n aituan rollout status deployment/trade-fulfillment-service --timeout=600s
kubectl -n aituan rollout status deployment/engagement-platform-service --timeout=600s
kubectl -n aituan rollout status deployment/aituan-web --timeout=600s
curl -fsS https://aituan.2b.gs/actuator/health | jq .
curl -fsS https://aituan.2b.gs/actuator/info | jq .
```

如果只想拍一行一行出现的动态过程，可在 CD 尚未完成时先执行 rollout status；如果录制的是已完成部署，则直接展示成功结果，不要伪造等待动画。

### 3.4 重新访问线上地址验证前端变化

Flutter Web 可能受浏览器缓存或 Service Worker 影响。CD 完成后不要只刷新原标签页，建议新开无痕窗口访问：

```text
https://aituan.2b.gs/web/
```

最终画面同时保留地址栏和首页功能入口卡片，确认同一线上地址的标题已从：

```text
爱团服务
```

变为：

```text
生活服务
```

若无痕窗口仍是旧文案，先核对 CD 是否成功、`aituan-web` Deployment 镜像是否为本次 `sha-<提交 SHA>`，不要反复剪辑刷新来掩盖未部署成功。

## 4. 视频 02 前半：核心业务手工流程

### 4.1 浏览器准备

开三个独立浏览器配置文件或三个无痕窗口，避免登录态互相覆盖：

| 端 | URL | 账号 | 密码 |
| --- | --- | --- | --- |
| 用户端 | `https://aituan.2b.gs/web/` | `demo_user` | `123456` |
| 商家端 | `https://aituan.2b.gs/merchant/` | `demo_merchant` | `123456` |
| 管理端 | `https://aituan.2b.gs/admin/` | `demo_admin` | `123456` |

关闭密码管理器弹窗和浏览器通知；保留地址栏中的域名。演示数据全部使用默认账号，不展示手机号、邮箱、地址详情等无关个人字段。

### 4.2 UC04 用户外卖下单

1. 用户登录并回到首页。
2. 点击“外卖”模块或外卖推荐，进入门店“外卖点单”。
3. 选择在售商品并增加数量，直到满足起送价。
4. 打开“购物车”，点击“去确认订单”。
5. 选择已有演示地址；核对商品金额、配送费和应付金额。
6. 支付方式保持“模拟支付”，点击“提交并支付”。
7. 打开订单详情，记下订单号；画面停留在“支付成功”和“待商家接单/已接单”。

如果没有合适地址，录制前先从“我的 → 地址”创建一个演示地址。不要在录制时输入真实地址。

### 4.3 UC05 商家履约

1. 商家端登录，确认“接单模式”为手动。
2. 打开“订单中心”，按刚才的订单号定位订单并展开详情。
3. 依次执行：`接单 → 开始备餐 → 出餐 → 推进配送 → 推进配送 → 完成订单`。
4. 每次点击后等待成功提示和新状态出现，再进行下一步。
5. 用户端打开“订单”，刷新同一订单，应显示已完成/可评价。
6. 打开配送时间线，展示 accepted、delivering、delivered、completed。
7. 打开“消息 → 订单”，展示与本订单关联的状态消息。

如果商家端一开始没有“接单”而是“开始备餐”，说明订单被自动接单；不要把它说成测试失败，先停止录制并把商家接单模式切回手动后重新创建订单。

### 4.4 UC09 评价、商家回复、平台治理（本次 4 分钟视频不录）

1. 用户端在已完成订单中点击“去评价”。
2. 输入带当天唯一标记的内容，例如 `答辩演示-0903-五星评价`，提交五星评价。
3. 商家端打开“评价管理”，按唯一标记找到该评价，输入回复并发送。
4. 用户端刷新评价详情，展示商家回复。
5. 管理端打开“评价审核”，找到同一评价，填写演示备注并点击“屏蔽”。
6. 用户端刷新公开评价列表，确认该评价不可见。
7. 管理员点击“恢复”；用户端刷新后重新看到评价及回复。

记录订单号和评价唯一标记到字幕工程中。剪辑时即使切换三端，也要在角落保留这两个标识。

## 6. 视频 03：HPA 压力扩缩容

### 6.1 正式参数

正式录制沿用已验证参数：180 秒、40 并发。压力脚本在集群内创建临时 Node Job，经 Gateway 等比例调用 A 用户资料、B 首页、C 订单列表和 D 门店评价。

不要同时运行性能对比或故障实验。先执行：

```bash
kubectl -n aituan get hpa
kubectl -n aituan get pods
kubectl top nodes
kubectl -n aituan top pods
```

5 个 HPA 应全部为 1 个副本且 `TARGETS` 有值。若前一轮仍在冷却，等它自然回到 1 再录。

### 6.2 终端 A：持续观察

```bash
while true; do
  clear
  date
  kubectl -n aituan get hpa
  kubectl -n aituan get pods
  kubectl -n aituan get jobs
  sleep 5
done
```

PowerShell 观察窗口：

```powershell
while ($true) {
  Clear-Host
  Get-Date
  kubectl -n aituan get hpa
  kubectl -n aituan get pods
  kubectl -n aituan get jobs
  Start-Sleep -Seconds 5
}
```

观察结束用 `Ctrl+C`，不会修改集群。

### 6.3 终端 B：触发真实负载

```bash
export HPA_OUT="$PWD/docs/stage-new-4/recording-evidence/hpa-$(date +%Y%m%d-%H%M%S)"
HPA_LOAD_DURATION_SECONDS=180 \
HPA_LOAD_CONCURRENCY=40 \
HPA_EXPERIMENT_OUTPUT_DIR="$HPA_OUT" \
bash scripts/experiments/run_hpa_experiment.sh
```

脚本会自动：

1. 检查 5 个 HPA 和五服务 rollout；
2. 创建 ConfigMap、Secret 和压力 Job；
3. 每 10 秒采集 HPA、副本、Pod CPU/内存；
4. 压力结束后等待最多 360 秒，直到五个 HPA 全部恢复为 1；
5. 校验总请求数大于 0、错误率不超过 5%、至少两个业务服务曾扩容；
6. 删除临时 Job、ConfigMap 和 Secret。

### 6.4 展示结果

```bash
jq '{startedAt,endedAt,config,overall}' "$HPA_OUT/load-summary.json"
awk -F '\t' '
  NR > 1 && $4 + 0 > max[$3] { max[$3] = $4 + 0 }

' "$HPA_OUT/hpa-timeline.tsv" | sort
kubectl -n aituan get hpa
kubectl -n aituan get pods
```

通过画面应同时包含：总体请求/错误率、每个服务达到的最大副本数、最终五个 HPA 回到 `1/1`。不要只截“扩到 4”的瞬间。

## 7. 视频 04：商品服务故障隔离

### 7.1 终端 A：观察 B 是否真的下线

```bash
while true; do
  clear
  date
  kubectl -n aituan get deployment/merchant-catalog-service
  kubectl -n aituan get pods -l app.kubernetes.io/name=merchant-catalog-service
  kubectl -n aituan get hpa/merchant-catalog-service
  kubectl -n aituan get deployment/api-gateway
  kubectl -n aituan get deployment/identity-asset-service
  kubectl -n aituan get deployment/trade-fulfillment-service
  kubectl -n aituan get deployment/engagement-platform-service
  sleep 3
done
```

### 7.2 正式录前端：运行分阶段暂停的 SSH 脚本

服务器已经准备好交互脚本。它会在正常基线、B 下线和 B 恢复后三次暂停，给录制者切换前端的时间：

```bash
ssh aituan-new
cd /tmp/aituan-fault-demo
./record_catalog_fault_demo.sh
```

完整的前端点击顺序、逐秒脚本和应急恢复见 `视频04-依赖故障隔离-前端与SSH录制版.md`。

不要用下面的全自动脚本录制前端主画面，因为它会连续完成验证并恢复 B，没有人工操作暂停。下面的命令只用于无人值守复验和保存完整证据：

export FAULT_OUT="$PWD/docs/stage-new-4/recording-evidence/catalog-fault-$(date +%Y%m%d-%H%M%S)"

不要手工另开窗口缩容 B。脚本会先保存购物车快照，再临时把 B HPA 的目标改为不存在的故障注入目标，随后将 B Deployment 缩为 0；这样 HPA 不会立刻把 B 拉起。退出时 `trap` 会尝试恢复 HPA 和 B。

### 7.4 实验真实改变了什么

| 阶段 | B Deployment | B HPA | C 购物车 |
| --- | ---: | --- | --- |
| 基线 | 1 | 指向 B | 正常创建快照 |
| 故障 | 0 | 临时指向不存在目标 | 读快照；新增/改数量拒绝；移除可用 |
| 恢复 | 1 | 重新指向 B | 实时校验恢复，脚本清空测试购物车 |

Gateway、A、C、D 不应被缩容或重启。C 的存活探针只检查自身 liveness，不把 B 当作自身存活条件。

## 8. 恢复与应急

### 8.1 HPA 脚本中断

脚本会清理临时 Job、ConfigMap、Secret；压力消失后 HPA 应自然缩回 1。先等 6 分钟并观察：

```bash
kubectl -n aituan get jobs,configmaps,secrets | grep aituan-hpa-load || true
kubectl -n aituan get hpa
kubectl -n aituan get pods
```

如果副本仍未回落，保存 `kubectl -n aituan describe hpa` 和事件，不要立刻手工缩容并继续录制；先查明是否仍有其他压力源。

### 8.2 HPA 没有扩容

依次检查：

```bash
kubectl -n aituan get hpa
kubectl top nodes
kubectl -n aituan top pods
kubectl -n aituan get jobs,pods
kubectl -n aituan get events --sort-by=.lastTimestamp
```

常见原因：metrics-server 无指标、压力 Job `ImagePullBackOff`、演示账号登录失败、集群本身资源不足、上一轮 HPA 尚未稳定。正式参数 180 秒/40 并发已经在当前 4C16G 基线上通过；只有排除故障后再完整重录，不要在失败的一半临时改变参数后拼接成“成功”。

### 8.3 故障脚本中断后的人工恢复

即使脚本已有 `trap`，仍应执行以下检查：

```bash
kubectl -n aituan get hpa/merchant-catalog-service \
  -o jsonpath='{.spec.scaleTargetRef.name}{"\n"}'
kubectl -n aituan get deployment/merchant-catalog-service
```

若 HPA 目标不是 `merchant-catalog-service`，或 B 未恢复，执行：

```bash
kubectl -n aituan patch hpa/merchant-catalog-service \
  --type=merge \
  -p '{"spec":{"scaleTargetRef":{"name":"merchant-catalog-service"}}}'
kubectl -n aituan scale deployment/merchant-catalog-service --replicas=1
kubectl -n aituan rollout status deployment/merchant-catalog-service --timeout=300s
kubectl -n aituan get deployment/merchant-catalog-service
kubectl -n aituan get hpa/merchant-catalog-service
curl -fsS https://aituan.2b.gs/api/app/discovery/home | jq '.code'
```

如果中断发生在清理购物车之前，B 恢复后使用用户端购物车“清空”按钮删除本轮测试数据。

### 8.4 CI 未触发或 CD 未触发

- CI 未触发：检查是不是只改了 `docs/**`、推送分支是否在允许列表、Actions 是否被禁用。
- CI 被取消：同一 ref 又发生了新 push；让全组暂停提交后重新推送一个真实修复。
- CD 未触发：自动 CD 只监听 `main` 的 `aituan-microservices-ci` 完成事件，而且 CI 必须成功；再核对 `AUTO_DEPLOY_PRODUCTION` 与 `DEPLOY_TARGET=k8s`。
- 手动 CD 失败在同 SHA 门禁：先让精确 SHA 的完整微服务 CI 成功，不能拿旧 SHA 的成功记录绕过。

### 8.5 业务场景失败

- 找不到订单：确认商家为 `demo_merchant`，并使用刚才记录的订单号。
- 缺少“接单”按钮：商家可能为自动接单；切回手动后新建订单。
- 不能下单：增加商品达到起送价，或检查演示地址是否在配送范围。
- 不能评价：订单必须已完成且同一订单未评价；使用本轮新订单。
- 后台找不到评价：使用唯一评价标记搜索或刷新列表，不要拿旧评价代替。
