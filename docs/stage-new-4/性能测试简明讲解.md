# 性能测试简明讲解

## 1. 测了什么

统一脚本 `tests/performance/load-test.mjs` 循环测试 B 商家商品域的 3 个只读主要接口：

| 场景 | 接口 |
| --- | --- |
| 首页发现 | `GET /api/app/discovery/home` |
| 推荐列表 | `GET /api/app/discovery/recommendations` |
| 门店搜索 | `GET /api/app/discovery/stores/search` |

选择只读接口是为了反复压测时不污染业务数据；本结论只代表这 3 个读场景，不代表支付、下单等写链路。

## 2. 怎么测试

单体和微服务都部署在 `aituan-new` 同一 k3s 节点，使用同一个 MySQL Pod、同一份 seed 和业务等价响应。微服务从 Gateway 进入；两端都不经过公网、TLS 和 Web Nginx。正式测试时把 HPA 固定为 1 个副本，避免扩容破坏公平性。

每个版本先预热 1,000 请求，再以并发 50 执行 15,000 请求，共跑 3 轮，轮间冷却 10 秒；两个版本合计 90,000 个正式请求。脚本逐请求记录耗时和结果，每 500 ms 从宿主 `/proc` 采集指定进程的 CPU 与 RSS 内存，最后输出 JSON/CSV 汇总。运行形式如下：

```bash
node tests/performance/load-test.mjs \
  --target monolith=http://performance-monolith:8080 \
  --target microservices=http://api-gateway:8080 \
  --pids monolith=<单体Java,MySQL PID> \
  --pids microservices=<Gateway,A,B,C,D,MySQL PID> \
  --runs 3 --concurrency 50 --requests 15000 --cooldown-ms 10000 \
  --output <结果目录>
```

成功不仅看 HTTP 200，还校验响应 JSON 的 `code=0`。测试前还对三组响应去除动态字段后做哈希比较，排除了两端数据或响应内容不同造成的假提升。

## 3. 结果怎么分析

| 三轮均值 | 单体 | 微服务 | 微服务变化 |
| --- | ---: | ---: | ---: |
| 吞吐 | 318.409 req/s | 463.943 req/s | +45.707% |
| 平均响应 | 159.643 ms | 107.765 ms | -32.496% |
| P95 | 324.870 ms | 238.821 ms | -26.487% |
| 错误率 | 0% | 0% | 相同 |
| 平均 CPU | 148.887% | 172.079% | +15.577% |
| 平均内存 | 545.113 MiB | 1433.684 MiB | +163.007% |

本次三个接口的微服务版本更快：单体 Java 平均 CPU 为 99.730%，已基本撞到 1 核限制；微服务把入口转发和商品查询分给 Gateway 与 B 两个 JVM，可并行使用更多 CPU。代价是 A/B/C/D 即使不在本次热链路上，也会占用 JVM 常驻内存，所以微服务内存约为单体的 2.63 倍。

当前微服务热点在 B：B 平均 CPU 为 74.241%，接近 750m 限制；三个接口中门店搜索最慢，代码路径存在“先查门店，再逐店补商品”的查询放大风险。后续应优先优化搜索 SQL/查询次数，或让 HPA 扩 B。结论应表述为“当前固定容量、同条件下，这 3 个只读接口更快”，不能泛化成“微服务天然更快”。

完整数据见 `docs/stage-new-4/单体与微服务同条件三轮性能对比报告.md` 和 `docs/stage-new-4/experiments/performance-comparison-65ddbf8/`。
