## 1 引言

### 1.1 编写目的
本文档旨在对爱团本地生活服务综合平台进行概要设计，明确系统的整体架构、模块划分、内外部接口设计、核心数据结构及运行模式。它为后续详细设计、编码实现和集成测试提供架构基础和统一技术依据。

预期读者为项目开发团队、设计人员、测试人员及项目管理人员。

### 1.2 背景
本项目旨在构建一个面向本地生活消费的综合服务平台，业务覆盖外卖订餐、到店团购、酒店民宿、休闲娱乐、电影演出、丽人医美、景点门票、足疗按摩等服务类型。系统遵循移动消费优先原则，用户端以 Android、iOS APP 为主，商家端和平台管理后台采用 Web 形态，后端基于 Spring Boot 构建。支付与配送均采用模拟机制，并设置 AI Agent 与 Skills 层作为智能辅助扩展能力。

### 1.3 定义
| 术语 | 说明 |
| :--- | :--- |
| 用户端 | 面向消费者的 Android / iOS 应用 |
| 商家端 | 面向商家的 Web 管理端，用于店铺、商品与服务、订单处理 |
| 平台管理后台 | 面向平台运营和管理员的 Web 管理系统 |
| 模拟支付 | 不发生真实资金结算的支付流程，仅用于验证支付结果与订单状态流转 |
| 模拟配送 | 不对接真实运力平台，由后台按业务规则推进外卖配送相关状态 |
| 烟火值 | 平台内部定义的用户活跃度或消费贡献指标，用于会员成长与权益展示 |

## 2 系统需求概述

### 2.1 需求规定

**输入项：** 用户的注册信息、搜索关键词、筛选条件、收货地址、订单备注、评价内容、商家入驻资料、商品信息、平台审核结果等。

**输出项：** 商家与服务项目列表、商家详情、订单详情与状态、支付结果、配送进度、券码/预约凭证、评价列表、经营数据看板、审核结论等。

**功能性能要求：**
- 建立完整的用户消费闭环（浏览→下单→支付→履约→评价）
- 建立商家经营闭环（入驻→商品管理→订单处理→经营查看）
- 建立平台治理闭环（审核→配置→数据看板→审计）

### 2.2 业务目标

建设统一的本地生活综合服务平台，覆盖吃、喝、玩、乐、购、服务等消费场景。

### 2.3 运行环境

#### 2.3.1 设备

**用户端：** Android / iOS 智能移动终端，支持主流屏幕尺寸。

**商家端与平台管理后台：** 运行于桌面浏览器环境，支持近两代主流 Chrome、Edge 浏览器。

**移动测试设备：** 三台 iPhone、三台 Android 手机（用于真机测试验证）、一台HarmonyOS设备（后续移植鸿蒙使用）。

**服务端：** 阿里云香港 ECS 服务器（2 vCPU，4 GB RAM，Ubuntu 系统，50 GB 以上可用存储）。

#### 2.3.2 支持软件

| 类型 | 选型 |
| :--- | :--- |
| 后端框架 | Spring Boot |
| 关系型数据库 | MySQL 8.0+ |
| 用户端开发 | Flutter SDK、Dart |
| 管理端开发 | Vue 3、Vite、Element Plus 或 Ant Design Vue |
| Web 服务器 | Nginx（反向代理 + 静态资源） |
| 版本控制 | Git |

### 2.4 设计约束
1. 用户侧以 Android、iOS 为优先建设对象，当前阶段不以桌面消费端为重点。
2. 商家端与平台管理后台采用 Web 形态建设。
3. 支付环节仅采用模拟支付机制，不涉及真实资金流转和清结算。
4. 履约环节采用后端模拟配送机制，不建设独立骑手应用。
5. AI 辅助能力不可用时，应自动降级为规则引擎、模板回复或 Mock 数据，不得阻断 P0 核心业务流程。
6. 系统实行基于角色的访问控制（RBAC），至少区分用户、商家、管理员三类角色。
7. 用户密码不得明文存储；关键操作需记录审计日志。

### 2.5 功能需求

本系统核心功能模块如下：

| 能力项 | 功能概述 |
| :--- | :--- |
| 用户账户与个人中心 | 注册、登录、地址管理、收藏、优惠券、会员/烟火值展示 |
| 商家搜索与浏览 | 关键词搜索、分类/区域/价格筛选、排序、首页推荐 |
| 商家与服务详情 | 商家信息、商品/套餐/票券/房型详情、价格规则、地图入口 |
| 购物车、下单与支付 | 购物车管理、优惠结算、订单提交、模拟支付（含幂等控制） |
| 外卖配送模拟 | 配送状态时间线、预计送达时间、模拟配送位置（可降级为阶段展示） |
| 到店团购与预约 | 券码生成与核销、日期/场次/预约时段管理、退款处理 |
| 评价互动与客服 | 评价发布（绑定已完成订单）、评价回复、举报、商家咨询 |
| 商家经营管理 | 入驻与资质、门店/商品维护、订单处理、退款审核、经营统计 |
| 平台管理与运营 | 商家审核、评价审核、投诉处理、类目/推荐位配置、数据看板 |
| AI 辅助能力 | 智能生活规划、搜索解析、推荐解释、文案生成、客服回复建议、降级保障 |

**关键业务流程概览：**

**外卖到餐流程：**
用户浏览/搜索外卖商家 → 选择商品加入购物车 → 确认订单（校验收货地址、配送可达性、优惠券） → 提交订单 → 模拟支付 → 商家接单 → 备餐 → 配送模拟进度 → 送达 → 用户确认/评价

**到店团购流程：**
用户浏览团购套餐 → 下单购买 → 模拟支付 → 生成券码 → 到店核销（商家验券） → 订单完成 → 用户评价

**上门服务预约流程：**
用户选择服务项目 → 选择技师/服务人员 → 选择预约时段 → 填写上门地址 → 提交订单 → 商家确认约 → 服务完成 → 用户评价

### 2.6 非功能需求
- **性能：** 50并发下，查询类接口95分位响应 ≤ 2s，订单提交类 ≤ 3s。首页首屏 ≤ 3s。
- **安全：** RBAC权限控制、密码加密存储、HTTPS传输、输入校验、接口限流。
- **可靠：** 关键操作幂等、AI不可用时降级、数据库每日备份、故障可恢复。
- **可维护：** 后端分层清晰、关键参数可配置、日志可追踪到订单/用户。
- **可扩展：** 模拟支付/配送/AI通过独立接口接入，可替换；数据库可增量扩展。

### 2.7 系统总体架构
系统采用前后端分离的分层架构，由六大软件配置项（CSCI）构成，通过 RESTful API 进行通信。

```text
爱团本地生活服务综合平台
├─ CSCI-01 用户端 (Android/iOS)
├─ CSCI-02 商家端 (Vue Web)
├─ CSCI-03 平台管理后台 (Vue Web)
├─ CSCI-04 后端服务系统 (Spring Boot)
│   ├─ 用户服务
│   ├─ 商家服务
│   ├─ 商品服务
│   ├─ 订单服务
│   ├─ 支付模拟服务
│   ├─ 评价服务
│   ├─ 营销会员服务
│   ├─ 消息通知服务
│   └─ 权限日志服务
├─ CSCI-05 配送模拟服务
└─ CSCI-06 AI Agent 与 Skills 层
    ├─ 智能搜索
    ├─ 智能推荐
    ├─ 智能客服
    └─ 智能运营助手
```

**架构说明：**
- **接入层：** Nginx 作为反向代理，处理 HTTPS 请求，将 `/api/*` 路由至后端服务，静态资源直返管理端页面。
- **核心服务层：** 各服务职责单一，通过清晰的服务边界协同。支付模拟服务与订单服务通过内部接口耦合；配送模拟服务由订单事件触发。
- **增强层：** 智能辅助能力依附于业务体系运行，通过统一接口接入，支持真实调用与 Mock 降级切换。
- **数据层：** MySQL 8.0 数据库统一存储所有核心业务数据。

### 2.8 设计范围与优先级

本概要设计以软件开发计划书的进度基线和软件需求规格说明书的 P0/P1/P2 优先级为范围依据。P0 功能必须在概要设计中给出模块、接口、数据和状态流转设计；P1 功能给出概要设计和扩展点；P2 功能以架构预留为主，不作为本期必交付承诺。

| 优先级 | 功能范围 | 概要设计处理方式 |
| :--- | :--- | :--- |
| P0 | 注册登录、首页、搜索、商家详情、购物车、下单结算、模拟支付、商家接单、平台商家审核、平台基础配置、外卖配送模拟 | 必须覆盖接口、数据结构、权限边界、状态流转和验收追踪 |
| P1 | 到店团购、预约类服务、评价互动、商家客服、优惠券、烟火会员等级、消息通知、基础数据看板、智能搜索与推荐 | 给出模块边界、关键数据、降级策略和后续详细设计入口 |
| P2 | 复杂营销、真实支付、真实配送、更多智能辅助能力、HarmonyOS / Web 后续移植 | 仅保留服务边界、配置开关和接口扩展点 |

## 3 系统接口设计

### 3.1 接口设计总体原则
1. 后端接口采用 RESTful 风格，使用 HTTPS 协议，请求与响应默认采用 JSON 格式。
2. 时间字段统一使用 ISO 8601 标准格式，金额字段使用统一精度（小数点后两位）。
3. 所有接口返回统一响应结构：`{code, message, data, timestamp, requestId}`。
4. 创建订单、支付回调、商家接单、审核处理等关键接口需实现幂等控制。
5. 列表接口统一支持分页（`page`, `size`）、排序（`sort`）和条件筛选。
6. 用户端、商家端和平台管理后台采用统一JWT认证机制。登录成功后签发访问令牌，服务端校验令牌合法性、有效期和角色权限。
7. 服务间不应绕过服务层直接访问他方业务边界。
8. 所有接口调用应记录请求标识、调用方身份、关键参数摘要、耗时和处理结果。涉及审核、状态流转、权限变更的操作保留完整审计记录。

### 3.2 外部接口设计

| 接口标识 | 接口类别 | 接入方式 | 主要用途 | 是否核心依赖 | 降级策略 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| EI-01 | 地图与位置服务 | HTTP/HTTPS API | 地址解析、距离估算、配送范围判断 | 否 | 故障时提示定位受限，不阻断业务 |
| EI-02 | 邮箱或短信验证码服务 | HTTP/HTTPS API | 注册、登录、敏感操作校验 | 是 | 开发环境使用固定验证码或控制台模拟 |
| EI-03 | 支付模拟 | 内部模拟服务 | 订单支付状态流转 | 是 | 不接入真实资金通道，内部模拟即可 |
| EI-04 | AI模型服务 | HTTP/HTTPS API | 智能问答、推荐辅助、内容生成 | 否 | 降级为规则引擎或Mock数据 |
| EI-05 | 图片与对象存储 | SDK/HTTP API | 商家/商品/评价图片存储 | 是 | 首期可采用本地文件存储替代 |
| EI-06 | 消息与通知 | 内部实现 | 站内消息推送 | 否 | 首期仅实现站内消息 |

### 3.3 内部接口关系

系统元素间核心接口调用关系如下：

- **用户登录→权限校验：** 用户端/商家端/后台请求携带JWT Token → 网关或权限服务校验 → 放行或拒绝。
- **下单→支付模拟：** 用户端提交订单 → 订单服务生成订单（待支付）→ 用户端发起支付 → 支付模拟服务处理 → 回调订单服务更新状态（已支付/支付失败）。
- **下单→配送模拟：** 外卖订单支付成功且商家接单 → 订单服务触发配送任务创建 → 配送模拟服务接管 → 按规则推进状态（待取餐→配送中→已送达）→ 回写订单状态。
- **订单完成→评价：** 订单服务标记“已完成”→ 评价服务开放评价入口 → 用户端提交评价 → 评价与订单强关联存储。
- **评价→审核：** 评价发布 → 平台管理后台获取待审列表 → 管理员审核通过/屏蔽 → 评价状态更新。
- **AI调用链路：** 用户/商家/平台请求AI辅助 → 后端服务调用AI Skills层 → Skills尝试外部AI服务 → 成功则返回结果，失败则返回降级数据。

### 3.4 接口分域设计

系统按访问角色和业务边界划分 API 前缀，避免用户端、商家端和平台后台共用混乱接口。

| 接口域 | 调用方 | 主要资源 | 权限要求 |
| :--- | :--- | :--- | :--- |
| `/api/app/**` | 用户端 APP | 首页、搜索、商家详情、购物车、订单、支付模拟、配送进度、评价、会员、AI 辅助 | 游客可访问公开浏览接口；订单、评价、会员等接口必须用户登录 |
| `/api/merchant/**` | 商家 Web 端 | 入驻、门店、商品服务、订单处理、退款审核、评价回复、客服会话、经营统计 | 商家账号登录；数据范围限定为所属商家和门店 |
| `/api/admin/**` | 平台管理后台 | 商家审核、评价审核、投诉处理、类目标签、推荐位、平台配置、数据看板、审计日志 | 管理员登录；按角色和权限点控制 |
| `/api/common/**` | 三端共用 | 文件上传、字典、城市、验证码、公共配置 | 按接口敏感程度决定是否登录 |
| `/api/ai/**` | 三端经后端调用 | 智能搜索、推荐解释、文案生成、客服回复建议 | 必须记录调用方、技能名称、耗时、状态和降级标记 |

### 3.5 错误码与幂等策略

| 错误码段 | 含义 | 示例场景 |
| :--- | :--- | :--- |
| `0` | 成功 | 请求处理成功 |
| `4xxx` | 请求参数错误 | 参数缺失、格式错误、分页参数非法 |
| `401x` | 认证错误 | Token 缺失、登录失效、验证码错误 |
| `403x` | 权限错误 | 商家访问非所属门店、普通用户访问后台接口 |
| `404x` | 资源不存在 | 商家、商品、订单或评价不存在 |
| `409x` | 状态冲突 | 重复支付、订单状态不允许接单、重复核销 |
| `5xxx` | 服务内部错误 | 数据库异常、第三方服务异常、未知系统错误 |

创建订单、支付确认、商家接单、券码核销、评价发布、审核处理、配送状态推进等接口必须具备幂等控制。幂等依据优先使用业务唯一号，如预提交订单号、支付流水号、券码、审核任务号或配送任务节点号。

## 4 系统数据结构设计

### 4.1 逻辑结构设计要点

系统围绕以下核心业务对象组织，其逻辑关系如下：

| 数据结构 | 标识符 | 核心数据项 | 关联关系 |
| :--- | :--- | :--- | :--- |
| 用户（User） | userID | 手机号、昵称、密码摘要、头像、会员等级、烟火值 | 一对多：地址、订单、评价；一对一：会员账户 |
| 商家（Merchant） | merchantID | 主体名称、资质信息、审核状态 | 一对多：门店 |
| 门店（Shop） | shopID | 名称、地址、坐标、营业时间、评分、分类标签 | 多对一：商家；一对多：商品、订单 |
| 商品/服务（Product） | productID | 名称、分类、价格、库存状态、规格、上下架状态 | 多对一：门店 |
| 订单（Order） | orderID | 订单编号、用户ID、门店ID、类型、状态、金额、地址快照 | 多对一：用户、门店；一对一：支付记录、配送任务（仅外卖）、评价 |
| 支付记录（Payment） | paymentID | 支付单号、关联订单号、支付渠道标识、状态、时间 | 一对一：订单 |
| 配送任务（Delivery） | deliveryID | 配送任务编号、关联订单号、当前状态、预计送达时间 | 一对一：外卖订单 |
| 评价（Review） | reviewID | 评价编号、关联订单号、用户ID、评分、内容、审核状态 | 一对一：订单；多对一：用户、商家 |
| 优惠券（Coupon） | couponID | 优惠券模板ID、用户ID、使用状态、有效期 | 多对一：用户 |
| 客服会话（Conversation） | conversationID | 参与方、关联订单、最新消息、处理状态 | 多对一：用户、商家；可关联订单 |
| 消息通知（Message） | messageID | 接收方、消息类型、标题、内容、已读状态 | 多对一：用户、商家或管理员 |
| 审核记录（AuditRecord） | auditID | 审核对象、审核人、审核结论、审核意见、前后状态 | 关联商家、评价、投诉或配置对象 |
| 烟火值记录（CreditRecord） | creditRecordID | 用户ID、变动值、来源、关联业务、变动时间 | 多对一：用户和会员账户 |
| AI调用记录（AILog） | logID | 调用方、请求摘要、结果摘要、耗时、状态、降级标记 | 用于统计、排障和治理 |

**核心实体关系描述：**
- 一个用户可以有多个地址、多个订单、多条评价、多张优惠券。
- 一个订单必须关联一个用户和一个门店，外卖订单额外关联一条配送任务。
- 评价必须与一个已完成订单强关联，一个订单只能对应一条评价。
- 商家通过门店提供商品和服务，订单明细中存储商品快照。
- 客服会话可由商家详情或订单详情发起，消息记录应保留发送方、接收方、已读状态和关联订单。
- 审核记录承接商家入驻、评价治理、投诉处理和平台配置发布等关键治理动作。
- 烟火值记录用于支撑会员等级展示和权益发放，退款、异常评价和违规行为不计入或可触发扣减。

### 4.2 内部数据域设计

系统内部数据按业务域划分，主要包括用户、商家、商品与服务、购物车、订单、支付模拟、配送模拟、评价、客服与消息、会员与营销、审核运营、系统权限和智能辅助调用记录等数据域。其中订单数据是交易链路的核心，支付、配送、评价、退款和烟火值变动都围绕订单建立关联；审核、配置、权限和智能辅助调用需要保留操作日志，便于后续排查和验收。

### 4.3 数据结构与程序关系
- 用户数据结构：通过 userID 关联订单、评价、会员等模块，用于身份验证、个人信息查询和权益计算。
- 订单数据结构：作为系统核心流转对象，被支付模拟服务、配送模拟服务、评价服务等多个模块访问和更新。
- 评价数据结构：通过 orderID 与订单强关联，评价发布时校验订单完成状态，评价审核流程依赖此关联关系。
- 配送数据结构：仅在外卖订单触发时创建，由配送模拟服务维护状态推进，用户端通过 orderID 查询展示。
- 客服消息数据结构：通过 conversationID 组织消息流，可关联订单或商家详情入口，商家 AI 回复建议只作为人工确认前的辅助内容。
- 审核数据结构：被商家审核、评价审核、投诉处理和平台配置发布共用，用于保证平台治理过程可追踪。
- AI 调用数据结构：由 AI Skills 网关统一写入，记录是否真实调用、是否降级、异常原因和响应时间。


## 5 系统数据库设计

### 5.1 数据库选择

系统采用关系型数据库管理系统 **MySQL 8.x** 作为核心业务库，统一使用 `utf8mb4` 字符集与 `utf8mb4_0900_ai_ci` 排序规则，理由如下：

1. 项目整体技术基线已确定为 Spring Boot + MySQL，开发、部署与运维链路成熟稳定。
2. MySQL 提供事务、行级锁、唯一约束和组合索引，能够支撑登录、下单、支付模拟、审核、配送状态流转等强一致场景。
3. 本项目当前以 P0 业务闭环为主，采用单库按业务域分表的方式即可满足容量与性能要求，无需过早引入分库分表和复杂中间件。
4. 结合组合索引与经纬度查询策略，可以满足附近商家、搜索结果排序、订单列表、评价列表和 AI 调用追踪等高频查询需求。

### 5.3 数据库关系设计

核心表之间的主要关系如下：

| 关系 | 类型 | 说明 |
| :--- | :--- | :--- |
| `iam_account` ↔ `user_profile` | 一对一 | 一个用户账号对应一份用户资料 |
| `iam_account` ↔ `merchant_profile` | 一对一 | 一个商家主账号对应一个商家主体 |
| `iam_account` ↔ `iam_account_role` ↔ `iam_role` | 多对多 | 一个账号可拥有多个角色，一个角色可分配给多个账号 |
| `iam_role` ↔ `iam_role_permission` ↔ `iam_permission` | 多对多 | 角色与权限点通过关系表绑定 |
| `user_profile` ↔ `user_address` | 一对多 | 一个用户可维护多个收货地址 |
| `merchant_profile` ↔ `merchant_store` | 一对多 | 一个商家主体可管理多个门店 |
| `merchant_store` ↔ `catalog_item` | 一对多 | 一个门店可上架多个商品或服务 |
| `catalog_item` ↔ `catalog_sku` | 一对多 | 一个商品或服务可对应多个规格 |
| `user_profile` ↔ `cart` ↔ `cart_item` | 一对多 | 用户可在多个门店形成购物车分组，每个购物车包含多个明细 |
| `user_profile` ↔ `order_main` | 一对多 | 一个用户可产生多个订单 |
| `order_main` ↔ `order_item` | 一对多 | 一个订单包含多个成交明细 |
| `order_main` ↔ `order_payment_record` | 一对多 | 一个订单可产生多次支付尝试或回调记录 |
| `order_main` ↔ `delivery_task` | 一对零或一 | 仅外卖等需要履约配送的订单会生成配送任务 |
| `delivery_task` ↔ `delivery_track_node` | 一对多 | 一个配送任务包含多个时间线节点 |
| `order_main` ↔ `order_voucher` / `order_booking_record` | 一对零到多 | 团购、票券、预约类订单关联对应扩展信息 |
| `order_main` ↔ `review_record` | 一对一 | 一个订单仅对应一条订单级评价记录 |
| `review_record` ↔ `review_media` / `review_reply` / `review_report` | 一对多或一对一 | 评价可挂载图片、回复和举报处理信息 |
| `support_session` ↔ `support_message` | 一对多 | 一个咨询会话包含多条消息 |
| `ai_skill_config` ↔ `ai_invoke_log` | 一对多 | 一个技能配置对应多次调用日志 |

**关系模型说明：**
- 账号体系采用统一账号模型，用户、商家、管理员统一归口到 `iam_account`，业务资料按角色拆分到各自扩展表。
- 交易模型采用 `order_main` + `order_item` + 扩展表/日志表的组合方式，不再单独拆金额主表，订单金额直接沉淀在 `order_main` 中，便于 P0 阶段实现。
- 订单明细、联系人、地址、预约资源、券码等关键展示信息采用快照存储，避免源商品或门店资料变更影响历史订单。
- 评价采用订单级评价模型，一个订单仅允许生成一条评价记录，评价入口挂载在订单内部。
- 配送模块按既定方案保持轻量，不单独建设骑手实体和复杂轨迹规划，只保留任务与节点最小闭环。
- AI 相关数据拆分为配置表和调用日志表，便于做技能治理、调用统计和问题追踪。

### 5.5 数据库安全性考虑

1. **访问权限控制：** 运行时数据库账号遵循最小权限原则，仅授予对应库的增删改查权限，不授予 `DROP`、`TRUNCATE` 等高危 DDL 权限；只读分析任务应使用独立只读账号。

2. **敏感数据保护：**
   - 账号密码统一采用 **BCrypt** 等不可逆摘要算法存储，数据库中不保存明文密码。
   - 手机号、邮箱、联系人信息在非必要展示场景下统一脱敏；如后续接入更高安全要求，可对高敏字段增加列级加密。

3. **验证码与认证安全：**
   - 验证码记录应设置短时有效期、使用状态和发送场景限制，当前阶段主要服务邮箱验证码流程。
   - 应用日志和审计日志不得输出完整验证码、密码摘要和敏感令牌。

4. **数据备份与恢复：** 数据库至少每日自动备份一次，保留最近 7 天以上备份副本，并定期验证备份文件的可恢复性；上线前应明确恢复脚本与回滚流程。

5. **逻辑删除与审计追踪：** 用户、商家、商品、订单、评价等核心业务表统一采用 `is_deleted` 软删除；支付记录、登录日志、审计日志、AI 调用日志等流水表原则上不物理删除，关键操作统一写入 `sys_audit_log`。

6. **SQL 注入与越权防护：** 应用层统一使用参数化查询或 ORM 框架，不拼接原始 SQL；动态排序、动态筛选字段必须采用白名单控制，避免注入和越权读取。


## 6 运行设计

### 6.1 运行模块组合
系统运行时的模块协同组合如下：

1. **前台消费组合：** 用户端 ←→ 后端网关 ←→（搜索服务、商品服务、订单服务、支付模拟服务）←→ MySQL
2. **商家经营组合：** 商家Web端 ←→ 后端网关 ←→（商家服务、订单服务、评价服务）←→ MySQL
3. **平台治理组合：** 平台管理后台 ←→ 后端网关 ←→（审核服务、配置服务、统计服务、权限服务）←→ MySQL
4. **外卖履约组合：** 订单服务触发 → 配送模拟服务 → 定时回调 → 订单服务更新状态 → 用户端展示
5. **AI辅助组合：** 用户端/商家端 ←→ 后端API ←→ AI Skills层 ←→（外部AI或Mock降级模块）

### 6.2 运行控制
1. **用户操作流程控制：** 订单状态严格遵循状态机。例如外卖订单主路径：待支付 → 已支付 → 商家已接单 → 制作中 → 待配送 → 配送中 → 已送达 → 已完成。任何不符合状态机的跳转请求将被拒绝。
2. **并发控制：** 下单扣库存、优惠券核销等场景使用乐观锁或数据库行级锁，防止超卖和重复核销。
3. **幂等控制：** 创建订单使用客户端生成的预提交订单号防重；支付回调使用支付流水号防重。
4. **异常处理：**
   - 当AI服务超时或不可用时，自动降级为规则引擎输出或Mock数据，并记录异常日志。
   - 当支付模拟或配送模拟服务出现内部错误时，订单保持在当前有效状态，记录错误，支持重试或人工修正。
   - 当数据库操作失败时，返回明确错误码，事务回滚保证一致性。

### 6.3 运行时间
- 交互响应时间：常用查询类接口在常规负载下 ≤ 1s；订单提交、支付确认 ≤ 3s。
- 数据处理时间：配送状态推进由定时任务（如每30秒扫描一次）触发，或由管理后台手动触发。
- AI处理时间：单次AI辅助请求响应宜 ≤ 8s；降级后 ≤ 3s。
- 首页首屏加载：在正常网络条件下 ≤ 3s 完成主要内容展示。

### 6.4 部署拓扑

系统支持本地演示环境和云端演示环境两种运行方式。本期验收环境建议不低于 2 vCPU、4 GB RAM、50 GB 可用存储，操作系统采用 Ubuntu，管理端静态资源由 Nginx 托管，后端服务以 Spring Boot 进程运行。

```text
用户端 APP / 商家 Web / 平台后台 Web
        │
        ▼
   HTTPS / HTTP
        │
        ▼
      Nginx
   ├─ 静态资源：商家端、后台端
   └─ /api/* 反向代理
        │
        ▼
 Spring Boot 后端服务
   ├─ 用户、商家、商品、订单、支付模拟
   ├─ 配送模拟、评价、客服、会员、平台治理
   └─ AI Skills 网关
        │
        ├─ MySQL 8.0
        ├─ 本地文件存储 / OSS 对象存储
        ├─ 邮箱或短信验证码模拟服务
        └─ 外部 AI 服务 / 规则与 Mock 降级模块
```

### 6.5 阶段落地顺序

概要设计按开发计划书的迭代顺序支撑实现：

1. 项目骨架、数据库初始化、统一响应、统一异常、登录鉴权。
2. 首页、分类、搜索、商家详情和商品服务展示。
3. 购物车、订单提交、金额计算、模拟支付。
4. 商家端门店维护、商品管理、订单处理。
5. 平台后台商家审核、平台基础配置、审计日志。
6. 外卖配送模拟、订单时间线和配送状态展示。
7. 评价互动、商家客服、消息通知、烟火会员、优惠券。
8. AI 辅助搜索、智能生活规划 Agent、商家 AI 运营助手。

## 7 核心状态流转设计

### 7.1 订单状态流转

| 订单类型 | 正常主流程 | 常见异常流转 | 设计说明 |
| :--- | :--- | :--- | :--- |
| 外卖订单 | 待支付 → 待商家接单 → 制作中 → 待配送 → 配送中 → 已送达 → 已完成 | 待支付 → 已取消；待商家接单/制作中/配送中 → 退款中 → 已退款 | 仅外卖订单进入配送模拟链路 |
| 到店团购或券码订单 | 待支付 → 待核销 → 已核销 → 已完成 | 待支付 → 已取消；待核销 → 退款中 → 已退款 | 券码核销是核心履约节点 |
| 预约类订单 | 待支付 → 待商家确认 → 已预约 → 待到店/待服务 → 已完成 | 待支付 → 已取消；商家拒绝或用户规则内取消 → 退款中 → 已退款 | 预约时段和资源占用是关键约束 |

“可评价”不是订单状态，而是订单进入“已完成”后的用户操作权限。评价记录由评价模块独立维护，避免把操作权限混入订单状态机。

### 7.2 支付模拟状态流转

```text
待支付 → 支付中 → 支付成功
待支付 → 支付中 → 支付失败
待支付 → 超时关闭
支付成功 → 退款中 → 已退款
```

支付模拟不接入真实资金渠道，不采集银行卡号、支付账户或支付密码。支付确认接口以支付流水号和订单号进行幂等控制，重复确认不得生成重复支付记录。

### 7.3 配送模拟状态流转

| 模拟状态 | 触发条件 | 驱动主体 | 用户端展示 |
| :--- | :--- | :--- | :--- |
| 待调度 | 商家接单且订单满足配送条件 | 订单服务、配送模拟服务 | 商家已接单，准备配送 |
| 已分配模拟运力 | 后端规则完成分单 | 配送模拟服务 | 已分配虚拟配送对象 |
| 待取餐 | 达到预计出餐时间或商家标记可取餐 | 配送模拟服务、商家端、平台后台 | 等待取餐 |
| 配送中 | 取餐完成并开始模拟推进 | 配送模拟服务 | 展示预计送达和模拟位置 |
| 已送达 | 达到模拟送达条件或后台人工闭环 | 配送模拟服务、平台后台 | 已送达，待确认完成 |
| 已完成 | 用户确认或系统超时自动完成 | 订单服务 | 可发起评价 |
| 已取消 | 订单取消或退款导致无需继续配送 | 用户、商家、平台或规则任务 | 配送终止 |

配送任务仅适用于外卖订单。订单进入取消、退款或关闭链路时，配送任务必须同步关闭或标记终止，避免用户端继续显示配送中。

### 7.4 审核与评价状态流转

| 对象 | 主流程 | 异常或治理流程 |
| :--- | :--- | :--- |
| 商家入驻 | 待提交 → 待审核 → 审核通过 → 可经营 | 待审核 → 驳回补充；可经营 → 违规停用 |
| 评价内容 | 待审核 → 审核通过 → 前台展示 | 待审核 → 屏蔽；已展示 → 举报 → 复核 → 屏蔽/恢复 |
| 投诉工单 | 已提交 → 处理中 → 已结案 | 已提交/处理中 → 转派/升级/补充材料 |

审核、屏蔽、恢复、封禁、配置发布等治理动作必须写入操作日志，记录操作人、操作时间、操作对象、前后状态和处理意见。

## 8 权限、安全与审计设计

### 8.1 角色权限矩阵

| 角色 | 访问端 | 主要权限 | 数据边界 |
| :--- | :--- | :--- | :--- |
| 游客 | 用户端 | 首页、分类、搜索、商家详情等公开浏览 | 仅公开数据，不可查看订单和个人信息 |
| 普通用户 | 用户端 | 地址、购物车、下单、支付模拟、订单、评价、客服、会员 | 仅本人账户、订单、评价、优惠券和消息 |
| 商家管理员 | 商家端 | 入驻、资质、门店、商品服务、订单、退款、评价回复、客服、经营统计 | 仅所属商家及其门店数据 |
| 商家店员 | 商家端 | 订单处理、核销、客服回复、部分商品维护 | 仅授权门店和授权功能 |
| 平台管理员 | 平台后台 | 商家审核、评价治理、投诉处理、类目配置、推荐位、数据看板、审计 | 平台治理范围内全局数据 |
| 审核员 | 平台后台 | 商家审核、评价审核、投诉处理 | 仅审核任务和相关证据数据 |
| 数据分析员 | 平台后台 | 数据看板、统计报表 | 只读统计数据，敏感字段脱敏 |
| AI 辅助服务 | 后端内部 | 搜索解析、推荐解释、文案生成、客服建议 | 不直接执行交易确认和状态变更 |

### 8.2 安全设计

1. 登录成功后签发 JWT 或等价访问令牌，服务端校验令牌有效期、角色和权限点。
2. 用户密码采用 BCrypt 等不可逆算法存储；验证码具备有效期和频率限制。
3. 手机号、地址、证照等敏感信息在日志和列表展示中按权限脱敏。
4. 上传图片需校验文件类型、大小和访问权限，禁止上传可执行文件。
5. 接口统一做参数校验、权限校验和限流控制。
6. 模拟支付不得采集或存储真实银行卡号、支付密码和真实资金账户。
7. AI 请求不得上传真实证件、完整地址、验证码、Token 或其他敏感信息。

### 8.3 审计设计

以下操作必须记录审计日志：

| 操作类别 | 记录内容 |
| :--- | :--- |
| 登录与权限 | 登录主体、IP、时间、结果、失败原因、权限变更内容 |
| 订单状态流转 | 订单号、前状态、后状态、触发主体、触发来源 |
| 支付与退款模拟 | 支付单号、订单号、模拟结果、回调次数、失败原因 |
| 配送状态推进 | 配送节点、触发方式、预计送达、模拟位置摘要 |
| 审核治理 | 审核对象、审核人、审核结论、审核意见、前后状态 |
| 配置变更 | 配置键、变更前值、变更后值、操作人、生效范围 |
| AI 调用 | 技能名称、调用方、输入摘要、输出摘要、耗时、状态、降级标记 |

## 9 AI Agent 与 Skills 概要设计

### 9.1 能力边界

AI Agent 与 Skills 层属于增强层，不直接修改订单、支付、配送、退款、审核等核心交易和治理状态。所有 AI 输出均为辅助建议，涉及商品发布、客服回复、活动文案、推荐理由时需由用户、商家或平台人员确认后进入业务流程。

### 9.2 Skills 清单

| Skill | 使用端 | 输入 | 输出 | 降级策略 |
| :--- | :--- | :--- | :--- | :--- |
| 智能生活规划 Agent | 用户端 | 人数、预算、位置、口味、时间、场景、优惠偏好 | 推荐商家、套餐、优惠券、推荐理由和跳转入口 | 规则解析 + Mock 推荐 |
| 智能搜索解析 | 用户端 | 自然语言搜索词和上下文 | 结构化筛选条件 | 关键词匹配 |
| 推荐解释 | 用户端 | 推荐对象、用户上下文、排序原因 | 可读推荐理由 | 模板解释 |
| 商品描述生成 | 商家端 | 商品名称、价格、卖点、标签 | 可编辑商品描述 | 模板文案 |
| 活动文案生成 | 商家端 | 活动主题、优惠规则、目标客群 | 可编辑活动文案 | 预设模板 |
| 客服回复建议 | 商家端 | 用户咨询内容、订单上下文 | 候选回复建议 | 快捷回复模板 |
| 运营辅助分析 | 平台后台 | 指标、时间范围、异常点 | 趋势摘要和运营建议 | 固定规则说明 |

### 9.3 调用治理

AI Skills 网关统一处理鉴权、限流、超时、降级、内容安全和日志。每次调用至少记录：调用方、角色、技能名称、版本、输入摘要、输出摘要、耗时、状态、是否降级、异常原因和 requestId。外部 AI 服务不可用、超时、返回异常或命中敏感内容时，系统自动降级为规则引擎、模板回复或 Mock 数据，并保证 P0 主流程继续可用。

## 11 未决问题与风险应对

| 未决问题 | 当前概要设计选择 | 降级或后续处理 |
