# 爱团后续功能待办

## 1. 文档目标

本文档专门记录当前阶段明确暂缓、后续再做但不能遗忘的功能和技术事项。这里不是某个单独 Stage 的交付文档，而是长期待办清单；后续进入对应阶段时，应先阅读本文档，再决定是否迁移到新的 Stage 计划中。

## 2. 后端业务功能后置项

### 2.1 真实支付接入

- 首包只开放 `mock` 支付。
- 数据库和接口保留 `wechat`、`alipay` 等支付方式字段。
- 后续可接入易支付等第三方支付程序接口。
- 接入时需要补充支付回调、签名校验、幂等处理、支付异常补偿。

### 2.2 复杂库存和资源锁

- 首包只做简单库存字段、下单校验、支付成功扣减。
- Stage5 分工 C 外卖链路只做基础扣减、售罄展示和后续扩展预留。
- 后续再做复杂并发库存锁、库存冻结、未支付取消回补、超时释放、库存流水。

### 2.3 酒店/电影/门票/预约复杂资源

首包除外卖外都先按类似团购的券码核销逻辑处理。以下能力后续再做：

- 酒店房态、入住日期、房型库存、取消规则。
- 电影演出场次、座位、票档、入场规则。
- 景点门票日期票、成人/儿童票、分时预约。
- 洗脚、丽人医美、休闲娱乐等预约时间段、技师/资源排班。
- 统一可扩展表建议继续沿用 `catalog_service_schedule`，复杂后再拆领域表。

### 2.4 商家端完整前端

- 首包后端实现或预留核销接口，商家端前端先不做。
- 后续补商家 Web：登录、门店资料、商品服务维护、订单处理、券码核销、评价回复、经营看板。

### 2.5 后台完整前端

- 首包后端预留后台治理接口。
- 后续补后台 Web：商家审核、评价审核、类目配置、Banner/推荐位、投诉工单、系统日志、角色权限。

### 2.6 AI 与问小爱

- 搜索结果顶部保留“问小爱”入口。
- 首包 AI 可先返回降级占位。
- 后续再做智能推荐、搜索解释、商家文案生成、客服回复建议、AI 调用日志和治理。

### 2.7 商家入驻认证与业务分型深化

- 后续需要补完整商家注册/入驻申请流程，包括提交资料、后台审核、驳回补充、通过后绑定商家账号。
- 后续需要补商家资质认证材料管理，包括营业执照、门店照片、行业许可证等文件上传、审核状态和审核记录。
- 商家账号与商家主体应保持一账号一商家的清晰归属；如未来支持集团商家多门店，应单独设计商家主体、门店和员工账号权限。
- 非外卖七类商家的管理不能复用外卖配送流程；券码核销、预约确认、房型/场次/票种/服务时段等由后续对应成员深化。
- 外卖商家不应显示券码核销，非外卖商家不应显示备餐、出餐、配送推进；当前阶段若只做预留，也必须保留按 `businessType` 扩展的代码结构。

## 3. 部署与工程后置项

### 3.1 Docker Compose 实机验证

- 当前本机没有 Docker Compose 环境，本地测试不依赖 Docker Compose。
- 项目仍应提供 Docker Compose 部署文件。
- 后续在有 Docker Compose 的机器上验证 MySQL volume、后端镜像、环境变量和数据迁移。

### 3.2 数据库迁移长期规则

- 已执行迁移脚本不回改。
- 结构更新新增 Flyway 迁移文件。
- 种子数据使用幂等语句，不覆盖用户真实数据。
- 禁止用无条件 `DROP`、`TRUNCATE`、全表 `DELETE` 作为升级手段。

### 3.3 前端后端地址切换

- Flutter 后续应支持 `--dart-define=API_BASE_URL=...`。
- Android 模拟器访问本机后端使用 `http://10.0.2.2:8080`。
- 真机访问本机后端使用电脑局域网 IP。
- 不应为了换后端地址反复改源码。

## 4. 环境约束长期规则

- 当前 C 盘空间特别少，构建、缓存、运行和打包尽量放到 D 盘英文路径。
- 不要把临时构建目录直接堆在 D 盘根目录，应放在 `D:/aituan_build/`、`D:/aituan_cache/`、`D:/aituan_runtime/`、`D:/aituan_release/` 等子目录。
- 修改系统环境变量、全局 Gradle 配置、系统路径前必须先确认。

## 5. 使用方式

后续每次进入新阶段前：

1. 先阅读本文档。
2. 把当前阶段需要实现的条目迁移到对应 Stage 计划。
3. 实现完成后，在本文档中标记或移除对应待办。
4. 不要只依赖对话上下文记忆后续事项。
