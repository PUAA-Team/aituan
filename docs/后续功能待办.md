# 爱团后续功能待办

## 1. 文档目标

本文档专门记录当前阶段明确暂缓、后续再做但不能遗忘的功能和技术事项。这里不是某个单独 Stage 的交付文档，而是长期待办清单；后续进入对应阶段时，应先阅读本文档，再决定是否迁移到新的 Stage 计划中。

## 2. 后端业务功能后置项

### 2.1 真实支付接入

- 首包只开放 `mock` 支付。
- 数据库和接口保留 `wechat`、`alipay` 等支付方式字段。
- 后续可接入易支付等第三方支付程序接口。
- 接入时需要补充支付回调、签名校验、幂等处理、支付异常补偿。

### 2.2 复杂库存和资源锁

- 首包只做简单库存字段、下单校验、支付成功扣减。
- Stage5 分工 C 外卖链路只做基础扣减、售罄展示和后续扩展预留。
- 后续再做复杂并发库存锁、库存冻结、未支付取消回补、超时释放、库存流水。

### 2.3 酒店/电影/门票/预约复杂资源

首包除外卖外都先按类似团购的券码核销逻辑处理。以下能力后续再做：

- 酒店房态、入住日期、房型库存、取消规则。
- 电影演出场次、座位、票档、入场规则。
- 景点门票日期票、成人/儿童票、分时预约。
- 洗脚、丽人医美、休闲娱乐等预约时间段、技师/资源排班。
- 统一可扩展表建议继续沿用 `catalog_service_schedule`，复杂后再拆领域表。

### 2.4 商家端完整前端

- 首包后端实现或预留核销接口，商家端前端先不做。
- 后续补商家 Web：登录、门店资料、商品服务维护、订单处理、券码核销、评价回复、经营看板。

### 2.5 后台完整前端

- 首包后端预留后台治理接口。
- 后续补后台 Web：商家审核、评价审核、类目配置、Banner/推荐位、投诉工单、系统日志、角色权限。

### 2.6 AI 与问小爱

- 搜索结果顶部保留“问小爱”入口。
- 首包 AI 可先返回降级占位。
- 后续再做智能推荐、搜索解释、商家文案生成、客服回复建议、AI 调用日志和治理。

### 2.7 商家入驻认证与业务分型深化

- 后续需要补完整商家注册/入驻申请流程，包括提交资料、后台审核、驳回补充、通过后绑定商家账号。
- 后续需要补商家资质认证材料管理，包括营业执照、门店照片、行业许可证等文件上传、审核状态和审核记录。
- 商家账号与商家主体应保持一账号一商家的清晰归属；如未来支持集团商家多门店，应单独设计商家主体、门店和员工账号权限。
- 非外卖七类商家的管理不能复用外卖配送流程；券码核销、预约确认、房型/场次/票种/服务时段等由后续对应成员深化。
- 外卖商家不应显示券码核销，非外卖商家不应显示备餐、出餐、配送推进；当前阶段若只做预留，也必须保留按 `businessType` 扩展的代码结构。

## 3. 部署与工程后置项

### 3.1 Docker Compose 实机验证

- 当前本机没有 Docker Compose 环境，本地测试不依赖 Docker Compose。
- 项目仍应提供 Docker Compose 部署文件。
- 后续在有 Docker Compose 的机器上验证 MySQL volume、后端镜像、环境变量和数据迁移。

### 3.2 数据库迁移长期规则

- 已执行迁移脚本不回改；如课程演示环境明确允许丢弃数据，也要在部署前统一确认并记录。
- 结构更新新增 Flyway 迁移文件。
- 所有 Flyway 迁移脚本必须同时兼容 MySQL 8 与 H2（`MODE=MySQL`）空库迁移；禁止只在服务器 MySQL 或只在本地 H2 通过。
- 迁移 SQL 避免 `AFTER`、触发器、存储过程、JSON 专有函数等未经双端验证的单方言写法；提交前至少跑后端 `test` profile 构建验证。
- 种子数据使用幂等语句，不覆盖用户真实数据。
- 禁止用无条件 `DROP`、`TRUNCATE`、全表 `DELETE` 作为升级手段。

### 3.3 前端后端地址切换

- Flutter 后续应支持 `--dart-define=API_BASE_URL=...`。
- Android 模拟器访问本机后端使用 `http://10.0.2.2:8080`。
- 真机访问本机后端使用电脑局域网 IP。
- 不应为了换后端地址反复改源码。

### 3.4 爱团介绍与下载页

- 后续新增纯 HTML/CSS/JS 静态前端目录，例如 `apps/landing_web`，用于展示爱团产品介绍与 App 下载入口。
- 页面需要自适应桌面、平板和手机，视觉延续爱团红色主色、控制台/APP 统一的简洁风格，不使用蓝紫渐变和大圆角。
- 内容包含爱团核心能力、App 下载、商家端入口、后台端入口、公司地址“北京航空航天大学学院路37号”和联系邮箱 `gay@wcnmb.eu.org`。
- 部署时可将服务器根路径 `/` 改为介绍下载页，保留 `/merchant/`、`/admin/` 和 `/downloads/aituan-user-server-debug.apk`。

### 2.8 Stage5 修复计划 1 后置项

- 商家入驻审核通过后的账号设置流程需要重做，不能长期依赖申请号 + 固定默认密码 `123456`；后续应改为商家主动设置密码、一次性初始化链接或后台安全重置流程。
- 首页推荐算法后续继续完善；当前先做分页加载、前端循环去重和同商家间隔，后续可补个性化、距离、销量、类目多样性、曝光去重和服务端推荐策略。
- 开发环境返回邮箱验证码只是临时便利；后续应移除或严格限制，生产/服务器环境不得向前端返回验证码明文。
- 手机号/邮箱资料修改暂不做；后续如实现，需要验证码二次验证、唯一性校验和登录态安全处理。

## 4. APP 体验与调试后置项

### 4.1 首页首次打开加载慢

- 用户反馈：服务器版 APK 每次第一次打开首页都会加载特别长。
- 后续需要专项排查首页首屏耗时来源，至少区分以下阶段：系统定位权限/定位服务等待、反向地理编码、首页接口请求、图片资源加载、后端服务冷启动或数据库查询。
- 当前定位服务存在超时等待逻辑，若真机定位不可用，可能先等待系统定位失败后才回退默认位置；后续可考虑开发版增加阶段耗时日志或首屏调试面板。

### 4.2 开发版定位错误提示不明显

- 用户反馈：已安装开发服务器 APK 后，首页没有看到定位失败报错提示。
- 当前实现只在首页首次加载时用底部 SnackBar 短暂提示，可能被首屏加载、页面切换或显示时机遮挡。
- 后续建议把 `LOCATION_DEBUG_ERRORS=true` 下的定位错误改为更明显的开发提示，例如首页固定调试条、弹窗或位置区域下方常驻文案；正式版不传该开关时继续保持静默 fallback。

## 5. 环境约束长期规则

- 当前 C 盘空间特别少，构建、缓存、运行和打包尽量放到 D 盘英文路径。
- 不要把临时构建目录直接堆在 D 盘根目录，应放在 `D:/aituan_build/`、`D:/aituan_cache/`、`D:/aituan_runtime/`、`D:/aituan_release/` 等子目录。
- 修改系统环境变量、全局 Gradle 配置、系统路径前必须先确认。

2. 把当前阶段需要实现的条目迁移到对应 Stage 计划。
3. 实现完成后，在本文档中标记或移除对应待办。
4. 不要只依赖对话上下文记忆后续事项。
