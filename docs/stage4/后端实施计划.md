# 爱团后端实施计划（Stage 4）

## 1. 文档目标

本文档承接 `docs/stage1/代码架构设计.md`、`docs/stage1/数据库表设计.md`、`docs/stage1/API 分组设计.md` 与 Stage3 Flutter 用户端首包，实现后端进入编码前的完整规划。

本阶段目标不是只搭一个空接口，而是建设可支撑当前用户端 APP 首包的真实后端基础：认证、首页、模块、搜索、商家、商品、确认订单、模拟支付、订单、券码、配送模拟、收藏、消息、评价等主链路都要有明确数据模型和接口边界。商家端、后台端首包暂不完整实现 UI，但后端需预留经营端和治理端接口分组，避免后续推翻。

## 2. 已确认口径

1. 后端采用 `Spring Boot + MySQL`，保持 Stage1 确定的模块化单体方案，不拆微服务。
2. 后端放在 `services/backend/`，数据库脚本放在 `database/`，脚本放在 `scripts/`。
3. Java 包名统一使用 `com.aituan`，不再使用高校或 `buaa` 相关命名。
4. 当前首包用户端已在 `apps/user_app/` 完成静态 Flutter 实现，后端接口需要优先对齐该 APP 的 Mock 数据形态。
5. Mock 只是临时数据源，后端要提供可替换 Mock 的真实 REST API；前端后续通过 `AppApiClient` / Repository 接口切换。
6. 用户端登录支持手机号或邮箱 + 密码；手机号必须 11 位数字，当前不接短信验证码；邮箱验证码用于注册和找回密码。
7. 首页八个业务模块固定为：外卖、团购、酒店、休闲娱乐、电影演出、丽人医美、景点门票、洗脚。
8. 外卖与其他七类业务逻辑分开：外卖商品和外卖商家都进入外卖点单页；非外卖商家进入商家页，非外卖商品进入商品详情页。
9. 非外卖七个模块首包统一走类似团购的券码核销逻辑：支付后进入“未使用”，生成券码/二维码载荷，商家核销后进入“已使用”。
10. 商家端前端首包先不做，但后端首包实现券码核销接口，并预留二维码生成/扫码核销接入能力。
11. 一个商家门店只绑定一个主业务类型，门店内商品/服务必须与门店业务类型一致。
12. 商家详情页商品列表要返回分类字段，前端右侧全量分组展示，左侧分类点击滚动到分类首项。
13. 当前支付首包只开放 `mock` 支付；`wechat` / `alipay` 字段和支付记录结构保留，后续可接入易支付等第三方支付接口。
14. 商品库存首包做简单真实扣减：保留库存字段，下单时校验库存，支付成功后扣减；复杂库存锁和高并发库存后续再做。
15. 酒店、电影、门票、预约等复杂房态、座位、场次、排期资源后续再做；首包除外卖外都先按团购式券码核销链路处理。
16. 外卖订单支付后进入“待完成”，配送模拟用定时任务每 2-5 分钟检查并自动推进一次状态，同时保留后台、商家手动推进接口。
17. Docker Compose 作为部署方式提供，但本机没有 Docker Compose 环境，本地开发和测试必须在 D 盘英文路径手动构建运行。
18. 数据库更新只允许使用 Flyway 增量迁移，不覆盖已有数据；种子数据必须幂等，不允许清空真实数据后重灌。
19. 评价采用“一个订单一条评价”模式，已使用订单才可评价。
20. 文件大小不机械死守 200 行；复杂 Controller、Service、SQL、DTO 仍按职责拆分，稳定配置类或迁移脚本可以适当放宽。

## 3. 技术栈规划

| 类别 | 方案 | 说明 |
| --- | --- | --- |
| 后端框架 | Spring Boot 3.x | 课程项目部署简单，生态成熟 |
| Java 版本 | Java 17 | 与 Spring Boot 3 匹配 |
| 构建工具 | Gradle Kotlin DSL | 与 Flutter/Android 现有生态不冲突 |
| 数据库 | MySQL 8.x | 使用 `utf8mb4`，金额用 `decimal(10,2)` |
| 数据迁移 | Flyway | 迁移脚本可版本化提交 |
| 持久层 | MyBatis / MyBatis-Plus | 便于显式 SQL、分页和课程展示；文档中统一称 Repository/Mapper |
| 鉴权 | Spring Security + JWT | 三端共用账号体系，按角色控制接口 |
| 接口文档 | springdoc-openapi | 生成 Swagger / OpenAPI，方便 Flutter 联调 |
| 参数校验 | Jakarta Validation | Controller 入参边界统一校验 |
| 测试 | JUnit 5 + Spring Boot Test | 重点测认证、搜索、下单、支付、订单状态 |
| 开发环境 | dev / test / demo profile | demo 使用种子数据，便于演示 |

> 若开发时希望更轻量，可先不引入 Redis、消息队列、对象存储。验证码、配送推进、消息通知都可先用数据库和定时任务完成。

### 4.1 拆分原则

1. `controller` 只做参数校验、鉴权读取和响应封装，不写业务规则。
2. 查询与命令分开：例如 `OrderQueryService`、`OrderCommandService`。
3. App 查询 DTO 与数据库 Entity 分离，避免后续字段变更影响接口。
4. 复杂状态流转放入 `state/`，不要散落在 Controller 或 Service 中。
5. `delivery/` 保持在 `order/` 内部，不单独部署。
6. `repository` 命名代表持久化端口，实际可用 MyBatis Mapper 实现。

## 7. 业务流程设计

## 7.1 登录注册流程

```text
注册：
用户输入手机号、邮箱、邮箱验证码、密码
-> 校验手机号 11 位数字、邮箱格式、验证码有效
-> 创建 iam_account + user_profile
-> 返回 token 和用户资料

登录：
用户输入手机号或邮箱 + 密码
-> 查 iam_account phone/email
-> 校验密码和状态
-> 写 sys_login_log
-> 返回 token

找回密码：
用户输入邮箱、邮箱验证码、新密码
-> 校验验证码
-> 更新 password_hash
-> 作废旧验证码
```

## 7.2 首页、模块、搜索流程

1. `home` 接口返回八模块、精选推荐、猜你喜欢首屏。
2. `recommendations` 使用分页，前端滚动到底部继续请求。
3. `modules/{moduleCode}` 根据模块映射到 `business_type`，只返回该业务类型门店和商品。
4. `stores/search` 同时查门店名、摘要、标签、商品名、商品标签，最终按门店聚合。
5. 搜索命中外卖时返回 `businessType=takeaway`，前端点击店铺或商品都进入外卖点单页。
6. 搜索命中非外卖商品时返回 `itemId`，前端点击商品进商品详情页。

## 7.3 商家详情流程

```text
GET /api/app/discovery/stores/{storeId}
-> 查询 merchant_store
-> 校验 store.business_type
-> 查询 catalog_category + catalog_item
-> 按 category 分组
-> 外卖追加 deliveryRule
-> 返回 StoreDetailDto
```

后端必须保证：`catalog_item.business_type == merchant_store.business_type`，避免一个商家里出现混品类商品。

## 7.4 下单与模拟支付流程

```text
POST /checkout/preview
-> 校验商品、数量、价格、门店类型
-> 外卖计算配送费；非外卖返回使用规则和券码说明
-> 返回金额明细

POST /orders
-> 使用 Idempotency-Key 防重复提交
-> 创建 order_main + order_item
-> payment_status=unpaid，display_status=unpaid

POST /orders/{orderId}/pay paymentMode=mock
-> 创建 order_payment_record
-> payment_status=paid
-> 外卖：display_status=pending，创建 delivery_task + track nodes
-> 非外卖：display_status=unused，创建 order_voucher
-> 写 order_state_log
-> 生成站内消息
```

## 7.5 配送模拟流程

1. 外卖支付成功后创建 `delivery_task`。
2. `DeliveryTickJob` 每隔一段时间推进状态：`accepted -> preparing -> delivering -> delivered`。
3. 推进到 `delivered` 后，订单 `display_status` 变为 `used`。
4. 前端订单详情读取时间线，不需要用户手动切换状态。

## 7.6 非外卖核销流程

首包用户端只展示券码和二维码载荷，商家端核销可后置；但数据状态先设计完整：

```text
非外卖支付成功
-> order_voucher.status=unused
-> display_status=unused
-> 商家端后续输入券码/扫码
-> order_voucher.status=used
-> order_main.display_status=used
-> 用户可评价
```

## 7.7 评价流程

1. 只有 `display_status=used` 的订单可评价。
2. 一个订单只允许一条 `review_record`。
3. 发布评价后 `order_item.is_reviewed` 或订单评价标识更新。
4. 商家回复、评价审核可后置，但表和接口预留。

## 10. 部署与数据迁移策略

### 10.1 本地开发与测试

1. 本机不使用 Docker Compose 做日常测试，因为当前本地没有 Docker Compose 环境。
2. 后端本地构建、测试、运行必须放在 D 盘英文路径，例如 `D:/aituan_build/backend/`、`D:/aituan_cache/gradle/`、`D:/aituan_runtime/backend/`，避免占用 C 盘。
3. 脚本要尽量支持把 Gradle 缓存、构建产物、临时日志放到 D 盘项目子目录，不要散落在 D 盘根目录。
4. 如需修改系统环境变量或全局 Gradle 配置，必须先展示修改内容并获得确认。

### 10.2 Docker Compose 部署

1. 后端仍提供 Docker Compose 部署方式，便于以后在有 Docker Compose 的机器上一键启动演示环境。
2. Compose 至少包含 `mysql` 和 `backend` 两个服务，后续可扩展 Redis、Nginx、管理工具。
3. MySQL 必须使用 named volume 保存数据，更新后端镜像或重启容器不得清空数据库。
4. Docker 初始化脚本只做首次建库，不做删除表、清空表或覆盖真实数据。

### 10.3 数据库迁移

1. 数据库结构更新统一使用 Flyway 增量脚本，例如 `V009__add_xxx.sql`。
2. 已经执行过的迁移脚本不回改；新增字段、索引、表都写新的迁移文件。
3. 禁止在迁移脚本里对真实业务表执行无条件 `DROP TABLE`、`TRUNCATE`、全表 `DELETE`。
4. 演示种子数据必须使用幂等写法，例如唯一编码 + `ON DUPLICATE KEY UPDATE`。
5. 种子数据和结构迁移分离，避免更新版本时覆盖用户已有数据。

### 11.3 前后端联调

1. Flutter `AppApiClient.baseUrl` 指向本地后端。
2. 先把 `MockAppRepository` 替换为远程 Repository 的单个模块验证，不一次性大改。
3. 推荐替换顺序：登录 -> 首页/搜索 -> 商家/商品 -> 订单 -> 消息/收藏/评价。
4. 每替换一个模块，保留 Mock fallback 或 demo profile 种子数据，避免演示数据断链。

## 13. 风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 前端字段和后端 DTO 不一致 | 本文档以 `ItemCardDto`、`StoreCardDto`、`OrderSummaryDto` 作为接口基线，编码时同步 Flutter 模型 |
| 商家商品混品类 | 数据库同时在 `merchant_store` 和 `catalog_item` 保存 `business_type`，Service 校验一致性 |
| 订单状态复杂 | 用 `display_status` 对齐 APP 展示，用内部 `payment_status/order_status/fulfillment_status` 承接真实状态 |
| 配送模拟过重 | 只做定时状态推进和文字时间线，不引入骑手、地图、路线规划 |
| 真实支付延期 | `payment_method` 与 `order_payment_record` 先按扩展字段设计，首包只开放 mock |
| 后台/商家端未做 UI | 后端分组和数据权限先留好，用户端首包不依赖后台 UI |
| C 盘空间不足 | 后端本地测试、构建、运行、缓存和日志必须优先放到 D 盘项目子目录，避免占用 C 盘 |
