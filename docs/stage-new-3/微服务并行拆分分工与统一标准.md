# 微服务并行拆分分工与统一标准

> 日期：2026-08-31  
> 适用范围：软件工程基础实践后五天，四人并行拆分后端微服务、拆数据库、补微服务流水线  
> 文档定位：本文件是四人并行开发时的统一入口文档。所有人先看本文，再看自己负责服务的详细清单。本文中的命名、端口、数据库、接口、测试、部署和协作约定优先于口头约定。

## 1. 一句话结论

四个人可以并行做微服务拆分，推荐按 **一人一个业务微服务** 分工：

| 成员角色 | 负责服务 | 工程名 | 数据库 | 主要职责 |
| --- | --- | --- | --- | --- |
| 成员 A | 账号与用户资产服务 | `identity-asset-service` | `aituan_identity` | 认证、用户、地址、收藏、会员、优惠券、站内消息 |
| 成员 B | 商家与商品服务 | `merchant-catalog-service` | `aituan_merchant` | 商家、门店、资质、商品、SKU、库存、搜索、履约规则 |
| 成员 C | 交易与履约服务 | `trade-fulfillment-service` | `aituan_trade` | 购物车、结算、订单、支付、退款、券码、预约、配送 |
| 成员 D | 互动与平台服务 | `engagement-platform-service` | `aituan_platform` | 评价、投诉、客服、AI、公告、配置、审计、看板 |

公共工作不单独设置第五个人，而是由四人按规则共同完成：

- Gateway：每个服务负责人提交自己服务的路由规则，最后由轮值集成人合并。
- 数据库：每个服务负责人拆自己服务的迁移脚本和 seed。
- Docker/K8s：每个服务负责人维护自己服务的 Dockerfile、Deployment、Service、健康检查。
- CI/CD：每个服务负责人保证自己的服务能被矩阵流水线构建、测试、制镜像和部署。
- E2E 回归：每个服务负责人认领自己主责用例，最终统一从 Gateway 跑全链路测试。

## 3. 统一命名标准

### 3.1 服务名

后续代码、文档、镜像、K8s、流水线统一使用以下英文工程名：

```text
api-gateway
identity-asset-service
merchant-catalog-service
trade-fulfillment-service
engagement-platform-service
```

中文名统一：

```text
API 网关
账号与用户资产服务
商家与商品服务
交易与履约服务
互动与平台服务
```

注意：旧材料中如果出现 `interaction-platform-service`，统一视为历史别名；后续代码和新增文档统一写 `engagement-platform-service`。

```text
com.aituan.gateway
com.aituan.identity
com.aituan.merchant
com.aituan.trade
com.aituan.platform
```

禁止每个人自己发明包名，例如 `com.xxx.usercenter`、`com.aituan.user`、`com.aituan.shop`。

## 4. 分支和协作约定

### 4.1 推荐分支

建议先建立微服务主开发分支：

```text
microservices-main
```

四个人从该分支切自己的服务分支：

```text
ms/identity-asset
ms/merchant-catalog
ms/trade-fulfillment
ms/engagement-platform
```

公共集成或 Gateway 可以从 `microservices-main` 临时开：

```text
ms/gateway-integration
ms/database-split
ms/microservices-ci
```

注意：创建分支、提交、推送属于版本控制操作，需要执行前确认。

### 4.2 合并顺序

推荐顺序：

1. 先合公共契约和 Maven 多模块骨架；
2. 再合商家与商品服务；
3. 再合互动与平台服务；
4. 再合账号与用户资产服务；
5. 最后合交易与履约服务；
6. 最后合 Gateway、K8s 和微服务流水线。

原因：交易服务依赖最多，最后合能减少反复返工。

### 4.3 每次合并前必须自检

每个人提交前至少确认：

```powershell
mvn -f services/pom.xml -pl <自己的服务名> -am -Dmaven.repo.local=D:/aituan_cache/m2 test
```

并检查：

- 服务能启动；
- `/actuator/health` 返回 UP；
- 没有连接其他服务数据库；
- 没有直接查询其他服务表；
- 内部写接口有幂等键；
- 相关接口有测试。

## 5. 工程结构统一标准

### 5.1 目标目录

```text
services/
├─ pom.xml
├─ common-contract/
├─ api-gateway/
├─ identity-asset-service/
├─ merchant-catalog-service/
├─ trade-fulfillment-service/
└─ engagement-platform-service/
```

当前 `services/backend/` 暂时保留，作为单体基线和迁移参考，不直接删除。

### 5.2 单个服务内部结构

每个服务尽量保持相同结构：

```text
<service>/
├─ pom.xml
└─ src/
   ├─ main/
   │  ├─ java/com/aituan/<domain>/
   │  │  ├─ <ServiceApplication>.java
   │  │  ├─ controller/
   │  │  ├─ service/
   │  │  ├─ repository/
   │  │  ├─ dto/
   │  │  ├─ client/
   │  │  ├─ config/
   │  │  └─ internal/
   │  └─ resources/
   │     ├─ application.yml
   │     └─ db/migration/<domain>/
   └─ test/
      └─ java/com/aituan/<domain>/
```

目录含义：

| 目录 | 说明 |
| --- | --- |
| `controller/` | 对外公开 API Controller |
| `internal/` | 服务间 `/internal/**` Controller |
| `service/` | 业务规则和流程编排 |
| `repository/` | 只访问本服务数据库 |
| `dto/` | 本服务 API DTO |
| `client/` | 调用其他服务的 HTTP Client |
| `config/` | 安全、Web、数据源、RestClient 等配置 |

### 5.3 公共模块限制

`common-contract` 可以放：

- `ApiResponse`
- 分页对象；
- 错误码；
- JWT claims DTO；
- 请求头常量；
- 内部接口 DTO；
- 通用异常基础类。

`common-contract` 禁止放：

- Repository；
- JdbcTemplate SQL；
- 商品、订单、优惠券等业务规则；
- 可变业务状态；
- 任一服务专属配置。

## 8. 统一接口标准

### 8.1 外部接口响应格式

沿用当前项目统一响应格式。若需要明确标准，统一为：

```json
{
  "code": "OK",
  "message": "success",
  "data": {}
}
```

错误示例：

```json
{
  "code": "TRADE_CHECKOUT_UNAVAILABLE",
  "message": "结算信息暂不可用，请稍后重试",
  "data": null
}
```

各服务不得自行返回完全不同结构。

### 8.2 内部接口响应格式

内部接口也使用同一响应结构，不暴露数据库表名、Repository 名称、SQL 错误、JPA 实体或内部外键。

内部接口只返回：

- 业务 DTO；
- 稳定快照；
- 聚合指标；
- 幂等处理结果。

### 8.3 内部请求头

所有服务间调用统一带：

| 请求头 | 是否必需 | 说明 |
| --- | --- | --- |
| `X-Request-Id` | 是 | 全链路追踪 ID，从 Gateway 或入口服务透传 |
| `X-Caller-Service` | 是 | 调用方服务名 |
| `Authorization` 或 `X-Service-Token` | 是 | 内部服务鉴权凭证，具体实现可先用共享 Secret |
| `Idempotency-Key` | 写接口必需 | 内部写接口幂等键 |

### 8.4 超时和重试

统一建议：

| 调用类型 | 超时 | 重试 |
| --- | ---: | --- |
| 内部查询 GET | 1500ms | 最多 1 次，仅连接失败或 5xx 可重试 |
| 内部写 POST | 3000ms | 默认不自动重试；只有同一 `Idempotency-Key` 的补偿任务可重试 |
| Gateway 到业务服务 | 5000ms | 不自动重试写请求 |

### 8.5 幂等键规则

内部写接口必须支持 `Idempotency-Key`。

建议生成规则：

```text
<caller-service>:<business-action>:<business-id>:<attempt-id>
```

示例：

```text
trade-fulfillment-service:inventory-deduct:order-10001:v1
trade-fulfillment-service:coupon-use:order-10001:v1
trade-fulfillment-service:inventory-restore:refund-20001:v1
engagement-platform-service:mark-order-reviewed:review-30001:v1
```

提供方按以下维度保存或识别幂等结果：

```text
调用方 + 接口 + 幂等键
```

## 9. 数据库拆分统一标准

### 9.1 基本规则

1. 每张业务表只能归属一个服务。
2. 每个服务只能连接自己的逻辑库。
3. 不允许跨库外键。
4. 不允许跨服务 JOIN。
5. 不允许一个服务复用另一个服务的 Repository。
6. 跨服务读取通过内部接口。
7. 跨服务展示通过快照或摘要 DTO。
8. 跨服务写入通过幂等命令和补偿。

### 9.2 四个逻辑库

```text
aituan_identity
aituan_merchant
aituan_trade
aituan_platform
```

### 9.3 推荐迁移目录

```text
database/microservices/
├─ identity/
│  ├─ migrations/
│  └─ seeds/
├─ merchant/
│  ├─ migrations/
│  └─ seeds/
├─ trade/
│  ├─ migrations/
│  └─ seeds/
└─ platform/
   ├─ migrations/
   └─ seeds/
```

### 9.4 Flyway 要求

项目已有硬性要求：Flyway 迁移脚本必须同时兼容 MySQL 8 与 H2 `MODE=MySQL` 空库迁移。

每个人负责自己的迁移脚本时必须遵守：

- 避免 MySQL 单方言专有写法；
- 避免 `AFTER`、触发器、存储过程、JSON 专有函数等未经双端验证的语法；
- seed 数据必须幂等；
- 不依赖清空数据库才能启动；
- 新增字段、索引、表要用风险低的增量迁移。

### 9.5 快照字段要求

跨服务历史展示必须保存快照，不能依赖远程服务实时 JOIN。

必须保存快照的典型场景：

| 场景 | 快照内容 |
| --- | --- |
| 下单 | 门店名、门店地址、商品名、SKU、单价、优惠金额、收货地址、履约规则 |
| 退款 | 原订单金额、支付流水、优惠使用情况、库存恢复对象 |
| 评价 | 订单 ID、门店 ID、门店名、商品摘要、用户展示名 |
| 投诉 | 订单摘要、门店摘要、用户摘要、投诉对象 |
| 客服 | 用户、商家、门店、订单上下文摘要 |
| 收藏 | 收藏对象名称、封面、副标题、类型 |

## 11. 关键业务链路统一标准

### 11.1 下单链路

```text
1. Gateway 转发下单请求到 trade-fulfillment-service
2. 交易服务读取购物车
3. 调用户资产服务获取用户状态和地址快照
4. 调商家商品服务获取门店履约规则和商品报价
5. 调商家商品服务预扣库存
6. 调用户资产服务使用优惠券
7. 创建订单、订单明细、支付记录、配送/预约记录和状态日志
8. 调用户资产服务发布站内消息
```

失败处理：

- 步骤 3 或 4 失败：不创建订单，返回“结算信息暂不可用，请稍后重试”。
- 步骤 5 失败：不使用优惠券，不创建成功订单。
- 步骤 6 失败：用原幂等键恢复库存，订单不进入支付成功。
- 步骤 7 后通知失败：订单不回滚，只记录消息发送失败并可重试。

### 11.2 退款链路

```text
1. 交易服务校验订单和退款资格
2. 写退款主记录
3. 更新订单状态
4. 调用户资产服务恢复优惠券或成长值
5. 调商家商品服务恢复库存
6. 写状态日志和补偿结果
```

失败处理：

- 补偿失败不重复退款；
- 退款记录保存 `compensation_pending`；
- 后台任务按原幂等键重试；
- 用户可看到退款已受理和补偿状态。

### 11.3 评价链路

```text
1. 互动平台服务接收评价请求
2. 调交易服务校验订单所属人和可评价状态
3. 调商家商品服务获取门店快照
4. 写评价记录
5. 调交易服务幂等标记订单已评价
6. 如需要，调用户资产服务发布站内消息
```

失败处理：

- 交易校验失败：不创建评价；
- 标记订单已评价失败：评价记录按订单唯一，后续用评价 ID 重试；
- 不允许互动平台直接更新订单表。

### 11.4 商家入驻链路

```text
1. 商家商品服务接收入驻申请
2. 平台后台审核资质
3. 审核通过后调用用户资产服务创建商家账号
4. 创建成功后商家状态变为可登录
```

失败处理：

- 商家资料已审核但账号创建失败：申请保持“账号待创建”；
- 重试账号创建；
- 如果账号创建成功但后续失败，调用停用账号命令补偿。

- [ ] 只连接自己的数据库；
- [ ] 迁移脚本只包含自己的表；
- [ ] seed 幂等；
- [ ] 不存在跨库 JOIN；
- [ ] 不存在直接访问其他服务表；
- [ ] 外部接口归属与 `微服务接口清单.md` 一致；
- [ ] 内部写接口有 `Idempotency-Key`；
- [ ] 服务间调用透传 `X-Request-Id`；
- [ ] 超时和错误文案符合约定；
- [ ] 单元/API/契约测试通过；
- [ ] Docker 镜像可构建；
- [ ] K8s health/readiness 可通过；
- [ ] 测试报告和运行日志可追溯。

## 17. 严格禁止事项

1. 禁止把服务按用户端、商家端、后台端拆。
2. 禁止建立万能 `admin-service` 直接读写所有表。
3. 禁止一个服务连接多个业务数据库。
4. 禁止跨库 JOIN。
5. 禁止跨服务共享 Repository。
6. 禁止内部接口返回数据库实体或表结构。
7. 禁止写接口没有幂等键。
8. 禁止为了赶进度只拆代码不拆数据库。
9. 禁止测试失败后继续部署。
10. 禁止只用截图代替测试代码、日志和原始报告。
11. 禁止提交密码、Token、数据库真实口令、云平台密钥。
12. 禁止在未确认前删除当前单体工程或覆盖主流水线。
