# 微服务接口清单

## 1. 清单口径

本清单基于当前后端运行时 OpenAPI 文档核对，接口统计日期为 2026-08-28，并于 2026-08-29 按课程任务书和数据所有权重新复核目标服务归属。

- 当前源码共有 **198 个带映射注解的 Controller 方法**。
- 由于部分方法同时暴露商家端与后台端前缀，且个别接口提供兼容别名，网关实际需要承接 **227 个 HTTP 操作、195 条唯一 URL 路径**。
- 227 个操作均且只归属一个目标服务：账号与用户资产 47 个、商家与商品 65 个、交易与履约 56 个、互动与平台 59 个。资源归属优先于 URL 字面前缀，例如 `/api/*/trade/stores/**` 由商家商品服务处理，`/api/admin/delivery/settings` 由平台配置所有者处理。
- 外部 URL 保持不变，仅由 Gateway 按资源路径转发；Controller/方法列用于从目标清单追溯当前模块化单体代码。

相关材料：[微服务划分设计](./微服务划分设计.md)、[微服务数据表归属方案](./微服务数据表归属方案.md)。

## 4. 内部契约约束

1. **身份与追踪**：请求携带服务身份凭证、`X-Caller-Service` 和 `X-Request-Id`；服务身份按调用矩阵授予最小权限。
2. **幂等**：所有 `POST` 写操作必须携带 `Idempotency-Key`，服务端按“调用方 + 接口 + 幂等键”保存处理结果。
3. **数据边界**：接口只返回业务 DTO 或稳定快照，不暴露 JPA 实体、逻辑库表名和内部外键。
4. **超时与重试**：查询接口允许有限次数短重试；写接口只有在幂等键不变时才允许重试。
5. **失败补偿**：当前阶段采用同步 REST 和显式补偿，不引入消息队列。交易服务是下单、支付、退款流程编排者。
6. **禁止跨库访问**：服务间只能调用本清单中的内部契约，不允许跨库 JOIN、共享 Repository 或直连其他服务账号。
7. **兼容策略**：拆分期间 Gateway 保持现有外部 URL；迁移完成后再按版本化策略演进外部 API。

## 5. 契约与当前代码的对应关系

内部接口不是凭空新增业务，而是把当前跨包方法调用或跨领域 SQL 移到数据所有者服务中。下表说明主要契约可复用的现有实现。

| 内部能力 | 当前代码基础 | 拆分动作 |
| --- | --- | --- |
| 地址和用户摘要 | `AccountService`、`AccountRepository` | 保留查询和 DTO，增加仅内网 Controller |
| 优惠券报价/使用/恢复 | `CouponService.calcDiscount/redeem/releaseByOrder` | 保留规则，补幂等记录和内部鉴权 |
| 成长值增加/退款恢复 | `MemberService.addOrderCompletionGrowth/refundOrderGrowth` | 保留规则，改由交易服务 HTTP 调用 |
| 站内消息发布 | `StationMessagePublisher` | 保留发布逻辑，改为内部命令 |
| 商家账号创建 | `AdminRepository.insertMerchantAccount/insertAccountRole` | 移入用户资产服务，商家审核只发幂等命令 |
| 门店/商品/履约快照 | `MerchantRepository`、`CatalogRepository`、`DiscoveryRepository` 及 `TradeRepository` 中相关映射 | 把 SQL 归并到商家商品库，返回稳定快照 DTO |
| 库存扣减/恢复 | 当前 `TradeService.reserveStock/restoreOrderStock` 及 `TradeRepository` 商品 SQL | 将库存写入移到商家服务，交易服务保留编排 |
| 订单快照/评价资格 | `TradeRepository`、`InteractionRepository` 当前订单校验逻辑 | 由交易服务统一校验，互动服务不再 JOIN/UPDATE 订单表 |
| 评价摘要 | `InteractionRepository.countStoreReviews`、`DiscoveryRepository.reviewSummary`、`StatisticsRepository` | 由互动服务聚合后返回数值 DTO |
| 平台审计 | 各 Repository 直接写 `sys_audit_log` 的方法 | 集中为互动平台内部命令 |
| 看板指标 | `StatisticsService/Repository` | 按数据所有者拆为四个指标端点，再由商家/平台看板聚合 |

该对应关系表同时给出实现边界：原 Controller、业务校验、状态机和返回 DTO 可以继续复用；需要改写的是数据访问方向和远程失败处理，不需要重新实现全部业务。

## 6. 调用失败、补偿与故障隔离

| 场景 | 失败点 | 对外结果 | 补偿/恢复 |
| --- | --- | --- | --- |
| 下单 | 地址、商品报价或履约规则查询失败 | 返回可重试的“结算信息暂不可用”，不创建订单 | 无已写数据则直接结束 |
| 下单 | 已扣库存后优惠券使用失败 | 订单保持创建失败/待补偿，不进入支付 | 用原 `Idempotency-Key` 调库存恢复 |
| 退款 | 恢复优惠券或库存失败 | 退款主记录保存 `compensation_pending`，用户可看到退款已受理/成功和补偿状态 | 后台任务按原幂等键重试，禁止重复增加库存或恢复券 |
| 商家入驻 | 商家资料已审核但账号创建失败 | 申请保持“账号待创建”，不暴露不可登录的正常商家 | 重试账号创建；已创建账号但后续失败时调用停用命令 |
| 发布评价 | 平台库已写评价但订单“已评价”标记失败 | 评价按 `order_id` 唯一键保持单份，用户不重复创建 | 用评价 ID 作为幂等键重试订单标记命令 |
| 评价/投诉/客服 | 订单或门店快照暂时不可用 | 创建动作返回明确提示；已存在记录继续使用历史快照展示 | 查询恢复后重新提交，不跨库兜底 |
| 首页/搜索 | 评分、偏好或未读数接口超时 | 返回门店/商品基本结果，扩展字段为空或默认值 | 不重试写操作；记录 requestId 和降级原因 |
| AI | 任一业务 skill 超时 | 返回现有确定性降级回复，保留会话 | 单个 skill 故障不阻塞其他服务 |

内部查询默认短超时并仅对连接失败做有限重试；写命令只能在幂等键不变时重试。服务启动不主动探测并阻塞等待其他服务，因此停止一个依赖服务不会造成四个服务一起启动失败或崩溃。

## 7. 接口测试与端到端回归责任

| 服务 | 外部 HTTP 操作数 | API 测试责任 | 主要 E2E 用例 |
| --- | ---: | --- | --- |
| 账号与用户资产 | 47 | 认证、账户、会员、优惠券、消息全部公开操作 | UC01、UC04、UC15、UC16、UC22 |
| 商家与商品 | 65 | 商家、门店、目录、搜索、位置以及门店规则全部公开操作 | UC02、UC03、UC17、UC18、UC19 |
| 交易与履约 | 56 | 购物车、结算、订单、支付、退款、预约、券码、配送任务全部公开操作 | UC05–UC10 |
| 互动与平台 | 59 | 评价、投诉、客服、AI、公告、配置、审计、看板和平台配送配置全部公开操作 | UC11–UC14、UC20、UC21、UC23 |

每个服务可以在只启动自身和自己的 H2 逻辑库时运行 Controller/Service/Repository 测试；跨服务调用使用契约 Stub 或 MockWebServer。完整 E2E 必须通过 Gateway 启动四个真实服务执行，禁止让测试直接连接逻辑库或依赖 spec 的执行顺序。

内部契约需要同时具备提供方契约测试和调用方错误处理测试，至少覆盖：成功、资源不存在、重复幂等键、超时、5xx 和补偿重试。公开接口的 227 个操作与 UC01–UC23 的 E2E 结果应进入同一份追溯表。
