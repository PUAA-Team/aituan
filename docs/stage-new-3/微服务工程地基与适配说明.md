# 微服务工程地基与适配说明

> 日期：2026-08-31
> 适用范围：分工前已完成的微服务基础框架，以及四位成员后续把单体业务迁入各自服务时的适配规则。
> 当前边界：本文只说明工程地基、公共契约、启动骨架、health/info 和后续适配方式；不代表业务拆分、数据库拆分、K8s、CI/CD 已经全部完成。

## 1. 当前已完成的工程地基

当前仓库已经从单体后端的单 Maven 模块，调整为 `services/` 下的 Maven 多模块工程：

```text
services/
├─ pom.xml
├─ common-contract/
├─ api-gateway/
├─ identity-asset-service/
├─ merchant-catalog-service/
├─ trade-fulfillment-service/
├─ engagement-platform-service/
└─ backend/
```

说明：

- `services/backend/`：保留原单体后端，作为业务迁移来源和单体基线，不直接删除。
- `services/common-contract/`：公共契约模块，供原单体和新微服务复用。
- `services/api-gateway/`：API Gateway 启动骨架，当前只验证启动、健康检查和版本信息。
- 四个业务微服务：当前只搭好启动骨架，不包含业务 Controller、Service、Repository 和数据库迁移。

## 2. 各模块职责

| 模块 | 当前职责 | 后续适配方向 |
| --- | --- | --- |
| `common-contract` | 统一响应、错误码、JWT 当前用户、请求追踪、公共枚举、基础异常 | 只继续放跨服务公共契约，不放业务规则和数据库访问 |
| `api-gateway` | 网关启动骨架，端口 8080，提供 `/actuator/health`、`/actuator/info` | 后续配置外部 URL 到四个业务服务的路由，并拦截外部访问 `/internal/**` |
| `identity-asset-service` | 账号与用户资产服务骨架，端口 8081 | 迁入认证、用户资料、地址、收藏、会员、优惠券、消息等归属代码 |
| `merchant-catalog-service` | 商家与商品服务骨架，端口 8082 | 迁入商家、门店、商品、SKU、库存、搜索、履约规则等归属代码 |
| `trade-fulfillment-service` | 交易与履约服务骨架，端口 8083 | 迁入购物车、结算、订单、支付、退款、券码、预约、配送等归属代码 |
| `engagement-platform-service` | 互动与平台服务骨架，端口 8084 | 迁入评价、投诉、客服、AI、公告、配置、审计、看板等归属代码 |
| `backend` | 原单体后端，继续可编译和测试 | 作为迁移参考；微服务稳定后再决定是否保留为基线或归档 |

## 3. 统一端口和启动类

| 服务 | 端口 | 启动类 |
| --- | ---: | --- |
| `api-gateway` | 8080 | `com.aituan.gateway.ApiGatewayApplication` |
| `identity-asset-service` | 8081 | `com.aituan.identity.IdentityAssetServiceApplication` |
| `merchant-catalog-service` | 8082 | `com.aituan.merchantcatalog.MerchantCatalogServiceApplication` |
| `trade-fulfillment-service` | 8083 | `com.aituan.tradefulfillment.TradeFulfillmentServiceApplication` |
| `engagement-platform-service` | 8084 | `com.aituan.engagementplatform.EngagementPlatformServiceApplication` |

当前 `api-gateway` 和 legacy 单体 `backend` 默认都可能使用 8080；本地验证时不要同时启动二者，或者临时通过 `SERVER_PORT` 调整其中一个端口。

## 4. common-contract 使用规则

### 4.1 可以放入 common-contract 的内容

- `ApiResponse`：统一响应壳。
- `PageResponse`：统一分页响应。
- `RequestIds` / `RequestIdFilter`：请求追踪 ID。
- `BusinessException` / `ErrorCode` / `GlobalExceptionHandler`：基础异常和错误码。
- `CurrentUser` / `CurrentUserContext` / `JwtTokenService` / `JwtAuthenticationFilter`：JWT 与当前用户上下文。
- `AccountType`、`BusinessType`、`DisplayOrderStatus`、`PaymentStatus` 等跨服务共享枚举。
- 后续确实被多个服务复用的内部接口 DTO。

### 4.2 禁止放入 common-contract 的内容

- Repository、Mapper、JdbcTemplate 访问逻辑。
- SQL、Flyway migration、seed 数据。
- 订单、商品、优惠券、会员、评价等具体业务规则。
- Controller 业务端点。
- 文件存储、图床、地图、AI、支付等具体实现。
- 定时任务、可变业务状态、跨服务缓存状态。

原则：`common-contract` 只做“契约和轻量基础设施”，不做“业务公共大杂烩”。

## 5. 成员迁移代码时怎么适配

### 5.1 迁移前先确认归属

每个成员先按以下文档确认自己负责的包、接口和表：

- `docs/stage-new-3/微服务并行拆分分工与统一标准.md`
- `docs/stage-new-3/微服务接口清单.md`
- `docs/stage-new-3/数据表归属方案.md`

不能只按当前 Java 包名迁移，因为单体里有些包可能同时服务多个端，例如后台、商家端和用户端聚合接口需要按资源归属重新分配。

### 5.2 迁移代码的推荐顺序

每个服务建议按以下顺序迁移，避免一次性搬太多导致难排错：

1. 先迁 DTO 和纯转换逻辑。
2. 再迁 Controller 的最小只读接口。
3. 再迁 Service 业务逻辑。
4. 再迁 Repository 和本服务数据库配置。
5. 最后迁写接口、幂等、跨服务调用和补偿逻辑。

每迁一步都要能单独编译，至少执行：

```powershell
mvn -f services/pom.xml "-Dmaven.repo.local=D:\aituan_cache\m2" -pl <服务模块名> -am test
```

### 5.3 package 适配规则

当前新服务启动类根包如下：

```text
com.aituan.identity
com.aituan.merchantcatalog
com.aituan.tradefulfillment
com.aituan.engagementplatform
```

业务代码迁入后，建议在对应根包下继续按职责分层：

```text
controller/
service/
repository/
dto/
client/
config/
internal/
```

例如商家与商品服务：

```text
services/merchant-catalog-service/src/main/java/com/aituan/merchantcatalog/
├─ MerchantCatalogServiceApplication.java
├─ controller/
├─ service/
├─ repository/
├─ dto/
├─ client/
├─ config/
└─ internal/
```

如从单体迁入的类原包名与新根包不一致，应在迁入时统一调整，不要在新服务里继续保留大量单体历史包名。

## 6. 数据库适配口径

当前工程地基阶段没有拆数据库，也没有给四个新服务加入 JDBC、Flyway、MySQL、H2 依赖。后续拆业务时再分别加入数据库能力。

后续适配时必须遵守：

| 服务 | 目标数据库 |
| --- | --- |
| `identity-asset-service` | `aituan_identity` |
| `merchant-catalog-service` | `aituan_merchant` |
| `trade-fulfillment-service` | `aituan_trade` |
| `engagement-platform-service` | `aituan_platform` |

要求：

- 每张业务表只能归属一个服务。
- 服务只能连接自己的库。
- 禁止跨服务直接查表、跨库 JOIN、跨库外键。
- 跨服务读取或写入必须通过 `/internal/**` 接口或后续约定的事件机制。
- Flyway 脚本必须兼容 MySQL 8 和 H2 `MODE=MySQL` 空库迁移。

## 7. Gateway 适配口径

当前 `api-gateway` 只做启动骨架，不配置真实路由。

后续适配时统一按资源归属配置路由：

- 外部 URL 尽量保持现有前端调用不变。
- Gateway 负责把 `/api/**` 转发到对应业务服务。
- 外部访问 `/internal/**` 必须拒绝。
- 后台接口不能整体做成一个“大后台服务”，仍应按资源归属路由到具体服务。

建议每个成员在自己服务分支中提交一份路由清单，最后由集成人统一合并到 Gateway。

## 8. health/info 验收方式

每个服务都应提供：

- `/actuator/health`：健康检查。
- `/actuator/info`：服务名、版本号、git commit 等版本信息。

| --- | ---: | --- | --- | --- |

| `identity-asset-service` | 8081 | `UP` | `0.0.1-SNAPSHOT` | `4a45cd7` |
| `merchant-catalog-service` | 8082 | `UP` | `0.0.1-SNAPSHOT` | `4a45cd7` |

## 9. 本地构建与验证命令

Windows 本机统一使用 D 盘 Maven 缓存，避免占用 C 盘：

```powershell
mvn -f services/pom.xml "-Dmaven.repo.local=D:\aituan_cache\m2" "-DskipTests" compile
```

新骨架模块打包：

```powershell
mvn -f services/pom.xml "-Dmaven.repo.local=D:\aituan_cache\m2" -pl common-contract,api-gateway,identity-asset-service,merchant-catalog-service,trade-fulfillment-service,engagement-platform-service -am "-DskipTests" package
```

全量 services 打包：

```powershell
mvn -f services/pom.xml "-Dmaven.repo.local=D:\aituan_cache\m2" "-DskipTests" package
```

legacy 后端测试：

```powershell
mvn -f services/pom.xml "-Dmaven.repo.local=D:\aituan_cache\m2" -pl backend -am "-Dspring.profiles.active=test" test
```

单个服务后续开发时：

```powershell
mvn -f services/pom.xml "-Dmaven.repo.local=D:\aituan_cache\m2" -pl <服务模块名> -am test
```

## 10. 后续分工前必须统一的检查项

每个成员开始拆业务前，先确认：

- 自己服务名、端口、数据库名与统一文档一致。
- 只从单体迁自己负责的业务，不顺手搬别人的表和接口。
- 新增公共代码前先判断是否真的跨服务复用；否则放在自己服务内。
- 内部接口统一放 `/internal/**`，并使用 `X-Request-Id`、`X-Caller-Service` 等请求头。
- 写接口后续要考虑 `Idempotency-Key`。
- 本地测试命令必须使用 D 盘 Maven 缓存。
- 提交和推送前必须先确认，提交信息不要添加 Claude co-author 行。
