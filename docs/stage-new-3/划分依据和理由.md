# 微服务划分依据与理由（内部论证报告）

> 口径更正：课程正式业务用例为 UC01–UC13，当前以 13 个 spec / 15 个 Playwright 场景追溯。

> **文档性质：内部讨论与答辩准备材料，不属于课程正式提交文件。**
>
> 正式提交仍以《微服务划分设计》《微服务接口清单》《微服务数据表归属方案》和图源为准。本报告用于记录决策过程、备选方案、代码证据和未完成风险，避免正式材料只给结论而无法回答“为什么”。

## 1. 结论

选择四个业务微服务：

1. 账号与用户资产服务；
2. 商家与商品服务；
3. 交易与履约服务；
4. 互动与平台服务。

API Gateway 使用现有 Nginx 演进，不计入业务微服务；四个服务使用同一 MySQL 实例的四个 Schema 和四个独立账号。

这套方案的核心依据不是接口数量均分，而是四类稳定业务不变量：

- “谁能登录、用户拥有什么资产”由账号与用户资产服务维护；
- “什么可以卖、在哪里卖、能否履约”由商家与商品服务维护；
- “一次交易处于什么状态、钱和履约如何流转”由交易与履约服务维护；
- “交易后的评价、投诉、客服和平台治理如何留痕”由互动与平台服务维护。

## 2. 课程任务书给出的判断标准

《软件工程基础实践》课程任务书（2026 夏）对后五天改造提出了以下硬要求：

- 至少三个业务微服务，Gateway、数据库和前端不计数；
- 每个服务能独立构建、测试和部署；
- 每张业务表明确归属，其他服务不能直接读写；
- 可以共用数据库服务器，但不能跨服务直接联表；
- 跨服务数据操作通过接口、事件或消息完成，并说明失败处理；
- 所有公开接口有 API 测试，全部确认用例做端到端回归；
- 完成自动扩缩容与依赖故障处理实验。

因此，判断一次划分是否合格，不能只看图是否有四个方框，还要同时回答：

1. 服务内的表和业务规则是否足够内聚；
2. 每个 UC 是否存在绕不开的跨库 JOIN；
3. 当前代码是否能渐进迁移；
4. 拆分后是否能独立启动、测试和部署；
5. 是否有适合 HPA 和故障注入的真实服务链路。

## 3. 备选方案比较

| 方案 | 结构 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- | --- |
| 三服务 | 用户；商家商品；订单 + 互动平台 | 服务数量少，短期工程量小 | 订单状态机与评价/客服/投诉/AI 混在一起，平台治理库和交易库耦合过高；故障隔离边界弱 | 不采用 |
| 四服务 | 用户资产；商家商品；交易履约；互动平台 | 与现有领域包吻合，交易强一致边界清楚，满足课程数量与实验要求 | 互动平台职责较多，需要用“交易后互动与治理”原则约束 | 采用 |
| 五服务 | 在四服务基础上再拆“客服 AI”或“平台治理” | 边界更细，独立扩缩容更灵活 | 课程周期短，内部调用、部署和测试矩阵明显增加；现有 support/complaint/interaction 共享治理逻辑较多 | 暂不采用 |
| 按三端拆分 | 用户后端、商家后端、后台后端 | 与页面入口直观对应 | 同一订单/商家数据会被多服务共同写，后台容易演变成万能服务，违反单一数据所有者 | 明确拒绝 |
| 按技术层拆分 | Controller、业务、数据库服务 | 工程结构看似整齐 | 不属于业务微服务，网络调用按技术层放大，不能形成业务内聚 | 明确拒绝 |

四服务方案是在十天课程周期、现有代码基础和最终实验要求之间的可执行折中。后续业务规模扩大时，互动平台服务可以再拆客服 AI 与治理服务，但本轮没有必要提前增加部署复杂度。

## 4. 各服务的内聚性理由

### 4.1 账号与用户资产服务

账号、角色、资料、地址、会员、优惠券和站内消息看似跨越“认证”和“营销”，共同点是都以账号/用户为资产所有者，并且需要维护领取次数、成长值唯一记账、券状态和消息已读等不变量。

将优惠券留在用户资产服务，而不是交易服务，可以让券模板、领取和用户券状态形成单一所有者；交易服务只请求报价、使用或恢复。将站内消息放在这里，是因为最终状态是用户的消息列表和已读状态，不是客服会话状态。

### 4.2 商家与商品服务

商家、门店、目录、价格、库存、接单模式和配送规则共同决定某项商品/服务是否可被交易。下单前的门店营业状态、起送价、配送范围、SKU 库存必须由同一个服务给出权威报价，避免交易服务复制并修改商品主数据。

Banner 和推荐配置也归这里，因为它们组织的是门店/商品发现结果。推荐所需的用户偏好和历史购买只通过有限信号接口输入，排序仍在商品目录边界内完成。

### 4.3 交易与履约服务

购物车、订单、支付、退款、券码、预约、配送和状态日志围绕一个订单聚合。支付是否成功、订单能否退款、券码是否可核销、预约是否取消和配送是否完成必须由同一个状态机编排。

用户券和商品库存不放进交易库，但交易服务承担跨服务流程编排：先获取报价，再执行库存/优惠券动作，失败时按幂等键反向补偿。订单保存门店、商品、地址和价格快照，使历史订单展示不依赖其他服务实时可用。

### 4.4 互动与平台服务

评价、投诉、客服、AI、公告配置和审计都属于交易后的互动与平台治理。它们共同使用参与者、订单/门店目标、人工处理状态、消息/日志时间线和审核留痕。

这个服务边界的约束是：它只拥有互动和治理事实，不成为用户、商家、商品或订单的主数据副本。后台治理请求仍按资源路由到各所有者；平台看板只聚合各服务返回的指标 DTO。

## 5. 现有代码为什么支持渐进拆分

### 5.1 已经存在的有利结构

当前后端是 Spring Boot 3.4.6、Java 17、JdbcTemplate，共 129 个 Java 文件。业务代码已经按包组织：

- 用户资产候选包：`auth/account/member/coupon/message`；
- 商家商品候选包：`merchant/catalog/discovery`；
- 交易候选包：`trade`；
- 互动平台候选包：`interaction/complaint/support/ai`。

这些包普遍具有 Controller、Service、Repository、DTO 四层。Controller 已经稳定暴露 198 个方法，运行时展开为 227 个 HTTP 操作；只要 Gateway 保持 URL，三端不需要同步重写。

Repository 使用 JdbcTemplate 而不是跨包 JPA Entity 关联。拆分时可以保留本服务表的 SQL 和 RowMapper，只把跨领域 SQL 替换为 Client，避免全量重写实体关系。

现有公共能力也可复用：

- `JwtTokenService` 和 `JwtAuthenticationFilter` 支持无状态本地验签；
- `RequestIdFilter` 已处理 `X-Request-Id`；
- `application.yml` 支持环境变量端口和数据源；
- Actuator 已暴露 health/info；
- Dockerfile 已使用 Java 17 JRE；
- Nginx 已统一代理 `/api/`，可继续细化资源路由。

### 5.2 需要局部改造的真实位置

不应声称“直接复制四个包就完成”。当前单数据库代码有以下拆库阻塞点：

- `TradeRepository` 直接查询地址、商品、门店和规则表，`TradeService` 直接调用 Coupon/Member/Message 类；
- `DiscoveryRepository` 的个性化推荐直接 JOIN 收藏、订单、评价，并查询未读消息；
- `InteractionRepository` 直接 JOIN 订单、门店、用户并修改 `order_item.is_reviewed`；
- `ComplaintRepository`、`SupportRepository` 依靠订单、门店、用户 JOIN 生成列表；
- AI skills 直接查询多个领域表；
- `AdminRepository` 与 `StatisticsRepository` 是明显的跨域聚合点。

这些位置数量有限且职责明确，可以通过内部接口和快照逐个替换。订单状态机、评价治理状态、投诉日志、客服消息编排、优惠券规则等核心业务逻辑可以保留。

### 5.3 推荐的最小改造路径

1. 在单体内先定义 `UserAssetPort`、`MerchantCatalogPort`、`TradeQueryPort`、`PlatformQueryPort`，用现有类实现，保证测试不变。
2. 把跨表 RowMapper 和查询逻辑移到真正的数据所有者包。
3. 创建四个启动模块和共享 contract/security 模块，先保持同仓库 Maven 多模块。
4. 将 Port 实现从本地调用替换为带超时、幂等和 requestId 的 HTTP Client。
5. 按商家商品、互动平台、用户资产、交易履约的顺序逐域切换 Gateway。
6. 每切一个域，先跑该服务 API/契约测试，再跑 UC01–UC13 的 15 个完整 E2E 场景；失败立即回退该路由。

这个过程属于“抽取服务”，不是重新开发一套业务。

## 6. 每个用例为什么不需要跨服务联表

正式的 UC01–UC13 逐用例审查位于《微服务划分设计》第 11 节。内部论证按数据协作方式归纳如下：

| 类型 | 用例 | 消除跨库 JOIN 的方式 |
| --- | --- | --- |
| 单服务闭环 | UC01、UC03、UC06、UC07、UC10、UC13 的核心记录 | 所需主数据和状态由一个服务拥有 |
| 查询增强 | UC02、UC11 | 基础结果由主责服务返回，评分/偏好/AI 卡片通过小型 DTO 契约补充 |
| 交易编排 | UC04–UC08、UC12 | 交易服务调用地址、券、商品、库存接口；订单快照和幂等补偿替代联表事务 |
| 交易后互动 | UC09、UC10 | 创建时校验订单/门店/用户并保存快照，后续状态流转只查平台库 |

不存在必须按多服务表实时分页 JOIN 才能完成的业务目标。当前投诉、客服和评价页面的名称筛选可以改为平台库快照列；推荐可以改为“偏好信号 + 商家目录本地排序”；看板可以改为指标 API 聚合。

## 7. 回归测试可行性

现有 Playwright 工程已经证明真实后端、商家 Web 和后台 Web 可以由测试自动启动，且外部请求集中在 `http://127.0.0.1:18080`。微服务化后保持这个 Gateway 地址，可复用 API Client、页面定位器和六个现有业务流。

当前 Playwright 已包含 UC01–UC13 的 13 个 spec / 15 个场景，经 Gateway 运行真实四服务；单个服务的跨服务依赖在其独立测试中使用契约 Stub。

## 8. 云原生实验为什么可做

### 8.1 HPA

首选商家与商品服务。首页、搜索和详情是读多接口，当前 `DiscoveryController` 已提供 `/api/app/discovery/home`、`/stores/search` 等公开 GET，服务无会话且没有定时任务，适合用稳定脚本提升 CPU/吞吐负载。

不首选交易服务，因为当前 `TradeDeliveryScheduler` 使用 `@Scheduled`。没有分布式锁时，多 Pod 会重复推进配送任务。这个风险应在文档中明确，而不是为了实验临时忽略。

### 8.2 故障处理

停止商家与商品服务是最有代表性的依赖故障：

- 新下单需要商品报价和库存，应在短超时后返回明确提示，且不能扣券或创建成功订单；
- 历史订单由交易快照展示，仍能查询；
- 用户资产、互动平台和交易服务自身健康检查仍保持正常；
- 商家服务恢复后可再次下单。

这一实验同时证明服务没有启动期强依赖、失败范围可控、快照设计有效。

## 9. 当前未完成项和风险

| 风险/缺口 | 影响 | 正式实施前措施 |
| --- | --- | --- |
| 仍是单 JAR、单数据源 | 不能证明独立构建/部署 | 创建四启动模块、四数据源配置和四镜像 |
| 跨领域 SQL 尚未替换 | 拆库后直接失败 | 按正式文档热点表逐项替换并加静态扫描 |
| 单个 Demo seed 写全部表 | 服务无法独立初始化 | 按 60 表归属拆为四份 |
| E2E 覆盖回退 | 不满足任务书用例回归项 | 保持 UC01–UC13 的 15 个场景经 Gateway 运行 |
| 尚无 Kubernetes/HPA 文件 | 无法完成两项实验 | 增加 Deployment/Service/HPA、资源限制和实验脚本 |
| 交易定时器多副本风险 | 可能重复推进配送 | 数据库抢占、分布式锁或单副本 Worker |
| 本地上传目录不支持平台多副本 | 文件可能只在某个 Pod | 对象存储或 ReadWriteMany 共享卷 |
| JWT 当前不含 merchantId | 交易/互动商家端需要解析归属 | 保留 accountId，通过商家内部映射接口获取并缓存 |
| 同一 MySQL 实例是共享故障点 | HPA 不等于数据库高可用 | 课程实验接受单实例，但报告中不宣称数据库高可用 |

## 10. 最终判断

四服务方案满足课程“至少三个业务服务”的数量要求，也能够给每张表单一所有者。更重要的是，它与当前领域包结构、外部 URL、JdbcTemplate Repository 和现有测试入口兼容，可以用有限的适配器替换完成抽取，而不需要重写全部业务。

正式答辩时应强调三点：

1. 当前设计已经证明每个 UC 都有非跨库联表的数据路径；
2. 当前仓库仍是单体，跨域 SQL 和部署文件属于下一阶段真实实施内容；
3. HPA、故障处理和 UC01–UC13 回归都有明确目标拓扑、接口和验收证据，不能只用文档或截图代替运行结果。
