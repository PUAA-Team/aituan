> 日期：2026-08-31  
> 阶段：软件工程基础实践后五天，微服务拆分与微服务流水线实施  
> 范围：本文只覆盖微服务拆分、数据库拆分、独立构建测试部署、微服务 CI/CD。自动扩缩容、故障注入、压力测试和性能对比实验后续单独成文。

## 1. 背景与验收口径

课程任务书要求后五天完成后端微服务改造，并能证明改造后的系统仍覆盖原业务场景。本阶段不是重新开发一套系统，而是在当前“爱团”单体后端基础上抽取业务微服务。

本方案延续 `docs/stage-new-3` 已形成的三份设计材料：

- `微服务划分设计.md`
- `微服务接口清单.md`
- `数据表归属方案.md`

当前仓库实际状态仍是单体后端：

- 后端工程：`services/backend/pom.xml`
- 后端镜像：`deploy/backend/Dockerfile`
- Kubernetes 后端部署：`k8s/03-backend.yaml`
- GitHub Actions 部署流水线：`.github/workflows/deploy.yml`

因此，本阶段的目标是把已有“设计方案”落成“可独立构建、测试、镜像化、部署的多个服务”。

### 1.1 本阶段必须满足的要求

| 课程要求 | 本阶段落地口径 |
| --- | --- |
| 至少 3 个业务微服务 | 拆为 4 个业务微服务，Gateway 不计数 |
| 每个服务单独构建、测试、部署 | 每个服务有独立 Maven 模块、启动类、配置、测试、JAR、Docker 镜像、K8s Deployment/Service |
| 每张表明确归属 | 60 张表按 4 个逻辑库和 4 个服务账号归属 |
| 其他服务不能直接读写表 | 每个服务只连接自己的逻辑库；跨服务数据通过 `/internal/**` REST 契约访问 |
| 不能跨服务联表 | 移除或隔离跨领域 SQL，改为快照、内部接口或聚合 DTO |
| 跨服务失败要有处理 | 同步 REST + 短超时 + 幂等键 + 显式补偿；暂不引入 MQ 和分布式事务 |
| 微服务自动构建部署 | GitHub Actions 按服务矩阵构建、测试、制镜像、部署、健康检查 |
| 改造前后版本可对比 | 保留单体基线版本，微服务完成后形成微服务版本标签或提交记录 |

### 1.2 本阶段暂不覆盖

以下内容是课程后五天也要求的内容，但不放在本文第一阶段实施范围内：

- HPA 自动扩缩容实验；
- 停止依赖服务或注入延迟的故障实验；
- 单体与微服务性能对比压测；
- 压测原始数据分析。

后续应单独补充：

- `云原生实验方案.md`
- `性能对比实验方案.md`
- `性能测试原始结果/`

## 2. 目标微服务架构

### 2.1 服务清单

| 服务 | 工程名 | 端口建议 | 逻辑库 | 核心职责 |
| --- | --- | ---: | --- | --- |
| API Gateway | `api-gateway` | 8080 | 无业务库 | 统一入口、路径路由、外部限流、健康聚合 |
| 账号与用户资产服务 | `identity-asset-service` | 8081 | `aituan_identity` | 认证、账号、用户资料、地址、收藏、会员、优惠券、站内消息 |
| 商家与商品服务 | `merchant-catalog-service` | 8082 | `aituan_merchant` | 商家、门店、资质、商品目录、库存、搜索推荐、履约规则 |
| 交易与履约服务 | `trade-fulfillment-service` | 8083 | `aituan_trade` | 购物车、结算、订单、支付、退款、券码、预约、配送 |
| 互动与平台服务 | `engagement-platform-service` | 8084 | `aituan_platform` | 评价、投诉、客服、AI、公告、配置、审计、看板聚合 |

说明：

- 4 个业务微服务都计入课程要求的“业务服务”。
- `api-gateway` 是基础设施，不计入业务服务数量。
- 暂不引入注册中心和配置中心，避免课程周期内复杂度过高。
- 服务发现先使用 Kubernetes Service DNS，例如 `http://merchant-catalog-service:8082`。

### 2.2 服务间调用方向

核心调用关系如下：

```text
客户端/前端
  ↓
api-gateway
  ├─ identity-asset-service
  ├─ merchant-catalog-service
  ├─ trade-fulfillment-service
  └─ engagement-platform-service

trade-fulfillment-service
  ├─ 调 identity-asset-service：地址快照、优惠券报价/使用/恢复、成长值、消息
  └─ 调 merchant-catalog-service：门店商品快照、履约规则、库存扣减/恢复

engagement-platform-service
  ├─ 调 identity-asset-service：用户摘要、消息发布
  ├─ 调 merchant-catalog-service：门店/商品快照、评分回写查询
  └─ 调 trade-fulfillment-service：订单快照、评价资格、订单指标

merchant-catalog-service
  ├─ 调 identity-asset-service：用户偏好、会员摘要
  ├─ 调 trade-fulfillment-service：订单指标、购买偏好
  └─ 调 engagement-platform-service：评价摘要、互动指标
```

## 3. 代码拆分方案

### 3.1 推荐目录结构

建议采用同仓库 Maven 多模块，先降低拆分成本，后续如果课程或部署需要，可再演进为多仓库。

目标结构：

```text
services/
├─ pom.xml                                  # 后端父 POM，统一依赖版本和插件
├─ common-contract/                         # 无业务状态共享契约
│  ├─ pom.xml
│  └─ src/main/java/com/aituan/common/...
├─ api-gateway/
│  ├─ pom.xml
│  └─ src/main/...
├─ identity-asset-service/
│  ├─ pom.xml
│  └─ src/main/...
├─ merchant-catalog-service/
│  ├─ pom.xml
│  └─ src/main/...
├─ trade-fulfillment-service/
│  ├─ pom.xml
│  └─ src/main/...
└─ engagement-platform-service/
   ├─ pom.xml
   └─ src/main/...
```

保留当前单体工程作为迁移参考：

```text
services/backend/
```

在微服务完全验证前，建议不要立即删除 `services/backend`，它用于：

- 单体基线对比；
- 回退参考；
- 迁移遗漏排查；
- 后续性能对比。

### 3.2 公共模块边界

`common-contract` 只能放无业务状态、跨服务真正通用的内容：

- 统一响应结构；
- 错误码枚举；
- 分页 DTO；
- JWT claims 读取结构；
- 请求追踪常量；
- 内部调用请求头常量；
- 通用异常基类；
- API 契约 DTO。

禁止放入：

- Repository；
- 业务 Service；
- 具体业务表名；
- 商品、订单、优惠券等业务规则实现；
- 可以导致共享数据库访问的工具类。

### 3.4 拆分实施顺序

为了降低一次性大改风险，建议按以下顺序推进：

#### 步骤 1：建立 Maven 多模块骨架

目标：先让 5 个服务工程空跑起来。

交付物：

- `services/pom.xml`
- `services/common-contract/pom.xml`
- `services/api-gateway/pom.xml`
- 4 个业务服务 `pom.xml`
- 5 个 Spring Boot 启动类
- 5 份 `application.yml`
- 5 个 `/actuator/health` 可访问

验收命令示例：

```powershell
mvn -f services/pom.xml -Dmaven.repo.local=D:/aituan_cache/m2 clean test
mvn -f services/pom.xml -pl identity-asset-service -am -Dmaven.repo.local=D:/aituan_cache/m2 package
```

#### 步骤 2：抽取公共契约和鉴权基础

目标：避免四个服务重复粘贴公共代码。

迁移内容：

- `ApiResponse`
- 分页响应；
- 错误码；
- 统一异常；
- `X-Request-Id` 常量；
- JWT claims 解析；
- 内部调用请求头和幂等键常量。

验收标准：

- `common-contract` 不依赖任何业务服务；
- 业务服务可以依赖 `common-contract`；
- `common-contract` 不访问数据库。

#### 步骤 3：先拆商家与商品服务

推荐优先拆该服务，因为它是读多服务，接口相对稳定，也便于后续 Gateway 路由验证。

迁移内容：

- 商家、门店、商品目录、首页搜索；
- 配送规则和接单设置；
- 库存扣减/恢复内部接口；
- 门店、商品、履约规则快照内部接口。

需要替换的跨域访问：

- 首页推荐中对用户收藏、订单、评价、未读消息的直接查询；
- 改为调用用户资产、交易、互动平台的摘要接口。

验收标准：

- 服务只连接 `aituan_merchant`；
- 能独立跑商家/商品 API 测试；
- Gateway 可以把 `/api/app/discovery/**` 和商家/目录路由转发到该服务。

#### 步骤 4：拆互动与平台服务

迁移内容：

- 评价；
- 投诉；
- 客服；
- AI 助手；
- 公告、配置、审计、文件元数据；
- 平台看板聚合。

需要替换的跨域访问：

- 评价创建时不直接 JOIN 订单表；改调交易服务的评价资格接口；
- 投诉和客服不直接 JOIN 用户、门店、订单表；改为创建时保存快照；
- AI 不直接读多个领域表；改调用内部只读契约。

验收标准：

- 服务只连接 `aituan_platform`；
- 评价、投诉、客服、AI API 测试通过；
- 订单或门店服务不可用时，不创建新的强校验数据，已有会话/投诉能展示快照。

#### 步骤 5：拆账号与用户资产服务

迁移内容：

- 认证登录；
- 账号角色；
- 用户资料、地址、收藏；
- 会员等级和成长值；
- 优惠券模板、用户券；
- 站内消息。

需要提供的内部接口：

- 用户摘要；
- 地址快照；
- 优惠券报价；
- 优惠券使用；
- 优惠券恢复；
- 成长值增加；
- 站内消息发布；
- 商家账号创建/停用。

验收标准：

- 服务只连接 `aituan_identity`；
- 登录后 JWT 能被其他服务本地验签；
- 交易服务不再直接调用本地 `CouponService`、`MemberService`、`StationMessagePublisher`。

#### 步骤 6：最后拆交易与履约服务

交易服务依赖其他三个服务，因此最后拆。

迁移内容：

- 购物车；
- 结算；
- 下单；
- 支付模拟；
- 退款；
- 预约；
- 券码；
- 配送任务和状态流转。

需要重点替换：

- `TradeRepository` 中直接查用户地址、商家门店、商品、优惠券、配送规则的 SQL；
- `TradeService` 中直接调用优惠券、会员、消息相关本地 Service 的逻辑；
- 配送任务多副本下的重复推进风险。

验收标准：

- 服务只连接 `aituan_trade`；
- 下单支付能通过用户资产和商家商品内部接口完成；
- 失败时不会出现“扣了库存但订单成功失败不明”的状态；
- 订单详情使用订单快照，不依赖商家服务实时可用。

## 4. 数据库拆分方案

### 4.1 逻辑库设计

使用一个 MySQL 实例，创建 4 个逻辑库：

```text
aituan_identity
aituan_merchant
aituan_trade
aituan_platform
```

每个服务只拥有自己的数据库账号：

```text
aituan_identity_svc   -> 只访问 aituan_identity
aituan_merchant_svc   -> 只访问 aituan_merchant
aituan_trade_svc      -> 只访问 aituan_trade
aituan_platform_svc   -> 只访问 aituan_platform
```

这样能满足课程“可以在同一个数据库服务器中使用不同数据库或 Schema，但不能跨服务直接联表查询”的要求。

### 4.2 数据库脚本目录结构

建议新增微服务数据库脚本目录：

```text
database/microservices/
├─ identity/
│  ├─ migrations/
│  └─ seeds/
├─ merchant/
│  ├─ migrations/
│  └─ seeds/
├─ trade/
│  ├─ migrations/
│  └─ seeds/
└─ platform/
   ├─ migrations/
   └─ seeds/
```

每个服务的 `spring.flyway.locations` 只指向自己的目录。

示例：

```yaml
spring:
  flyway:
    locations: classpath:db/migration/identity
```

### 4.3 表归属

| 逻辑库 | 表数 | 主要表 |
| --- | ---: | --- |
| `aituan_identity` | 17 | `iam_account`、`user_profile`、`user_address`、`member_level`、`coupon_template`、`user_coupon`、`support_station_message` |
| `aituan_merchant` | 14 | `merchant_profile`、`merchant_store`、`merchant_delivery_rule`、`catalog_item`、`catalog_sku`、`ops_banner_config` |
| `aituan_trade` | 11 | `cart`、`cart_item`、`order_main`、`order_item`、`order_payment_record`、`order_refund_record`、`delivery_task` |
| `aituan_platform` | 18 | `review_record`、`support_session`、`support_message`、`complaint_ticket`、`ai_assistant_conversation`、`sys_audit_log`、`file_asset` |

完整表归属以 `数据表归属方案.md` 为准。

### 4.4 跨库引用规则

1. 不建立跨库外键。
2. 不写跨库 JOIN。
3. 只保存逻辑 ID 和业务快照。
4. 历史订单、评价、投诉、客服会话必须保存必要展示快照。
5. 管理后台列表如果需要用户昵称、门店名、商品名，优先使用创建时保存的快照；确需实时展示时调用内部摘要接口。

### 4.5 迁移脚本拆分步骤

1. 以现有 `database/migrations/` 为基线，按 `数据表归属方案.md` 拆出四组建表语句。
2. 每组脚本只包含本服务拥有的表、索引和 seed。
3. 删除跨库外键或改为普通索引。
4. Demo 数据按依赖顺序拆分：账号和商家基础数据先导入，交易/互动保留逻辑 ID 和快照字段。
5. 每个服务单独跑 H2 `MODE=MySQL` 空库迁移测试。
6. 在 MySQL 8 中创建 4 个空库，分别执行四套迁移，验证从空库可初始化。

### 4.6 数据库验收命令示例

本机测试必须避开 C 盘缓存，继续使用 D 盘 Maven 缓存：

```powershell
mvn -f services/pom.xml -pl identity-asset-service -am -Dmaven.repo.local=D:/aituan_cache/m2 test
mvn -f services/pom.xml -pl merchant-catalog-service -am -Dmaven.repo.local=D:/aituan_cache/m2 test
mvn -f services/pom.xml -pl trade-fulfillment-service -am -Dmaven.repo.local=D:/aituan_cache/m2 test
mvn -f services/pom.xml -pl engagement-platform-service -am -Dmaven.repo.local=D:/aituan_cache/m2 test
```

## 5. 服务间接口与失败处理

### 5.1 内部接口前缀

所有服务间接口统一使用：

```text
/internal/**
```

Gateway 外网规则必须拒绝访问 `/internal/**`。

### 5.2 内部调用请求头

所有内部调用都带：

| 请求头 | 用途 |
| --- | --- |
| `X-Request-Id` | 串联一次外部请求的全链路日志 |
| `X-Caller-Service` | 标识调用方服务 |
| `Authorization` 或内部服务签名 | 服务间鉴权 |
| `Idempotency-Key` | 内部写接口幂等控制 |

### 5.3 关键内部接口

| 提供方 | 接口 | 调用方 | 用途 |
| --- | --- | --- | --- |
| 用户资产 | `GET /internal/users/{userId}/summary` | 交易、互动 | 获取用户状态与展示摘要 |
| 用户资产 | `GET /internal/users/{userId}/addresses/{addressId}/snapshot` | 交易 | 获取收货地址快照 |
| 用户资产 | `POST /internal/coupons/quote` | 交易 | 优惠券试算 |
| 用户资产 | `POST /internal/coupons/{couponId}/use` | 交易 | 占用或使用优惠券 |
| 用户资产 | `POST /internal/coupons/{couponId}/release` | 交易 | 取消/退款恢复优惠券 |
| 用户资产 | `POST /internal/messages` | 商家、交易、互动 | 发布站内消息 |
| 商家商品 | `GET /internal/stores/{storeId}/snapshot` | 交易、互动 | 获取门店快照 |
| 商家商品 | `GET /internal/stores/{storeId}/fulfillment-rules` | 交易 | 获取营业、起送、配送和预约规则 |
| 商家商品 | `POST /internal/catalog/checkout-quote` | 交易 | 校验商品、SKU、价格和可售状态 |
| 商家商品 | `POST /internal/inventory/deduct` | 交易 | 预扣库存 |
| 商家商品 | `POST /internal/inventory/restore` | 交易 | 恢复库存 |
| 交易履约 | `GET /internal/orders/{orderId}/snapshot` | 互动 | 获取订单快照 |
| 交易履约 | `GET /internal/orders/{orderId}/review-eligibility` | 互动 | 校验评价资格 |
| 交易履约 | `POST /internal/orders/{orderId}/reviewed` | 互动 | 幂等标记订单已评价 |
| 互动平台 | `GET /internal/reviews/stores/{storeId}/summary` | 商家商品 | 获取门店评分摘要 |
| 互动平台 | `POST /internal/audit-logs` | 账号、商家、交易 | 写入统一审计日志 |

完整接口清单以 `微服务接口清单.md` 为准。

### 5.4 失败处理原则

1. 查询接口：短超时、有限重试，失败后返回明确提示或降级字段。
2. 写接口：必须有幂等键，只有幂等键不变时允许重试。
3. 下单链路：如果地址、商品报价或履约规则查询失败，不创建订单。
4. 已扣库存后优惠券使用失败：订单不进入支付成功，使用原幂等键恢复库存。
5. 退款补偿失败：退款主记录保存 `compensation_pending`，后台任务按原幂等键重试。
6. 评价标记订单失败：评价记录按 `order_id` 唯一约束保持单份，后续用评价 ID 重试标记命令。
7. 首页和搜索增强信息超时：返回门店/商品基础结果，评分、偏好、未读数等扩展字段为空或默认值。

## 6. Gateway 与路由方案

### 6.1 Gateway 选型

为了控制实现复杂度，本阶段优先采用两种可选方案之一：

| 方案 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| Nginx Gateway | 仓库已有 Nginx 配置，改造成本低，适合课程展示 | 内部鉴权、服务聚合能力弱 | 第一阶段推荐 |
| Spring Cloud Gateway | Java 生态统一，路由和过滤器能力强 | 新增依赖和服务，调试成本高 | 后续可演进 |

本阶段建议先用 Nginx 实现路径路由，把精力放在业务服务拆分和数据库边界上。

### 6.2 路由规则

外部 URL 保持不变：

```text
/api/open/auth/**                         -> identity-asset-service
/api/app/account/**                       -> identity-asset-service
/api/app/message*/**                      -> identity-asset-service
/api/app/discovery/**                     -> merchant-catalog-service
/api/open/merchant/**                     -> merchant-catalog-service
/api/merchant/catalog/**                  -> merchant-catalog-service
/api/merchant/profile/**                  -> merchant-catalog-service
/api/merchant/stores/**                   -> merchant-catalog-service
/api/app/trade/**                         -> trade-fulfillment-service
/api/admin/delivery/tasks/**              -> trade-fulfillment-service
/api/app/interaction/**                   -> engagement-platform-service
/api/app/complaints/**                    -> engagement-platform-service
/api/app/support/**                       -> engagement-platform-service
/api/app/ai/**                            -> engagement-platform-service
/api/admin/governance/**                  -> engagement-platform-service
```

注意：后台路由不能按 `/api/admin/**` 整体转发，必须按资源归属细分。

### 6.3 路由验收

每条路由至少验证：

1. Gateway 可以转发到目标服务；
2. 目标服务日志能看到同一个 `X-Request-Id`；
3. `/internal/**` 无法从外部访问；
4. 服务下线时 Gateway 返回可识别错误，不误路由到其他服务；
5. 前端不需要改 base URL。

## 7. 独立构建与测试方案

### 7.1 构建目标

每个服务都要能单独构建：

```powershell
mvn -f services/pom.xml -pl api-gateway -am -Dmaven.repo.local=D:/aituan_cache/m2 package
mvn -f services/pom.xml -pl identity-asset-service -am -Dmaven.repo.local=D:/aituan_cache/m2 package
mvn -f services/pom.xml -pl merchant-catalog-service -am -Dmaven.repo.local=D:/aituan_cache/m2 package
mvn -f services/pom.xml -pl trade-fulfillment-service -am -Dmaven.repo.local=D:/aituan_cache/m2 package
mvn -f services/pom.xml -pl engagement-platform-service -am -Dmaven.repo.local=D:/aituan_cache/m2 package
```

### 7.2 测试分层

| 测试类型 | 范围 | 运行方式 |
| --- | --- | --- |
| 单服务单元测试 | Service、规则、状态机、异常分支 | 当前服务直接跑 Maven test |
| 单服务 API 测试 | Controller + Service + Repository + 本服务 H2/MySQL | 启动当前服务和自己的数据库 |
| 契约测试 | `/internal/**` 提供方和调用方 | 提供方校验 DTO；调用方使用 Stub/MockWebServer |
| 全链路 E2E | UC01–UC23 | Gateway + 四个真实服务 + 四个逻辑库 |
| 静态边界扫描 | 禁止跨库 SQL、禁止错误依赖 | CI 中脚本扫描 Repository 和配置 |

### 7.3 每服务测试责任

| 服务 | 必跑测试 |
| --- | --- |
| `identity-asset-service` | 登录注册、token 校验、资料地址、收藏、会员、优惠券、消息、商家账号创建内部接口 |
| `merchant-catalog-service` | 商家入驻、门店、资质、分类、商品、库存、首页、搜索、配送规则内部接口 |
| `trade-fulfillment-service` | 购物车、结算、下单、支付、退款、券码、预约、配送、补偿流程 |
| `engagement-platform-service` | 评价、回复、举报、投诉、客服、AI、公告、配置、审计、看板聚合 |
| `api-gateway` | 路由、外部路径阻断、`/internal/**` 拒绝、健康转发 |

### 7.4 边界扫描规则

CI 中建议增加轻量脚本，避免拆库后又写回跨域 SQL：

1. `identity-asset-service` 不得出现 `merchant_`、`catalog_`、`order_`、`review_` 等非本服务表直接 SQL。
2. `merchant-catalog-service` 不得出现 `user_coupon`、`order_main`、`review_record` 等非本服务表直接 SQL。
3. `trade-fulfillment-service` 不得出现 `user_address`、`catalog_item`、`coupon_template` 直接 JOIN。
4. `engagement-platform-service` 不得直接更新 `order_main`、`merchant_store`、`user_profile`。
5. 任一服务不得配置其他服务数据库账号。

## 8. Docker 镜像方案

### 8.1 镜像命名

使用 SHA 版本号，不只使用 `latest`：

```text
ghcr.io/<owner>/<repo>/api-gateway:sha-xxxxxxx
ghcr.io/<owner>/<repo>/identity-asset-service:sha-xxxxxxx
ghcr.io/<owner>/<repo>/merchant-catalog-service:sha-xxxxxxx
```

可额外保留分支标签：

```text
main
microservices
```

但部署必须使用 SHA tag，方便回滚和报告追溯。

### 8.2 Dockerfile 方案

可以采用一个通用 Dockerfile，通过构建参数选择 JAR：

```dockerfile
FROM eclipse-temurin:17-jre
WORKDIR /app
ARG SERVICE_JAR
COPY ${SERVICE_JAR} /app/app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

也可以每个服务独立 Dockerfile。课程验收更容易看的做法是每服务一份：

```text
deploy/microservices/
├─ api-gateway/Dockerfile
├─ identity-asset-service/Dockerfile
├─ merchant-catalog-service/Dockerfile
├─ trade-fulfillment-service/Dockerfile
└─ engagement-platform-service/Dockerfile
```

### 8.3 镜像构建验收

每个服务镜像构建后都要能：

1. 启动容器；
2. 暴露服务端口；
3. 返回 `/actuator/health`；
4. 输出版本信息；
5. 连接自己的数据库；
6. 不依赖其他服务启动才能进入健康状态。

## 10. GitHub Actions 微服务流水线方案

### 10.1 流水线目标

一次 push 后自动完成：

1. Checkout；
2. Java 17 环境；
3. 按服务运行单元/API/契约测试；
4. 打包每个服务 JAR；
5. 构建每个服务镜像；
6. 推送 GHCR；
7. 部署到 Kubernetes；
8. 等待 rollout；
9. 健康检查；

### 10.2 推荐工作流文件

保留原有单体流水线作为基线，新增微服务流水线：

```text
.github/workflows/microservices-ci.yml
.github/workflows/microservices-deploy.yml
```

不建议直接覆盖原 `.github/workflows/deploy.yml`，直到微服务版稳定。

### 10.3 CI 矩阵

示例矩阵：

```yaml
strategy:
  fail-fast: false
  matrix:
    service:
      - api-gateway
      - identity-asset-service
      - merchant-catalog-service
      - trade-fulfillment-service
      - engagement-platform-service
```

每个服务执行：

```yaml
- name: Test service
  run: mvn -B -f services/pom.xml -pl ${{ matrix.service }} -am test

- name: Package service
  run: mvn -B -f services/pom.xml -pl ${{ matrix.service }} -am -DskipTests package
```

### 10.4 镜像构建矩阵

```yaml
- name: Build and push service image
  uses: docker/build-push-action@v6
  with:
    context: .
    file: deploy/microservices/${{ matrix.service }}/Dockerfile
    push: true
    tags: |
      ${{ env.REGISTRY }}/${{ github.repository }}/${{ matrix.service }}:${{ steps.meta.outputs.image_tag }}
      ${{ env.REGISTRY }}/${{ github.repository }}/${{ matrix.service }}:main
```

### 10.5 部署步骤

部署时逐个服务设置镜像：

```bash
kubectl -n aituan set image deployment/api-gateway api-gateway="$IMAGE_REGISTRY/api-gateway:$IMAGE_TAG"

kubectl -n aituan set image deployment/engagement-platform-service engagement-platform-service="$IMAGE_REGISTRY/engagement-platform-service:$IMAGE_TAG"
```

```bash
kubectl -n aituan rollout status deployment/api-gateway --timeout=300s
kubectl -n aituan rollout status deployment/identity-asset-service --timeout=300s
kubectl -n aituan rollout status deployment/merchant-catalog-service --timeout=300s
kubectl -n aituan rollout status deployment/trade-fulfillment-service --timeout=300s
kubectl -n aituan rollout status deployment/engagement-platform-service --timeout=300s
```

内部健康检查：

```bash
kubectl -n aituan run health-$GITHUB_RUN_ID --rm -i --restart=Never \
  --image=curlimages/curl:8.10.1 -- \
  sh -c '
    curl -fsS http://api-gateway:8080/actuator/health &&
```

流水线失败时必须上传或打印：

- Maven Surefire 报告；
- E2E 报告；
- 镜像 tag 和 commit；
- rollout 失败记录。

这满足课程“要能说明一次部署失败是怎么查出来的”的要求。

## 14. 风险与处理

| 风险 | 表现 | 处理 |
| --- | --- | --- |
| 一次性拆分过大 | 编译错误和测试失败难定位 | 按服务逐个迁移，Gateway 按路径切流 |
| 跨域 SQL 遗漏 | 拆库后运行时报表不存在 | 增加静态扫描和 Repository 审查清单 |
| 交易流程补偿复杂 | 库存、优惠券、订单状态不一致 | 交易服务统一编排，内部写接口全部幂等 |
| 后台接口归属混乱 | 出现万能 admin 服务 | 后台接口按被管理资源归属到对应服务 |
| 公共模块膨胀 | 四服务又共享业务规则 | 公共模块只放契约和基础设施，不放业务 |
| Kubernetes 调试困难 | 只知道部署失败，不知道原因 | 流水线失败自动输出 describe、logs、events |
| 本地 C 盘空间不足 | Maven/Gradle/日志挤占 C 盘 | 坚持使用 D 盘缓存和产物目录 |

## 16. 当前结论

现有 `docs/stage-new-3` 的微服务设计材料已经说明“拆成什么”和“为什么这样拆”。本文补充的是“怎么实施”：

1. 用 Maven 多模块把单体抽成 4 个业务服务和 1 个 Gateway；
2. 用 4 个 MySQL 逻辑库和 4 个服务账号完成数据库拆分；
3. 用 `/internal/**` 契约、快照、幂等键和补偿替代跨服务联表；
4. 用每服务独立测试、镜像、K8s 资源和 GitHub Actions 矩阵流水线满足课程验收；
5. 暂不把 HPA、故障注入和压力测试混入第一阶段，避免主线任务过散。

下一步进入代码前，需要确认三项重大改动：

1. 是否采用同仓库 Maven 多模块；
2. 是否保留 `services/backend` 作为单体基线；
3. 是否用 Nginx 作为第一阶段 Gateway，而不是立刻引入 Spring Cloud Gateway。
