# 第二阶段微服务集成准备说明

> 分支：`ms/integration-prep`
> 来源：`软件工程基础实践-2026夏.pdf` 第二阶段要求
> 目的：在 A/B/D 分支修复、性能测试分工推进期间，提前完成不依赖具体业务代码合并的集成准备工作。

## 1. 第二阶段评分点对应关系

课程 PDF 后 5 天第二阶段共 30 分，核心不是继续做新业务，而是证明微服务版本能运行、能部署、能回归、能实验、能对比。

| 评分点 | 分值 | 要求摘要 | 当前能否单独先做 |
| --- | ---: | --- | --- |
| 微服务划分 | 7 | 至少 3 个业务微服务，说明每个服务负责什么、为什么这样分，提交服务划分图、接口清单、数据表归属表、跨服务调用说明 | 可以继续完善材料，但主体方案已基本有了 |
| 数据归属 | 5 | 每张业务表明确归属，其他服务不能直接读写，不能跨服务联表查询，调用失败要说明处理办法 | 可以先做最终归属核对和 SQL 扫描脚本/记录 |
| 微服务流水线 | 5 | 相关服务代码提交后自动构建、测试、制作镜像和部署 | 可以先做集成 workflow 草案和失败诊断机制，不做真实部署 |
| 用例回归 | 4 | 所有后端公开接口有 API 测试，全部业务场景做 E2E 回归 | 可以先整理公开接口到用例的映射，等服务合并后补跑 |
| 自动扩缩容 | 3 | HPA 能随压力升高扩容、压力下降缩容，记录吞吐、平均/P95、错误率 | 性能测试已分出去，这里只保留对接口径 |
| 故障处理 | 2 | 停止依赖服务或注入延迟，系统返回备用结果，其他服务不一起崩溃 | 可以先选实验链路和预期降级结果 |
| 性能对比 | 4 | 单体和微服务同机器、同数据、同脚本，2 到 3 个接口各跑至少 3 次 | 已分出去，当前不重复做 |

## 2. 当前你适合单独先做的事

不在 C 分支继续做，而是在 `ms/integration-prep` 做公共集成准备。按实际价值排序：

### 2.1 合并前最低门槛检查

这是为了避免 A/B/D 分支直接合进来把工程地基冲坏。它不是形式化清单，而是合并前必须执行的硬门槛。

每个成员分支合并前必须满足：

1. 分支基线正确：必须包含 `origin/microservices-main`。
2. 只提交自己服务范围内的代码、数据库、Docker/K8s、测试和文档。
3. 不反向覆盖 `services/backend` 的工程地基。
4. 不在 `services/backend/src/main/java/com/aituan/common/**` 重新复制公共类。
5. 不删除 `docs/ReadMe.md` 已有 stage-new-3 索引。
6. 服务只访问自己的库和表。
7. Gateway 路由不保留 `legacy`、不保留 `/api/** -> backend` 兜底。
8. Flyway 迁移能在 H2 `MODE=MySQL` 和 MySQL 8 空库运行。
9. 单服务测试、内部接口测试、Gateway 路由测试必须通过。
10. Docker/K8s/CI 文件不包含真实密码、Token、kubeconfig 或私钥。

建议检查命令模板：

```powershell
# 1. 拉取远端
git fetch origin

# 2. 检查分支是否包含微服务主地基
git merge-base --is-ancestor origin/microservices-main origin/<branch>

# 3. 查看相对微服务主分支的改动范围
git diff --name-status origin/microservices-main..origin/<branch>

# 4. 检查格式问题
git diff --check origin/microservices-main..origin/<branch>

# 5. 检查是否误改旧单体 common 公共类
git diff --name-only origin/microservices-main..origin/<branch> -- services/backend/src/main/java/com/aituan/common

# 6. 检查 Gateway 是否还有 legacy fallback
git grep -n "legacy\|AITUAN_LEGACY_URI\|/api/\*\*" origin/<branch> -- services/api-gateway/src/main/resources/application.yml
```

## 3. PDF 第二阶段里还能单独推进的实际工作

### 3.1 做最终服务运行证据口径

PDF 要求现场能查看：

- 服务日志；
- 健康检查；
- 就绪检查；
- 版本号；
- 一次部署失败是怎么查出来的。

这件事可以提前准备，不依赖 A/B/D 合并完成。

建议后续统一要求每个服务都有：

```text
/actuator/health
/actuator/info
readinessProbe
livenessProbe
service name
version
commit id
```

K8s 诊断命令口径：

```powershell
kubectl -n aituan get pods,svc,events
kubectl -n aituan describe deployment/<deployment-name>
kubectl -n aituan logs deployment/<deployment-name> --tail=120
kubectl -n aituan rollout status deployment/<deployment-name> --timeout=300s
```

### 3.2 做 Gateway 最终禁止项核对

PDF 要求最终微服务版本，不应依赖旧单体完成业务。Gateway 合并时必须保证：

```text
没有 AITUAN_LEGACY_URI
没有 legacy-api-fallback
没有 /api/** 兜底到 backend
外部不能访问 /internal/**
```

这个可以在合并前先形成固定口径，等 A/B/D 分支修完后再统一落代码。

### 3.3 做数据归属核对记录

PDF 对数据归属给 5 分，要求很明确：每张业务表归哪个服务，其他服务不能直接读写。

目前可以先做核对动作，重点查：

```text
identity-asset-service 是否只访问 aituan_identity 归属表
merchant-catalog-service 是否只访问 aituan_merchant 归属表
trade-fulfillment-service 是否只访问 aituan_trade 归属表
engagement-platform-service 是否只访问 aituan_platform 归属表
```

合并前发现跨服务查表，要让对应同学改成 `/internal/**` 调用。

### 3.4 做公开接口测试缺口统计

PDF 明确要求：所有后端公开接口都要有 API 测试，全部业务场景都要做 E2E 回归。

现在可以先做“接口覆盖统计”，不用马上写完所有测试：

1. 从 Controller 扫描所有公开接口；
2. 对照现有测试文件；
3. 标出未覆盖接口；
4. 合并后按缺口补测试。

这比泛泛写清单更有用，因为它直接对应第二阶段 4 分“用例回归”。

### 3.5 做故障处理实验链路选择

性能测试已分出去，但故障处理还有 2 分，可以先设计具体实验链路。

建议选 C 下单链路作为故障处理实验：

```text
Gateway -> trade-fulfillment-service -> merchant-catalog-service
```

实验方式：停止 B 服务或让 B 服务超时。

预期结果：

- C 服务不能崩溃；
- 用户得到明确提示，例如“商品服务暂不可用，请稍后重试”；
- Gateway 和 C 服务有错误日志；
- A/D 服务不受影响；
- K8s 中只有 B 或 C 相关调用失败，不出现全系统不可用。

这件事可以先写实验口径，等 A/B/C 合并后执行。

## 4. 本分支建议只做这些，不继续扩大

`ms/integration-prep` 分支建议只放公共集成准备内容，不放 C 服务业务代码。

当前建议范围：

- A/B 分支检查反馈文档；
- 第二阶段微服务集成准备说明；
- 必要时补一个很小的脚本，用于检查分支是否包含 `microservices-main`、是否误改 backend、是否有 legacy fallback。

不建议现在做：

- 替 A/B/D 改业务代码；
- 直接合并分支；
- 真实部署 Kubernetes；
- 写大量重复清单；
- 继续扩 C 服务功能；
- 做性能测试重复工作。

## 5. 下一步最实用建议

如果继续推进，我建议只做一个小工具脚本：

```text
scripts/verify/check_microservice_branch_ready.ps1
```

作用：输入分支名，自动输出它是否满足合并前最低门槛，例如：

- 是否包含 `origin/microservices-main`；
- 是否误改 `services/backend/src/main/java/com/aituan/common/**`；
- 是否删除 `docs/ReadMe.md` stage-new-3 索引；
- Gateway 是否包含 legacy fallback；
- 是否有格式问题。

这个比继续写更多文档更有价值，也符合 PDF 第二阶段对“可重复检查、可追溯证据”的要求。
