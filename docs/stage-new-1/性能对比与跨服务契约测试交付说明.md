# 性能对比与跨服务契约测试交付说明

## 1. 交付范围

本轮完成以下工作：

1. 建立单体与微服务共用的性能测试场景和无第三方依赖压测脚本。
2. 在同一台机器、同一份 H2 demo seed、同一套参数下完成单体正式压测 3 轮，保存逐请求结果、资源采样、机器配置和汇总。
3. 建立 3 项跨服务消费者驱动契约，并完成离线 HTTP mock 验证。
4. 将离线契约测试接入 GitHub Actions，保存契约报告 artifact。

本轮没有生成微服务性能数字。原因是 `origin/microservices-main` 在测试时只有 Gateway 和四个空服务骨架，尚无 Gateway 路由和业务接口；账号、商家、交易实现仍分散在三个功能分支，互动服务尚未落地。此时虚构或用空健康接口代替业务接口进行比较会使结论无效。

## 2. 性能测试工具

### 2.1 文件

- `tests/performance/load-test.mjs`：统一压测入口。
- `tests/performance/scenarios.json`：单体和微服务 Gateway 共用的场景与业务成功断言。
- `tests/performance/README.md`：本地运行、双目标比较和输出说明。

脚本支持重复传入 `--target label=URL`，并按顺序对各目标使用完全相同的场景和参数。指定 `--pids label=PID1,PID2` 后会同步采样服务 CPU 和常驻内存。

每次运行输出：

- `machine.json`：机器、操作系统、CPU、内存、Node、Java、Maven 和 Git commit。
- `test-config.json`：数据集、目标、并发、请求量、超时和 PID。
- `raw/*.jsonl`：逐请求时间、场景、HTTP 状态、业务断言结果和耗时。
- `resources/*.jsonl`：逐采样点进程 CPU 和内存。
- `summary.json`、`summary.csv`：每轮及多轮汇总。

### 2.2 统一场景

| 场景 | 方法与路径 | 说明 |
| --- | --- | --- |
| 发现页主页 | `GET /api/app/discovery/home` | 聚合模块与推荐数据 |
| 推荐列表 | `GET /api/app/discovery/recommendations` | 分页推荐查询 |
| 门店搜索 | `GET /api/app/discovery/stores/search` | 关键词分页搜索 |

三个接口均为只读接口，单体与微服务改造后保持外部 URL 不变。成功条件同时要求 HTTP 200 和 `$.code == 0`。

### 3.3 复现命令

后端以 demo profile 在 `18080` 启动后，取得 Java PID 并运行：

```powershell
node tests/performance/load-test.mjs `
  --target monolith=http://127.0.0.1:18080 `
  --pids monolith=<Java PID> `
  --runs 3 `
  --concurrency 50 `
  --requests 15000 `
  --warmup-requests 1000 `
  --output tests/performance/results/monolith-<日期>
```

微服务完成后，在同一台机器停止单体、启动 Gateway 和服务，再追加 `microservices` 目标及对应 PID；详细命令见 `tests/performance/README.md`。

离线执行结果为 **3/3 通过**，报告位于 `tests/contracts/results/offline-contract-report-20260901.json`。离线模式会建立本机临时 HTTP mock Provider，验证消费者请求序列化和响应解析；真实服务合并后使用 `--live` 对 Provider 原样复验。

## 5. 发现的不一致与后续门槛

公共 `ApiResponse.ok()` 的成功码为 `0`，`1000` 是 `BAD_REQUEST`。远端 `origin/microservice-b-merchant-catalog` 的 `MerchantCatalogServiceIntegrationTest.inventoryDeductRequiresServiceHeadersAndReusesIdempotencyKey` 当前把成功码断言为 `1000`，合并前应修正为 `0`，否则测试口径与公共契约冲突。

在宣布“微服务性能提升”或“真实跨服务契约全部通过”前，必须满足：

1. 四个业务服务与 Gateway 合并到同一可运行分支，外部三场景均通过 Gateway。
2. 单体和微服务使用同一机器、同一 seed、同一并发、请求量、预热和轮次，测试时不并行运行。
3. 在线契约模式对真实 Provider 通过，而不只依赖 mock。
4. 保存微服务逐请求、资源采样和机器配置原始文件，再基于数据解释差异；微服务更慢也属于有效结果。
