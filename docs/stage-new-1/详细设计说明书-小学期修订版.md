# 1 引言

## 1.1 编写目的

本文档用于说明“爱团”本地生活服务综合平台的详细设计。文档以业务场景为主线，描述系统在关键业务流程中的对象协作、数据状态、接口权限、异常处理、性能策略和测试追踪关系。

本文档重点服务于以下目标：

1. 说明当前系统在单体版本中的对象级实现设计。
2. 明确各业务场景涉及的前端页面、后端对象、数据表和状态流转。
3. 建立业务场景、详细设计、代码模块和测试项之间的追踪关系。
4. 为后端服务拆分、接口治理、自动化测试和系统维护提供设计依据。

## 1.2 系统背景

爱团是一个综合本地生活服务平台，面向城市居民提供外卖订餐、到店团购、酒店民宿、休闲娱乐、电影演出、丽人医美、景点门票、按摩足疗等服务。系统由用户端 APP、商家端 Web、平台管理后台 Web、Spring Boot 后端、MySQL 数据库和文件资源能力组成。

系统建设目标如下：

1. 为用户提供商家搜索、分类浏览、商品服务查看、收藏、下单、支付、配送跟踪、券码核销、评价反馈、会员优惠和消息通知等功能。
2. 为商家提供入驻申请、门店资料维护、商品服务管理、订单处理、外卖履约、券码核销、认证材料提交、评价回复和经营数据查看等功能。
3. 为平台管理员提供商家审核、认证审核、用户治理、商品治理、订单治理、配送治理、公告运营、平台配置、权限控制和审计追踪等功能。

## 1.3 运行角色

| 角色 | 说明 |
| --- | --- |
| 游客 | 未登录访问者，可浏览首页、模块、搜索结果和公开商家商品信息。 |
| 用户 | 注册并登录的消费者，可维护资料、地址和收藏，完成下单、支付、评价、投诉、客服、会员优惠券等操作。 |
| 商家 | 入驻平台的经营主体，可维护门店、履约规则、商品服务目录，并处理订单、核销、评价和客服消息。 |
| 平台管理员 | 平台运营和治理人员，可处理评价审核、投诉处理、退款干预、配置和审计等支撑能力。 |
| 系统服务 | 执行模拟支付、配送推进、消息生成、AI 降级回复、统计汇总等内部任务。 |

## 1.5 设计原则

1. 按最终业务场景组织详细设计，避免按页面、按钮或接口拆分用例。
2. 对象级设计追踪到真实代码模块，优先使用当前 Controller、Service、Repository 和 DTO 命名。
3. 统一订单模型承载外卖、券码、预约、退款等交易场景，通过状态和履约子对象区分差异。
4. 用户、商家、管理员使用不同接口空间，后端统一校验登录态、角色和数据归属。
5. 模拟支付、配送、AI 回复等增强能力可降级，不影响核心业务闭环。
6. 文档编号与测试编号保持一致，便于形成追溯表。

# 2 系统总体结构设计

## 2.1 总体架构

爱团系统采用前后端分离的多端架构。用户端 APP 负责消费者侧浏览、下单、履约查看和售后交互；商家端 Web 负责门店经营、商品服务维护和订单处理；平台管理后台 Web 负责评价、投诉、退款、配置和审计等平台支撑能力；后端服务统一承载认证授权、业务规则、状态流转、数据访问、文件处理、消息生成和 AI 辅助。

![系统总体架构图.drawio](https://2bpic.oss-cn-beijing.aliyuncs.com/%E7%B3%BB%E7%BB%9F%E6%80%BB%E4%BD%93%E6%9E%B6%E6%9E%84%E5%9B%BE.drawio.png)

`ARCH-OVERALL` 系统总体架构图。

系统主要组成如下：

| 组成部分 | 主要职责 |
| --- | --- |
| 用户端 APP | 首页浏览、搜索筛选、商家详情、下单支付、订单详情、配送跟踪、券码预约、评价投诉、客服、会员优惠券。 |
| 商家端 Web | 商家登录、门店资料、商品服务目录、履约规则、订单处理、配送推进、券码核销、预约确认、评价回复、客服会话。 |
| 平台管理后台 Web | 评价审核、投诉处理、退款干预、商家和商品治理、公告配置、平台设置、审计日志。 |
| 后端业务服务 | 认证、账号、发现搜索、商家商品、交易履约、会员优惠券、评价投诉、客服、消息、AI 辅助。 |
| 数据库 | 保存账号、用户、商家、门店、商品服务、订单、支付、配送、券码、预约、评价、投诉、客服、消息和配置数据。 |
| 文件资源服务 | 保存头像、门店封面、商品图片、评价图片、投诉证据和资质材料等文件资源。 |
| 系统任务与外部适配 | 执行配送模拟推进、消息生成、统计汇总、AI 调用和降级处理。 |

核心业务链路如下：

```text
用户发现服务 -> 浏览商家/商品 -> 下单与模拟支付 -> 商家履约 -> 配送/券码/预约完成 -> 评价/客服/投诉 -> 会员和优惠沉淀
```

## 2.2 技术结构

| 层次 | 技术与实现 |
| --- | --- |
| 用户端 | Flutter APP，采用页面、Repository、模型对象分层组织。 |
| 商家端 | Vue 3 + TypeScript，采用页面组件和 API 封装组织。 |
| 平台后台 | Vue 3 + TypeScript，采用管理页面、弹窗组件和 API 封装组织。 |
| 后端 | Spring Boot，按 `Controller -> Service -> Repository` 分层。 |
| 数据库 | MySQL，使用 Flyway 管理迁移和演示种子数据。 |
| 部署 | Docker Compose、Nginx、GitHub Actions，后续支持 Kubernetes 部署。 |

## 2.3 设计范围

本文档覆盖 13 个核心业务场景，范围包括用户账户、搜索浏览、资料地址收藏、外卖交易、配送履约、非外卖券码、预约核销、退款、评价、投诉、客服、会员优惠券和商家商品维护。

不作为独立业务场景展开的内容包括：

1. 平台后台完整治理链路。平台能力只作为评价审核、投诉处理、退款处理等用例中的参与动作。
2. 商家入驻和资质审核。该能力保留为支撑模块，不进入本轮 13 个核心用例。
3. 真实支付、真实配送、复杂酒店房态、电影选座和复杂技师排班。
4. 纯页面跳转、单个按钮点击、单个数据库操作和单个 API 调用。

# 3 功能模块与子系统详细设计

本章说明系统主要子系统及其职责。子系统描述用于给出稳定结构边界，业务场景章节用于说明跨子系统协作流程，两者共同构成详细设计。

## 3.1 账号与用户资产子系统

账号与用户资产子系统负责用户身份、登录态、个人资料、地址、收藏、会员、优惠券和站内消息等能力。该子系统对外提供用户侧账户接口，并在交易、客服、投诉等场景中提供用户身份和资产状态。

主要职责：

1. 用户注册、登录、验证码、Token 校验和退出登录。
2. 用户资料、头像、收货地址、默认地址和收藏记录维护。
3. 会员等级、成长值和权益展示。
4. 优惠券查询、领取、可用券筛选和状态维护。
5. 站内消息查询、已读、批量已读和订单状态消息展示。

支撑用例：UC01、UC03、UC12，并支撑 UC04、UC05、UC08、UC11。

## 3.2 商家与商品子系统

商家与商品子系统负责供给侧数据，包括商家、门店、商品服务、分类、上下架、封面图片和履约规则。该子系统支撑用户发现服务，也支撑交易下单时的商品状态、价格和可售性校验。

主要职责：

1. 首页、模块、搜索、筛选、排序、商家详情和商品服务详情查询。
2. 商家资料、门店资料、营业状态、公告、封面和联系方式维护。
3. 商品服务新增、编辑、分类、库存、价格、图片和上下架状态维护。
4. 外卖起送价、配送费、配送范围、餐具和打包费等履约规则维护。
5. 为交易下单提供商品快照、门店快照和业务类型判断。

支撑用例：UC02、UC13，并支撑 UC04、UC05、UC06、UC07。

## 3.3 交易与履约子系统

交易与履约子系统负责用户从加购、试算、下单、模拟支付到订单履约完成的核心状态流转。系统使用统一订单模型承载外卖、非外卖券码和预约类订单，并通过配送任务、券码记录、预约记录区分不同履约方式。

主要职责：

1. 外卖购物车、商品数量、清空购物车和金额小计。
2. 订单试算、优惠券抵扣、配送费、打包费和应付金额计算。
3. 订单创建、模拟支付、订单详情、取消、退款和状态日志。
4. 外卖订单接单、拒单、备餐、出餐、配送推进、送达和完成。
5. 非外卖订单出券、券码查询、券码核销、预约创建和预约确认。
6. 与消息、会员、优惠券子系统联动，处理订单状态通知和会员资产变化。

支撑用例：UC04、UC05、UC06、UC07、UC08、UC12。

## 3.4 互动、客服与投诉子系统

互动、客服与投诉子系统负责订单完成后的评价、售后沟通和投诉处理，也负责 AI 助手对业务数据的查询和降级回复。该子系统不直接改变交易主流程，但会读取订单、商家、用户和消息等上下文。

主要职责：

1. 评价发布、我的评价、评价详情、商家回复和平台审核。
2. 评价举报、有用投票和违规内容治理。
3. 客服会话创建、消息发送、商家回复、平台介入、转人工和关闭。
4. 投诉提交、证据上传、投诉补充、商家查看、平台受理、处理和关闭。
5. AI 助手调用订单、优惠券、地址、收藏、客服、投诉等 Skill，异常时返回规则降级回复。

支撑用例：UC09、UC10、UC11，并支撑 UC08。

## 3.5 平台支撑与治理子系统

平台支撑与治理子系统面向管理员，承担系统运营和治理能力。本文档不把平台后台完整治理链路作为独立业务场景，但其能力会参与退款、评价审核、投诉处理、配置维护和审计追踪。

主要职责：

1. 平台经营总览、用户、商家、门店、商品和订单查询。
2. 评价审核、投诉处理、退款干预和配送异常处理。
3. 会员等级、优惠券模板、公告、平台配置和配送设置维护。
4. 关键平台操作写入审计日志。
5. 为业务场景提供人工干预和治理兜底能力。

支撑用例：UC08、UC09、UC10、UC11、UC12，并作为系统支撑能力存在。

## 3.6 文件、消息与 AI 支撑模块

文件、消息与 AI 是跨业务场景的支撑能力。文件模块负责上传与访问控制；消息模块负责业务事件通知；AI 模块负责业务问答和客服辅助。

| 支撑模块 | 主要职责 | 支撑用例 |
| --- | --- | --- |
| 文件资源模块 | 头像、门店封面、商品图片、评价图片、投诉证据、资质材料上传和访问。 | UC03、UC09、UC10、UC13 |
| 消息通知模块 | 订单状态、配送状态、客服消息、系统公告、优惠券和会员消息。 | UC05、UC11、UC12 |
| AI 辅助模块 | 用户业务问答、订单查询、优惠券查询、客服辅助、降级回复。 | UC11，支撑 UC01、UC03、UC04、UC09、UC10、UC12 |

## 5.1 UC01 用户注册、登录并进入受保护业务

![1-3](https://2bpic.oss-cn-beijing.aliyuncs.com/1-3.png)

`OBJ-SEQ01` 用户注册登录对象级顺序图。

| 项目 | 内容 |
| --- | --- |
| 参与者 | 用户 |
| 触发条件 | 用户打开 APP 并选择注册、密码登录、验证码登录或访问受保护业务。 |
| 前置条件 | 用户端可访问后端认证接口；账号未被禁用。 |
| 关键对象 | `LoginPage`、`AppRouter`、`AuthStorage`、`AuthController`、`AuthService`、`AuthRepository`、`JwtTokenService`、`AccountController`。 |

主成功流程：

1. 用户提交注册或登录信息。
2. 用户端执行基础格式校验。
3. `AuthController` 接收请求并调用 `AuthService`。
4. `AuthService` 查询账号、校验密码或验证码，并检查账号状态。
5. 校验通过后 `JwtTokenService` 生成访问令牌。
6. 用户端通过 `AuthStorage` 保存令牌。
7. 用户访问订单、会员、投诉等受保护业务时，`AppRouter` 检查登录态并允许进入。

备选或异常流程：

1. 账号不存在、密码错误或验证码失效时返回认证失败。
2. 用户未登录访问受保护页面时跳转登录页。
3. Token 过期或角色不匹配时后端返回 401 或 403。

对应代码模块：

- `apps/user_app/lib/features/auth/presentation/login_page.dart`
- `apps/user_app/lib/app/router.dart`

## 6.2 订单状态设计

外卖订单主状态：

```text
待支付 -> 待商家接单 -> 备餐中 -> 待配送 -> 配送中 -> 已送达 -> 已完成
```

非外卖券码订单主状态：

```text
待支付 -> 待使用 -> 已使用 -> 已完成
```

预约类订单主状态：

```text
待支付 -> 待商家确认 -> 已预约 -> 待服务 -> 已完成
```

通用异常状态：

```text
已取消 / 退款中 / 已退款 / 异常
```

状态设计约束：

1. 订单状态变更必须由 `TradeService` 统一校验和写入。
2. 支付成功、商家接单、核销、退款等关键动作必须记录状态日志。
3. 外卖订单进入取消或退款后，配送任务必须同步关闭或终止。
4. 非外卖订单进入退款后，券码或预约记录必须同步置为不可用。
5. 订单列表和订单详情展示状态使用 `DisplayOrderStatus` 统一映射。

## 6.3 投诉状态设计

投诉工单状态：

```text
已提交 -> 已受理 -> 处理中 -> 已解决 -> 已关闭
```

异常约束：

1. 已关闭投诉不能再次受理或处理。
2. 商家只能查看与自身门店相关的投诉。
3. 平台处理动作需要记录处理人、处理时间和处理意见。

## 6.4 优惠券状态设计

优惠券状态：

```text
未使用 -> 已使用
未使用 -> 已过期
已使用 -> 退款释放或保持已使用
```

约束：

1. 优惠券领取校验库存、领取次数、用户资格和有效期。
2. 订单试算和订单创建必须重新校验优惠券，不能只信任前端选择结果。
3. 支付成功后才能最终标记优惠券使用。
4. 退款时按业务规则释放或记录已使用券的处理结果。

1. 开放认证接口允许未登录访问，但注册、验证码、重置密码等提交动作必须校验参数。
2. 用户端接口要求 `USER` 角色，且只能访问本人的资料、订单、优惠券、评价、投诉和客服会话。
3. 商家端接口要求 `MERCHANT` 角色，并校验商家与门店、商品、订单、评价、投诉、客服会话的归属关系。
4. 平台后台接口要求 `ADMIN` 角色。
5. 文件上传按业务类型校验权限，资质材料、投诉证据等敏感资源不得无权限访问。
6. 退款、评价审核、投诉处理、商品上下架等关键动作应保留操作记录或审计记录。

4. 平台后台支撑页面强调查询、筛选、处理记录和审计信息，不承担用户端消费流程。
5. 所有关键动作需要有成功、失败和加载状态反馈。
6. 列表型页面需要支持筛选、刷新或分页，避免一次性加载过多数据。

# 9 异常、安全与性能设计

## 9.1 用例异常处理

| UC | 主要异常 | 处理策略 |
| --- | --- | --- |
| UC01 | 密码错误、验证码失效、Token 过期、角色越权 | 返回明确认证或权限错误，前端引导重新登录。 |
| UC02 | 搜索无结果、定位失败、商家停业、商品下架 | 返回空态、默认推荐或不可购买提示。 |
| UC03 | 地址字段非法、重复收藏、文件上传失败 | 表单提示、幂等处理、保留原头像或原数据。 |
| UC04 | 起送价不足、库存不足、优惠券不可用、重复支付 | 后端重校验，返回业务错误或幂等支付结果。 |
| UC05 | 商家越权、非法状态推进、配送异常 | 拒绝越权和非法流转，异常状态通知用户。 |
| UC06 | 非外卖服务下架、券码生成失败、重复支付 | 阻止购买，支付成功后再出券，重复请求返回幂等结果。 |
| UC07 | 预约资源不可用、券码已核销或过期 | 提示重新选择，拒绝重复或无效核销。 |
| UC08 | 已完成订单退款、重复退款、优惠券释放失败 | 状态校验，事务内处理订单、券码、预约和优惠券状态。 |
| UC09 | 未完成订单评价、重复评价、违规内容 | 拒绝提交或进入平台审核治理流程。 |
| UC10 | 投诉材料缺失、非相关商家查看、重复关闭 | 表单校验、权限校验、状态机保护。 |
| UC11 | AI 不可用、会话已关闭、非相关商家回复 | AI 降级为规则回复，关闭会话禁止继续普通回复。 |
| UC12 | 优惠券库存不足、领取次数超限、下单门槛不足 | 领取和使用阶段均重新校验。 |
| UC13 | 非所属商品编辑、价格库存非法、下架商品被购买 | 权限校验、参数校验、订单创建时重新校验商品状态。 |

## 9.2 安全设计

1. 用户、商家、管理员使用独立角色边界，所有受保护接口统一经过 JWT 认证过滤器。
2. 商家侧数据必须校验门店或商家主体归属，禁止跨商家读取订单、投诉、客服和商品数据。
3. 用户敏感信息在商家侧按最小必要原则展示，地址和手机号只在履约需要时展示。
4. 订单金额、优惠券抵扣和支付状态以后端计算和状态为准，前端只展示结果。
5. 上传文件限制业务类型、大小和格式，文件记录必须带上传人和业务归属。
6. 平台处理评价、投诉、退款等动作时记录审计信息。

## 9.3 性能设计

1. 首页、搜索、订单、评价、投诉、客服等列表接口使用分页。
2. 首页、商家详情、订单详情采用聚合响应，减少移动端多次请求。
3. 高频查询字段建立索引，包括账号、用户、商家、门店、订单号、业务类型、状态、创建时间。
4. 优惠券领取、订单支付、退款和核销使用事务与状态校验保障一致性。
5. AI 回复、消息生成、统计汇总等非核心能力可异步或降级处理，不阻断交易主流程。
6. 微服务拆分后，跨服务查询优先通过接口获取快照数据，避免跨服务直接联表。
