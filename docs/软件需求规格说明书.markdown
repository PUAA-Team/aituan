### 1.2 系统概述

爱团本地生活服务综合平台面向本地生活消费场景建设，业务范围覆盖外卖订餐、到店团购、酒店民宿、休闲娱乐、电影演出、丽人医美、景点门票、足疗按摩等服务类型，并支持在线下单、支付模拟、评价互动、商家经营管理和平台运营管理等活动。

系统遵循移动消费优先原则，以 Android、iOS 用户端作为主要消费入口，以商家端和平台管理后台作为经营与治理入口，以后端服务系统作为统一业务支撑中心，以配送模拟服务作为外卖履约支撑模块，以 AI Agent 与 Skills 层作为智能辅助扩展能力层。

系统建设目标是形成用户消费闭环、商家经营闭环和平台治理闭环，重点保障商家信息准确性、配送时效展示稳定性、预约履约可靠性和用户评价真实性。系统整体产品形态和业务组织方式参考美团、饿了么、淘宝闪购、大众点评等本地生活平台。

### 1.3 文档概述

本文档用于规定爱团本地生活服务综合平台的软件需求，作为后续系统设计、详细设计、编码实现、测试验证、部署交付和版本验收的依据。

本文档内容包括系统范围、引用文件、总体需求、能力需求、接口需求、数据需求、非功能需求、优先级、合格性规定、需求可追踪性、尚未解决的问题和附录说明。

### 1.4 基线

本项目当前需求基线如下：

1. 用户端以 Android、iOS 为优先实现终端。
2. 商家端和平台管理后台采用 Web 形态实现。
3. 后端采用 Spring Boot 技术体系，关系型数据库采用 MySQL。
5. 外卖履约采用后端配送模拟机制，不设置独立骑手端。
6. P0 核心功能应满足可演示、可测试、可追踪要求。
7. 当前版本优先覆盖基础消费交易、商家处理、平台审核与配送模拟闭环。

## 3 需求

### 3.1 所需的状态和方式

爱团本地生活服务综合平台在当前阶段应支持以下状态和运行方式：

1. 软件应支持开发调试、联调测试、集成测试、演示试运行和正式运行等基本状态。
2. 用户端应以移动端方式提供访问，满足高频、碎片化的本地生活消费场景。
3. 商家端应以 Web 方式提供访问，满足门店经营、商品维护、订单处理和数据查看等操作需求。
4. 平台管理后台应以 Web 方式提供访问，满足商家审核、内容治理、平台配置和运营管理需求。
5. 后端服务系统应统一承载核心业务处理、状态流转、接口服务、数据存储和日志审计能力。
6. 支付环节应采用模拟支付方式，仅负责推动业务状态和记录支付结果，不承载真实资金流转和清结算处理。
7. 配送环节应采用后端模拟配送方式，通过规则、定时任务和后台触发推进状态流转，不设置独立骑手应用。
8. AI Agent 与 Skills 层应作为平台增强能力接入，在不改变核心业务边界的前提下，为用户服务、商家经营和平台运营提供智能辅助能力。

### 3.2 需求概述

#### 3.2.1 目标

本系统的建设目标如下：

1. 建设统一的本地生活综合服务平台，形成覆盖吃、喝、玩、乐、购、服务的基本业务闭环。
2. 支撑用户消费闭环、商家经营闭环和平台治理闭环，建立多角色统一承载能力。
3. 支持外卖到餐、到店团购、酒店民宿、休闲娱乐、电影演出、丽人医美、景点门票、上门按摩和会员体系等业务方向的扩展。
4. 优先完成 P0 核心能力，使系统具备可演示、可测试、可追踪的交付特性。
5. 在满足当前版本交付目标的前提下，为后续接入更复杂营销、更多终端和更多 AI 能力预留扩展空间。

#### 3.2.2 运行环境

1. 用户端运行于 Android、iOS 智能移动终端环境。
2. 商家端和平台管理后台运行于主流桌面浏览器环境。
3. 后端服务系统基于 Spring Boot 技术体系构建，并通过标准网络接口向前端提供服务。
4. 业务核心数据存储于 MySQL 关系型数据库。
5. 配送模拟服务与后端服务系统协同运行，通过统一业务数据和状态机制完成外卖履约仿真。
6. AI Agent 与 Skills 层依附于平台业务体系运行，面向既有业务对象和业务上下文提供辅助处理能力。

#### 3.2.3 用户的特点

1. 普通用户以移动端使用为主，操作时间碎片化，对搜索效率、下单流程顺畅性、订单状态可见性和评价反馈及时性要求较高。
2. 商家用户以门店经营人员和运营人员为主，主要通过 Web 端维护门店资料、商品或服务信息、处理订单和查看经营数据。
3. 平台管理员和运营人员主要通过 Web 后台进行商家审核、内容治理、平台配置、活动运营和数据查看，重视规则一致性、异常可追踪性和管理效率。
4. AI 辅助使用者包括普通用户、商家和平台运营人员，对自然语言理解、建议有效性和结果可解释性有较高要求。

#### 3.2.4 关键点

本系统需求的关键点如下：

1. 建立完整的用户消费闭环，包括浏览、搜索、下单、支付模拟、履约查看和评价互动。
2. 建立商家经营闭环，包括入驻、门店维护、商品或服务维护、订单处理、营销配置和数据查看。
3. 建立平台治理闭环，包括商家审核、评价审核、投诉处理、类目与推荐配置、运营看板和日志审计。
4. 外卖类订单应具备清晰、稳定、可追踪的配送模拟状态流转能力。
5. 到店和预约类服务应具备券码、场次、日期、预约时段、核销和退款等差异化规则。
6. 评价系统应保证评价与真实已完成订单的关联关系，支持平台治理和商家回复。
7. AI Agent 与 Skills 层应支持用户辅助搜索、推荐解释、商家文案生成和平台运营辅助，并具备可降级能力。

#### 3.2.5 约束条件

1. 用户侧以 Android、iOS 为优先建设对象，当前阶段不以桌面消费端为重点。
2. 商家端与平台管理后台采用 Web 形态建设。
3. 后端服务系统采用 Spring Boot 技术体系，核心关系型数据存储采用 MySQL。
4. 支付环节仅采用模拟支付机制，不涉及真实支付通道接入、真实分账和真实财务清结算。
5. 履约环节采用后端模拟配送机制，不建设独立骑手应用和运力调度系统。
6. 当前版本以 P0 核心功能为优先交付范围，增强能力和扩展能力按优先级增量实现。
7. 外部地图、消息、AI 等服务可根据实际条件接入，外部服务不可用时应支持本地模拟或规则降级。

### 3.3 需求规格

#### 3.3.1 软件系统总体功能/对象结构

爱团本地生活服务综合平台的软件总体结构由用户端、商家端、平台管理后台、后端服务系统、配送模拟服务、AI Agent 与 Skills 层六个部分构成，各部分通过统一业务对象和统一状态机制形成协同关系。

系统总体结构如下：

```text
爱团本地生活服务综合平台
├─ 用户端
│  ├─ Android APP
│  └─ iOS APP
├─ 商家端
│  └─ 商家 Web 管理端
├─ 平台管理后台
│  └─ 平台 Web 管理后台
├─ 后端服务系统
│  ├─ 用户服务
│  ├─ 商家服务
│  ├─ 商品与服务服务
│  ├─ 订单服务
│  ├─ 支付模拟服务
│  ├─ 配送模拟服务
│  ├─ 评价与客服服务
│  ├─ 营销与会员服务
│  └─ 权限与日志服务
└─ AI Agent 与 Skills 层
   ├─ 智能搜索
   ├─ 智能推荐
   ├─ 智能客服
   ├─ 智能运营助手
   └─ 技能治理与调用记录
```

系统围绕以下核心业务对象组织：用户、商家、门店、商品与服务、订单、预约、支付记录、评价、配送任务、平台规则、活动配置、消息通知和 AI 调用记录。

#### 3.3.2 软件子系统功能/对象结构

1. 用户端  
   用户端是面向消费者的移动应用子系统，负责承载首页浏览、搜索与筛选、商家详情、购物车、结算、下单、支付模拟、订单查看、配送进度查看、评价互动、会员与个人中心等场景。其主要对象包括用户账户、地址、收藏、优惠券、会员信息、商品或服务、订单、评价和消息。

2. 商家端  
   商家端是面向商家经营人员的 Web 子系统，负责承载商家入驻、资质提交、门店资料维护、商品与服务维护、订单与预约处理、用户咨询处理、退款审核、营销配置和经营数据查看等场景。其主要对象包括商家主体、门店信息、商品与服务目录、库存或可预约资源、订单、评价回复和经营统计数据。

3. 平台管理后台  
   平台管理后台是面向平台运营与治理人员的 Web 子系统，负责承载商家审核、评价审核、投诉处理、类目与标签管理、Banner 和推荐位配置、平台参数管理、数据看板和日志审计等场景。其主要对象包括平台角色权限、审核对象、运营配置、统计指标和审计记录。

4. 后端服务系统  
   后端服务系统是平台统一业务支撑子系统，负责维护核心业务对象、统一状态流转、接口服务、数据存储和日志能力。其主要对象包括用户、商家、门店、商品与服务、订单、预约、支付记录、评价记录、配送任务、活动规则和配置参数。

5. 配送模拟服务  
   配送模拟服务是面向外卖履约表达的支撑子系统，负责在后端内部完成配送任务生成、配送状态推进、预计送达时间计算和配送过程仿真。该子系统不面向独立骑手应用提供业务边界。

6. AI Agent 与 Skills 层  
   AI Agent 与 Skills 层是平台智能辅助子系统，负责围绕既有业务对象提供语义理解、搜索增强、推荐解释、商家内容生成、运营建议和统一技能治理能力。该层依附于平台业务体系运行，不独立构成核心交易闭环。

### 3.4 CSCI能力需求

#### 3.4.1 用户账户与个人中心能力

**能力描述**  
系统应提供用户账户注册、登录、身份保持及个人中心展示能力，支持用户维护基础资料、收货地址、收藏、优惠券、会员信息、烟火值及历史订单等个人消费相关信息。

**主要输入**

- 用户邮箱（手机号）、验证码、密码或第三方登录标识
- 用户昵称、头像、性别等基础资料信息
- 收货地址信息，包括联系人、手机号、详细地址、门牌号和默认地址标记
- 收藏、优惠券领取与使用请求
- 会员信息、烟火值及历史订单查询请求

**处理要求**

1. 系统应支持用户完成注册、登录、退出登录及登录态校验。
2. 系统应支持用户查看并修改个人基础资料。
3. 系统应支持新增、编辑、删除、设为默认及查询收货地址，并在下单流程中优先使用默认地址。
4. 系统应支持展示用户收藏的商家、商品或服务项目，并支持取消收藏。
5. 系统应支持展示用户可用、已使用和已失效的优惠券信息。
6. 系统应支持展示会员等级、烟火值、权益说明和历史订单摘要信息。

**输出结果**

- 注册、登录和退出结果
- 用户资料与个人中心汇总信息
- 地址列表及地址操作结果
- 收藏列表、优惠券列表、会员信息和订单列表

**异常处理**

1. 当邮箱或手机号格式错误、验证码失效、密码错误或账户异常时，应拒绝登录并返回明确提示。
2. 当用户未登录或登录态失效时，应提示重新登录。
3. 当地址信息缺失或不合法时，应阻止保存并提示修正。
4. 当订单记录为空时，应返回空列表及引导性提示。

**性能要求**

1. 登录、个人资料查询、地址查询等常用接口在本地部署环境下平均响应时间宜不大于 1 s。
2. 个人中心首页主要内容在正常网络条件下应于 3 s 内完成展示。

#### 3.4.2 商家搜索、推荐与浏览能力

**能力描述**  
系统应提供面向本地生活服务的搜索、推荐与浏览能力，支持用户在外卖到餐、到店团购、酒店民宿、休闲娱乐、电影演出、丽人医美、景点门票、上门按摩等业务范围内进行服务发现与比较。

**主要输入**

- 搜索关键词
- 分类、区域、当前位置及距离范围
- 评分、销量、价格、标签、营业状态等筛选条件
- 综合排序、距离排序、评分排序、销量排序、价格排序等排序条件
- 首页推荐、活动专区、分类入口、猜你喜欢和附近推荐访问请求

**处理要求**

1. 系统应支持基于关键词的商家、商品或服务项目搜索。
2. 系统应支持按分类、位置距离、评分、销量、价格区间、标签及营业状态进行组合筛选。
3. 系统应支持按多种排序规则返回搜索结果，并保证结果字段完整、排序逻辑一致。
4. 系统应支持首页推荐内容展示，包括 Banner、活动专区、分类入口、猜你喜欢及附近商家等模块。
5. 系统应支持结果列表分页加载，展示名称、封面图、评分、销量、距离、人均或起送信息、标签及营业状态等内容。
6. 系统应在个性化数据不足时提供通用推荐结果。

**输出结果**

- 搜索结果列表
- 筛选和排序后的商家或服务项目列表
- 首页推荐内容集合
- 空结果提示及补充推荐内容

**异常处理**

1. 当位置权限未授权或定位失败时，应提示用户授权或手动选择位置，并可返回非距离优先结果。
2. 当筛选条件冲突或超出有效范围时，应提示用户调整条件。
3. 当无匹配结果时，应返回空列表并提供重置筛选或浏览推荐的引导。
4. 当推荐数据暂不可用时，应降级展示基础分类内容和默认推荐列表。

**性能要求**

1. 搜索、筛选、排序等常用查询接口在本地部署环境下平均响应时间宜不大于 1 s。
2. 首页主要推荐内容在正常网络条件下应于 3 s 内完成首屏展示。

#### 3.4.3 商家详情与服务展示能力

**能力描述**  
系统应提供商家详情与服务展示能力，帮助用户在消费决策前获取商家基础信息、服务内容、价格信息及可消费条件。

**主要输入**

- 商家标识、服务项目标识或商品标识
- 用户当前位置或已选收货地址
- 用户查看图文、套餐、票券、房型、服务说明等详情请求

**处理要求**

1. 系统应展示商家基础信息，包括名称、封面图、图集、营业时间、联系电话、地址位置、标签、评分及评价摘要。
2. 系统应展示与用户决策直接相关的服务信息，包括名称、价格、原价、销量、使用规则、适用时间、退款说明及库存状态。
3. 外卖业务应展示配送范围、起送门槛、预计送达时间和配送费用说明。
4. 到店团购应展示使用条件、有效期和核销说明。
5. 酒店民宿应展示房型、入住离店时间和基础设施摘要。
6. 休闲娱乐、丽人医美、景点门票、上门按摩等业务应展示服务流程或注意事项摘要。
7. 系统应支持展示商家位置及地图入口，并支持收藏、加入购物车和发起下单等消费动作。

**输出结果**

- 商家详情页信息
- 商品、套餐、票券、房型或服务详情信息
- 价格、规则、营业信息和地图入口

**异常处理**

1. 当商家不存在、已下架、暂停营业或超出服务区域时，应返回状态提示并限制不可执行的消费操作。
2. 当服务项目库存不足、已售罄、已过期或当前不可预约时，应明确提示并更新可购状态。
3. 当详情数据加载失败时，应支持重试，并避免展示错误价格或错误规则信息。

**性能要求**

1. 商家详情和服务详情等常用查询接口在本地部署环境下平均响应时间宜不大于 1 s。
2. 详情页核心信息在正常网络条件下应于 3 s 内完成主要内容展示。

#### 3.4.4 购物车、下单与支付能力

**能力描述**  
系统应提供订单确认、优惠结算、订单提交及支付模拟能力，支持用户完成消费侧交易闭环。支付过程为模拟支付，不涉及真实资金清结算。

**主要输入**

- 加入订单的商品、套餐、票券、房型或服务项目
- 商品数量、规格、预约信息、入住日期、场次信息或备注信息
- 收货地址、联系人信息或预约联系人信息
- 优惠券、平台优惠、会员优惠等结算信息
- 订单提交请求与支付确认请求

**处理要求**

1. 系统应支持用户新增、修改、删除订单条目，并实时更新数量、金额及适用优惠。
2. 系统应在下单确认阶段展示商品明细、原始金额、优惠抵扣、配送费、服务费和实付金额。
3. 系统应支持用户选择或切换优惠券，并依据适用范围、门槛、有效期和互斥规则完成校验。
4. 系统应根据业务类型收集必要下单信息。外卖业务应校验收货地址与配送可达性；到店团购应校验购买数量与使用限制；酒店民宿应校验入住离店日期与房态；上门服务应校验服务地址与预约时段。
5. 系统应在用户确认订单后生成订单记录，并进入待支付或已支付等相应状态。
6. 系统应提供模拟支付能力，支持用户发起支付、接收支付结果并查看支付凭证摘要。
7. 系统应具备幂等控制能力，避免重复提交产生重复订单。

**输出结果**

- 订单列表与金额汇总结果
- 订单确认页结算结果
- 优惠使用结果与实付金额
- 订单编号、订单状态和模拟支付结果

**异常处理**

1. 当商品失效、价格变更、库存不足、房态变化或预约资源不可用时，应阻止下单并提示用户刷新确认。
2. 当优惠券不满足门槛、已失效、已被使用或与其他优惠互斥时，应取消该优惠并提示原因。
3. 当地址缺失、配送不可达、联系人信息不完整或必要预约信息缺失时，应拒绝提交订单。
4. 当支付模拟超时、失败或状态未知时，应允许用户重新查询订单状态或重新发起支付。

**性能要求**

1. 订单查询、订单确认、优惠试算等常用接口在本地部署环境下平均响应时间宜不大于 1 s。
2. 订单提交后的结果反馈应在正常条件下于 3 s 内返回。
3. 模拟支付结果反馈应在正常条件下于 5 s 内返回并更新订单状态。

#### 3.4.5 外卖配送模拟与订单跟踪能力

**能力描述**  
系统应提供外卖订单配送过程的模拟展示与跟踪能力，支持用户查看订单状态、预计送达时间、配送阶段和时间线进度。系统不提供独立骑手端应用，配送过程由后台模拟机制与管理触发规则驱动。

**主要输入**

- 外卖订单标识
- 用户查看订单详情、配送进度及时间线请求
- 后台模拟生成的配送节点、模拟位置、预计送达时间及状态变更数据

**处理要求**

1. 系统应向用户展示外卖订单从待接单、已接单、备餐中、待配送、配送中、已送达、已完成等状态的可视化进度。
2. 系统应展示订单时间线，包括下单、支付成功、商家备餐、开始配送、送达等关键节点及时间戳。
3. 系统应展示预计送达时间，并在状态变化时同步刷新。
4. 系统可采用地图模式展示商家位置、收货位置和模拟配送位置，也可退化为阶段时间线展示。
5. 系统应依据后台模拟规则更新配送状态与轨迹数据，并保证用户侧展示与订单当前状态一致。
6. 当订单尚未进入配送阶段时，系统应展示当前等待节点及预计后续状态。

**输出结果**

- 订单当前状态
- 配送时间线与关键节点信息
- 预计送达时间
- 模拟配送展示结果

**异常处理**

1. 当订单非外卖类型时，应隐藏配送进度与地图展示能力。
2. 当配送数据尚未生成时，应展示等待提示及当前订单进度。
3. 当模拟数据缺失、刷新失败或位置点异常时，应保留最近一次有效状态并提示稍后重试。
4. 当订单已取消、退款中或已退款时，应停止配送进度展示并返回相应状态说明。
5. 当地图资源不可用时，应降级展示文字时间线与预计送达时间。

**性能要求**

1. 订单状态、时间线及配送信息查询接口在本地部署环境下平均响应时间宜不大于 1 s。
2. 订单详情页中的配送核心信息在正常网络条件下应于 3 s 内完成展示。

#### 3.4.6 到店团购与预约服务能力

**能力描述**  
平台应支持非外卖履约场景的本地生活交易服务，覆盖到店团购、酒店民宿、休闲娱乐、电影演出、丽人医美、景点门票及上门按摩预约等业务类型，实现商品或服务展示、购买、预约、核销、使用、退款及订单状态流转闭环。

**主要输入**

- 用户提交的商品或服务选择信息，包括门店、规格、使用日期、场次、人数、预约时段等
- 用户身份信息、联系人信息及预约备注信息
- 商家配置的库存、价格、可预约资源、适用规则、有效期、退改规则和核销规则
- 支付结果、核销结果和退款申请信息

**处理要求**

1. 券码核销类业务应支持团购券、票券生成、券码展示、核销校验和未核销退款处理。
2. 日期或场次约束类业务应支持酒店民宿、电影演出、景点门票等场景的日期、场次、房型或票种资源管理。
3. 预约类业务应支持上门按摩、丽人医美、休闲娱乐等场景的预约时间冲突检测、资源占用控制和预约变更处理。
4. 平台应支持待支付、待确认、待使用、已使用、已完成、已取消、退款中、已退款等状态管理。
5. 平台应支持商家或核销终端对券码、预约码或订单凭证进行校验，防止重复核销和失效核销。
6. 平台应支持按业务规则执行未使用退款、超时自动关闭和过期失效处理。
7. 平台应记录下单、支付、预约、核销、改期和退款等关键业务日志。

**输出结果**

- 订单、券码或预约凭证
- 订单状态、使用规则和预约确认结果
- 核销结果和退款处理结果

**异常处理**

1. 当库存不足、场次不可用、预约时间冲突、价格失效或商品下架时，应中止交易并提示用户重新选择。
2. 当券码生成失败、核销失败或退款失败时，应保持订单状态一致，并支持补偿处理或人工介入。
3. 当出现重复提交、网络中断或超时情况时，应具备幂等控制能力，避免重复扣减库存或重复创建订单。
4. 当商家暂停营业、服务不可约或超出服务范围时，应阻止继续下单或预约。

**性能要求**

1. 普通查询类操作在常规负载下页面响应时间宜不超过 3 s。
2. 下单、预约确认、券码生成等关键交易操作在常规负载下处理时间宜不超过 5 s。
3. 核销结果反馈在网络正常条件下宜不超过 3 s。

#### 3.4.7 评价互动与商家客服能力

**能力描述**  
平台应支持基于真实交易的评价互动能力，以及用户与商家之间的咨询和客服会话能力，形成从订单完成后评价到商家回复、平台治理的闭环机制。

**主要输入**

- 已完成订单信息及其关联用户、商家、商品或服务信息
- 用户提交的评分、文字评价、图片内容、点赞、有用投票和举报信息
- 商家提交的评价回复内容和客服回复内容
- 平台审核规则、敏感词规则和内容治理规则

**处理要求**

1. 平台仅允许已完成订单的用户发起评价，并应建立订单与评价的关联关系。
2. 平台应支持用户对评价进行点赞、有用投票和举报，并对重复操作进行限制。
3. 平台应支持商家对评价进行公开回复，并保留回复时间和回复记录。
4. 平台可支持商家客服获取 AI 回复建议，但建议结果需经人工确认后发送。该能力的治理、日志和降级要求由 3.4.10 统一规定。
5. 平台应支持对评价内容、商家回复内容和咨询内容进行审核、屏蔽、下架或人工复核处理。

**输出结果**

- 评价发布结果、互动结果和举报受理结果
- 咨询回复结果和会话记录
- 待审核评价和待处理咨询清单

**异常处理**

1. 当订单未完成、订单不存在或评价资格不满足时，应禁止提交评价并提示原因。
2. 当评价内容、回复内容或咨询内容违反平台规则时，应拒绝发布、进入审核或执行屏蔽处理。
3. 当出现重复评价、重复点赞或恶意刷评行为时，应进行拦截、限流或标记。

**性能要求**

1. 评价提交、商家回复和咨询发送等交互操作在常规负载下响应时间宜不超过 3 s。
2. 新产生的评价、回复及会话消息在正常条件下宜于 1 min 内可见。

#### 3.4.8 商家经营管理能力

**能力描述**  
平台应提供商家侧 Web 经营管理能力，支持商家完成入驻、资质提交、门店维护、商品或服务管理、订单处理、退款审核、营销配置和经营数据查看等日常经营活动。

**主要输入**

- 商家注册信息、主体信息、经营资质和联系人信息
- 门店基础信息、营业时间、联系方式、服务范围和门店图片
- 商品或服务信息，包括类目、标题、价格、库存、预约规则、使用规则和上下架状态
- 订单处理动作、退款审核结果、营销活动配置参数和统计查询条件

**处理要求**

1. 商家端应支持商家申请入驻、提交资质材料、查看审核状态及补充更新资质信息。
2. 应支持商家维护门店信息、营业状态、服务说明和图文详情。
3. 应支持商家创建、编辑、上下架商品或服务，并按业务类型维护库存、场次、预约资源和价格规则。
4. 应支持商家查看订单详情、核销状态、预约安排和用户备注，并处理接单、确认、拒单、改期、核销和售后沟通等操作。
5. 应支持商家对符合规则的退款申请进行审核，并将审核结果同步至订单状态流转。
6. 应支持商家配置营销活动信息，包括优惠标签、套餐说明和活动文案。
7. 应支持商家查看营业额、订单量、退款量、评价情况和热销商品等统计信息。

**输出结果**

- 商家入驻申请和资质状态
- 门店档案、商品或服务档案和订单处理结果
- 经营看板、订单统计和评价统计结果

**异常处理**

1. 当资质材料缺失、格式不合法或有效期失效时，应阻止提交或要求重新补充。
2. 当商品信息不完整、价格或库存配置异常、预约规则冲突时，应禁止发布并提示修正。
3. 当商家处理退款、改期或上下架操作与当前订单状态冲突时，应拒绝执行并保持数据一致。
4. 当商家账号权限不足或会话失效时，应拒绝相应操作并提示重新认证。

**性能要求**

1. 商家端主要列表和详情页面响应时间宜不超过 3 s。
2. 商品发布、订单处理和退款审核等关键操作处理时间宜不超过 5 s。

#### 3.4.9 平台管理与运营能力

**能力描述**  
平台应提供平台侧 Web 管理与运营能力，支持商家审核、评价审核、投诉处理、类目与内容配置、推荐与活动配置、数据看板、平台参数管理及审计追踪，保障平台有序运营。

**主要输入**

- 商家入驻申请、资质材料和门店变更申请
- 用户评价、商家回复、举报记录、投诉工单和申诉材料
- 类目、标签、Banner、推荐位、专题活动和平台参数配置数据
- 统计分析条件和审核规则配置

**处理要求**

1. 平台管理后台应支持商家入驻审核、资质复核、门店状态管理和违规商家处置。
2. 应支持对评价内容、商家回复内容和举报内容进行审核、屏蔽、删除和申诉复核处理。
3. 应支持用户投诉、售后争议和内容举报等工单的受理、分派、跟踪与结案。
4. 应支持维护业务类目、服务标签、首页 Banner、推荐位、榜单和活动配置。
5. 应支持查看平台关键经营数据，包括商家数量、订单量、交易趋势、退款率、评价分布和投诉量等。
6. 应支持平台基础参数、审核阈值、角色权限和业务开关配置。
7. 应对审核、封禁、配置变更和参数调整等关键管理动作记录审计日志。

**输出结果**

- 审核结论、投诉处理结果和运营配置结果
- 统计报表、可视化看板和待办任务队列
- 审计记录和异常追踪结果

**异常处理**

1. 当审核材料不完整、证据不足或规则命中冲突时，应支持退回补充、人工复核或暂缓处理。
2. 当运营配置数据存在冲突、缺失或超出生效范围时，应拒绝发布并提示修正。
3. 当投诉处理超时、流程中断或角色权限不足时，应记录异常并支持转派或升级处理。
4. 当关键操作失败时，应保证平台配置一致性，避免部分生效。

**性能要求**

1. 平台管理后台常用管理页面和列表查询响应时间宜不超过 3 s。
2. 审核提交、配置发布和投诉流转等关键操作处理时间宜不超过 5 s。
3. 近实时运营指标延迟宜不超过 10 min。

#### 3.4.10 AI Agent 与 Skills 能力

**能力描述**  
平台应具备 AI Agent 与 Skills 能力，为用户、商家及平台运营提供智能辅助服务。该能力应覆盖用户侧生活需求理解与规划、智能搜索解析、推荐解释、商家经营辅助、平台运营辅助、技能治理、调用日志记录及外部 AI 服务异常时的降级保障。

**主要输入**

- 用户自然语言请求及上下文信息，包括位置、时间、预算、偏好和历史行为
- 商家侧输入的商品或服务基础信息、活动主题和经营目标
- 平台侧输入的推荐场景、热点主题、规则约束和待生成内容参数
- Skills 配置、提示模板、调用策略、权限策略和内容安全规则

**处理要求**

1. AI Agent 应能够解析用户自然语言意图，提取预算、人数、位置、品类、时间等约束条件，并转化为可执行的查询或推荐任务。
2. 平台应支持将智能搜索、推荐解释、客服辅助、商品描述生成、标签生成和活动文案生成等能力封装为 Skills。
3. AI 输出应以辅助建议形式提供，不得绕过商家和平台既有业务规则直接完成交易性确认操作。
4. 平台应建立 Skills 的注册、启停、版本、权限、适用范围和调用频率治理机制。
5. 平台应记录 AI Agent 与 Skills 的调用日志，包括调用时间、调用方、输入摘要、输出摘要、耗时、状态和降级信息。
6. 当外部 AI 服务不可用、超时或返回异常时，系统应降级到规则引擎、模板回复或模拟结果，不得阻断 P0 核心业务流程。
7. 对涉及违规、敏感或不确定内容的生成结果，应支持拦截、复核或提示用户调整请求。

**输出结果**

- 搜索解析结果、生活方案建议、推荐列表和推荐解释
- 商品描述、标签建议、营销文案等可编辑内容
- 技能调用结果、执行状态、错误信息和降级执行结果

**异常处理**

1. 当用户请求语义不完整、约束冲突或无法识别时，应提示补充条件或返回可选建议。
2. 当外部 AI 服务超时、失败或不可达时，应自动执行降级策略，并记录异常原因与降级结果。
3. 当生成内容命中敏感规则、存在明显事实错误或超出业务边界时，应拒绝直接输出并返回安全提示。
4. 当 Skills 调用权限不足、配置错误或版本不可用时，应阻止调用并记录治理日志。

**性能要求**

1. 智能搜索解析、推荐解释和文案生成等单次 AI 辅助请求在服务可用情况下响应时间宜不超过 8 s。
2. 降级到规则或模板方案后的响应时间宜不超过 3 s。
3. Skills 调用日志应在调用完成后 1 min 内可查询。

### 3.5 外部接口需求

#### 3.5.1 接口标识与分类

| 接口标识 | 接口类别 | 主要用途 | 接入方式 | 是否核心依赖 | 备注 |
| --- | --- | --- | --- | --- | --- |
| EI-01 | 地图与位置服务接口 | 地址解析、经纬度转换、距离估算、范围检索 | HTTP/HTTPS API | 否 | 可采用第三方服务或本地模拟 |
| EI-02 | 邮箱或短信验证码接口 | 注册、登录、敏感操作校验 | HTTP/HTTPS API | 是 | 应支持开发环境模拟发送 |
| EI-03 | 支付模拟接口 | 订单支付状态流转演示 | HTTP/HTTPS API 或本地模拟 | 是 | 不接入真实资金清算 |
| EI-04 | AI 模型服务接口 | 智能问答、推荐辅助、内容生成辅助 | HTTP/HTTPS API | 否 | 外部不可用时降级为规则或模拟数据 |
| EI-05 | 图片与对象存储接口 | 商户图片、商品图片、评价图片等资源存储 | SDK 或 HTTP/HTTPS API | 是 | 可采用本地文件存储作为替代 |
| EI-06 | 消息与通知接口 | 短信、站内消息、邮件或推送通知 | HTTP/HTTPS API | 否 | 首期可仅实现站内消息 |

#### 3.5.2 第三方接口说明

1. 地图与位置服务接口应支持地址检索、坐标解析、商户与用户距离估算、配送范围判断等功能。地图服务故障时，不应阻断已录入地址订单的基础提交流程，但应提示定位能力受限。
2. 短信验证码接口应支持验证码发送、有效期控制、发送频率限制和校验结果反馈。开发与测试环境可使用固定验证码或控制台输出方式模拟。
3. 支付模拟接口用于模拟待支付、支付中、支付成功、支付失败、超时取消等状态，不产生真实扣款与结算。
4. AI 模型服务接口用于支持智能搜索、推荐辅助、客服辅助和文案生成等非强依赖功能。外部 AI 服务不可用时，应自动切换至规则引擎、预生成模板或模拟响应。
5. 图片与对象存储接口用于上传、访问和删除商家、商品和评价图片资源，应支持文件类型校验、大小限制和访问权限控制。
6. 消息与通知接口用于订单状态提醒、审核结果通知和系统公告投递。首期允许以站内消息为主，短信、邮件或移动推送作为可选增强能力。

### 3.6 内部接口需求

1. 后端接口应采用 RESTful 风格，使用 HTTP/HTTPS 协议进行访问。
2. 请求与响应默认采用 JSON 格式，时间字段应统一使用标准时间表示方式，金额字段应使用统一精度规则。
3. 用户端、商家端和平台管理后台应采用统一认证机制。登录成功后应签发访问令牌，服务端应校验令牌合法性、有效期和角色权限。
4. 所有内部接口应返回统一响应结构，至少包含业务状态码、消息说明、数据体、时间戳和请求标识。
5. 创建订单、支付回调、商家接单、审核处理等接口应具备幂等控制能力。
6. 列表接口应统一支持分页、排序和条件筛选。
7. 用户服务、商家服务、商品服务、订单服务、支付模拟服务、评价服务、通知服务和权限服务之间应通过清晰的服务边界进行协同，不得绕过服务层直接访问他方业务边界。
8. 内部接口应记录请求标识、调用时间、调用方身份、关键参数摘要、处理结果和耗时。涉及审核、订单状态流转、权限变更和数据删除等操作应保留完整审计记录。
9. 当内部依赖服务异常时，调用方应接收可识别的错误码和降级提示。非核心能力失败时，应尽量维持核心业务继续执行。

### 3.7 内部数据需求

1. 用户数据域  
   应包括用户基础档案、登录账号、手机号、密码摘要、头像、昵称、地址、账号状态、注册来源、最近登录信息和隐私授权状态等数据。

2. 商户数据域  
   应包括商户基础信息、门店名称、营业分类、联系人、联系电话、营业时间、门店地址、地理坐标、资质材料、审核状态、上下线状态和评分统计等数据。

3. 商品与服务数据域  
   应包括商品或服务名称、分类、价格、库存状态、图片资源、规格选项、上下架状态、排序权重、销售统计、标签和描述信息等数据。

4. 购物车数据域  
   应包括用户标识、商户标识、购物项列表、规格组合、数量、小计金额、失效标记和更新时间等数据。购物车应支持同一用户在不同商户下分组存储。

5. 订单数据域  
   应包括订单主信息、订单编号、用户标识、商户标识、配送地址、下单时间、应付金额、优惠金额、支付状态、履约状态、完成状态、关闭原因和备注信息等。订单明细应包括商品快照、数量、成交单价、规格信息和评价状态等数据。

6. 支付模拟数据域  
   应包括支付单号、关联订单号、支付渠道标识、发起时间、回调结果、回调次数、支付状态、失败原因和模拟模式等数据，并与订单状态数据关联。

7. 配送模拟数据域  
   应包括配送任务编号、关联订单号、任务创建时间、配送阶段、预计送达时间、模拟位置或阶段节点、异常标记和完成时间等数据。配送实体可采用系统虚拟配送对象建模。

8. 评价与互动数据域  
   应包括评价编号、订单号、用户标识、商户标识、评分、文字内容、图片列表、评价时间、匿名标记、审核状态、是否追评和商户回复内容等数据。评价应与已完成订单建立强关联。

9. 客服与消息数据域  
   应包括会话编号、会话参与方、消息内容、消息类型、发送时间、已读状态、关联订单号、处理状态和消息来源等数据。

10. 会员与营销数据域  
    应包括烟火值变动记录、会员等级、等级权益、优惠券模板、优惠券实例、活动规则、推荐位配置和榜单配置等数据。

11. 审核与运营数据域  
    应包括商户入驻审核记录、评价审核记录、举报记录、投诉工单、处理动作、处理人、处理时间、审核意见和前后状态变更记录等数据。

12. 系统与权限数据域  
    应包括角色、权限点、账号、菜单授权、操作日志、登录日志、异常日志、配置参数、字典数据、黑名单和限流策略等数据。

13. AI 调用数据域  
    应包括调用方、请求摘要、结果摘要、耗时、状态、技能名称、降级标记和审计记录等数据，用于统计、排障和治理。

14. 数据完整性要求  
    关键主数据应具有唯一标识。订单、支付、审核、评价等关键表应建立必要的关联约束和状态约束。删除操作原则上采用逻辑删除，并保留更新时间和操作人信息。

### 3.9 需求优先级

#### 3.9.1 P0 核心需求

P0 为本期必须实现并通过验收的范围：

1. 用户注册、登录与角色隔离。
2. 首页展示、分类浏览、关键词搜索。
3. 商家详情与商品或服务展示。
4. 购物车管理、订单提交和模拟支付。
5. 商家端门店维护、商品或服务管理和订单处理。
6. 平台管理后台商家审核和基础管理。
7. 外卖订单配送模拟与订单状态流转展示。

#### 3.9.2 P1 增强需求

1. 用户评价互动、商家公开回复和举报处理。
2. 优惠券、烟火值和会员等级展示。
3. 消息通知、商家客服和基础经营统计。
4. 首页推荐位、榜单、活动配置和基础数据看板。
5. AI 辅助搜索、推荐解释和基础文案生成能力。

#### 3.9.3 P2 拓展需求

1. 更复杂的营销活动和更细粒度的权限管理。
2. 更多 AI Skills 和更高阶的个性化推荐能力。
3. 真实支付、真实配送及第三方平台深度对接预留。
4. 更多终端形态扩展，包括 Web/H5、小程序或其他终端。

## 4 合格性规定

本期验收以 P0 需求为基线，P1、P2 不作为必收项。满足下列条件且不存在阻断级缺陷、严重权限缺陷或严重订单数据一致性缺陷时，可判定本版本合格。

| 编号 | 对应需求 | 验收方式 | 合格判定 |
|------|----------|----------|----------|
| ACC-01 | P0-用户注册、登录与角色隔离（3.4.1） | 功能测试 | 用户可通过手机号/邮箱完成注册、登录、退出；不同角色无法访问未授权功能；登录态失效需重新登录。 |
| ACC-02 | P0-首页展示与分类浏览（3.4.2） | 场景测试 | 首页可加载Banner、活动专区、分类入口、猜你喜欢等模块；用户可进入各分类浏览商家列表，支持分页加载。 |
| ACC-03 | P0-关键词搜索（3.4.2） | 场景测试 | 用户可通过关键词搜索商家、商品或服务；支持筛选、排序；无结果时给出提示与推荐。 |
| ACC-04 | P0-商家详情与商品/服务展示（3.4.3） | 场景测试 | 用户可查看商家详情（名称、评分、地址、营业时间等）和商品/服务明细（价格、规格、库存、规则等）；支持收藏、加入购物车。 |
| ACC-05 | P0-订单管理与提交（3.4.4） | 场景测试、数据核验 | 用户可增删改订单内容，金额实时计算；下单时需收集/选择收货地址；确认创建后生成唯一订单编号，订单包含明细、金额、地址等信息。 |
| ACC-06 | P0-模拟支付（3.4.4） | 场景测试、日志核验 | 用户可对订单发起模拟支付，支付后订单状态更新为“已支付”；重复支付具备幂等性，不产生重复记录或错误状态。 |
| ACC-07 | P1-外卖配送模拟与订单状态流转（3.4.5） | 场景测试 | 外卖订单可从待接单、备餐、配送至完成等状态正确流转；用户端可查看时间线、预计送达和模拟配送进度。 |
| ACC-08 | P0-商家端门店、商品管理与订单处理（3.4.8） | 功能测试 | 商家可维护门店信息、管理商品/服务上下架；可查看并处理订单（接单、拒单、查看核销状态等）。 |
| ACC-09 | P1-平台管理后台商家审核与基础管理（3.4.9） | 功能测试 | 管理员可审核商家入驻、通过或拒绝；可进行用户、订单、类目等基础管理操作。 |
| ACC-10 | P0-非功能需求（3.8） | 性能测试、异常测试 | 核心流程满足性能指标（查询类≤2s，订单提交≤3s等）；AI不可用时系统可降级且不阻断P0流程；关键异常可记录并可恢复；数据备份恢复验证通过。 |

## 6 尚未解决的问题

1. 地图服务供应商尚未最终确定，需在可用性、配额和接入复杂度之间完成选型。
2. AI 服务的具体实现方式尚未最终确定，需明确采用外部模型接口、内部规则引擎或混合方案。
3. 消息通知的首期交付模式尚未最终确定，需明确是否仅实现站内消息，或同步接入短信、邮件等能力。
4. 图片与对象存储的最终方案尚未最终确定，需明确首期是否采用本地存储，后续是否切换云存储。
5. 配送模拟的细化深度尚未最终确定，需明确仅展示阶段状态，或同时展示预计时间、模拟位置和异常模拟。
6. 部分扩展业务类目的首期覆盖深度尚未最终确定，需在统一框架下进一步细化规则边界。

## 7 注解

| 术语 | 说明 |
| --- | --- |
| 用户端 | 面向消费者的 Android/iOS 应用。 |
| 商家端 | 面向商家的 Web 管理端，用于店铺、商品或服务与订单处理。 |
| 平台管理后台 | 面向平台运营和管理员的 Web 管理系统，用于审核、配置、运营和审计。 |
| 模拟支付 | 不发生真实资金结算的支付流程，仅用于验证支付结果与订单状态流转。 |
| 模拟配送 | 不对接真实运力平台，由后台按业务规则推进外卖订单配送相关状态。 |
| 烟火值 | 平台内部定义的用户活跃度或消费贡献指标，用于会员成长与权益展示。 |
| Skills | 系统可接入的智能能力单元，可用于搜索辅助、客服辅助、内容生成和推荐解释等场景。 |

## 附录A 角色说明

| 角色 | 角色定位 | 主要职责 | 权限边界 |
| --- | --- | --- | --- |
| 用户 | 通过 Android/iOS 客户端使用平台服务的消费者 | 注册登录、浏览首页、搜索商家、加入购物车、提交订单、支付模拟、查看订单状态、使用券码或预约服务、发起评价与售后申请 | 仅可访问本人账户、订单与互动数据；不可操作商家经营数据与平台管理数据 |
| 商家 | 通过 Web 端运营门店的经营主体 | 维护门店与商品信息、处理接单或拒单、核销券码、确认预约、查看订单与基础经营数据、处理用户咨询 | 仅可管理所属门店及其业务数据；不可执行平台级审核、全局配置与跨商家数据查看 |
| 平台管理员 | 通过 Web 管理后台执行平台治理与运营配置的角色 | 商家审核、内容审核、类目与基础配置、订单干预、异常处理、配送模拟规则维护、数据看板查看 | 可进行平台级治理与审计；不涉及真实资金清结算 |
| 支付模拟服务 | 系统内部服务角色 | 生成支付成功、支付失败、退款完成等模拟结果，驱动订单支付相关状态变更 | 仅提供状态模拟与回调，不对接真实资金渠道 |
| 配送模拟服务 | 系统内部服务角色 | 在商家接单后创建并推进模拟配送任务，生成虚拟运力、预计送达时间与配送状态 | 无独立骑手端；状态由后端规则、定时任务或后台人工干预驱动 |
| AI 辅助服务 | 系统内部服务角色 | 提供辅助搜索、推荐、问答和运营辅助能力 | AI 输出不作为交易最终依据；异常时可降级为规则或 Mock 数据 |

## 附录B 核心订单状态流转

下表用于补充说明不同订单类型的主干状态流转。退款相关状态为跨品类通用异常闭环。

| 订单类型 | 正常主流程 | 常见异常流转 | 说明 |
| --- | --- | --- | --- |
| 外卖订单 | 待支付 → 待商家接单（已支付） → 制作中 → 待配送 → 配送中 → 已送达 → 已完成 | 待支付 → 已取消；待商家接单阶段商家拒单或用户撤单 → 退款中 → 已退款；制作或配送阶段按规则允许取消时 → 退款中 → 已退款 | 仅该类订单进入配送模拟链路 |
| 到店团购或券码订单 | 待支付 → 待核销（已出券） → 已核销 → 已完成 | 待支付 → 已取消；未核销前申请退款 → 退款中 → 已退款；商家或平台关闭订单 → 退款中 → 已退款 | 无配送环节，券码核销为核心履约节点 |
| 预约类订单 | 待支付 → 待商家确认（已支付） → 已预约 → 待到店或待服务 → 已完成 | 待支付 → 已取消；商家拒绝预约或超时未确认 → 退款中 → 已退款；规则允许范围内用户取消预约 → 退款中 → 已退款 | 预约时间与资源占用为关键约束 |

通用异常状态定义如下：

| 状态 | 含义 | 备注 |
| --- | --- | --- |
| 已取消 | 订单在未完成支付或无需退款的条件下关闭，不再继续履约 | 常见于未支付超时关闭、用户主动取消 |
| 退款中 | 已付款订单因取消、拒单、核销失败或履约失败发起退款处理 | 处于逆向流程处理中 |
| 已退款 | 模拟退款处理完成，订单闭环结束 | 仅表示平台内业务结果，不代表真实资金清算 |

## 附录C 配送模拟状态流转

本项目配送为后台驱动的模拟流程，仅适用于外卖订单，不设置独立骑手应用。配送状态由订单服务、配送模拟服务与后台操作共同推进。

| 模拟状态 | 触发条件 | 驱动主体 | 业务说明 |
| --- | --- | --- | --- |
| 待调度 | 商家接单且订单满足配送条件 | 订单服务、配送模拟服务 | 创建模拟配送任务，准备生成虚拟运力与预计送达时间 |
| 已分配模拟运力 | 后端规则完成分单 | 配送模拟服务 | 系统绑定虚拟配送对象，不存在独立骑手接单动作 |
| 待取餐 | 达到预计出餐时间，或商家手动标记可取餐 | 配送模拟服务、商家、平台管理员 | 用户侧可见待取餐状态 |
| 配送中 | 系统触发取餐完成并开始时间或路径推进 | 配送模拟服务 | 根据距离、时长、规则或 Mock 数据更新进度与预计送达时间 |
| 已送达 | 达到模拟送达条件，或后台人工闭环 | 配送模拟服务、平台管理员 | 标记履约送达完成 |
| 已完成 | 用户确认收货，或系统超时自动完成 | 订单服务 | 订单进入交易完成状态，可进入评价等后续环节 |
| 已取消 | 订单在送达前被取消且无需继续配送 | 用户、商家、平台管理员或规则任务 | 配送任务同步关闭 |
| 退款中 → 已退款 | 已付款订单因取消、拒单或履约失败触发退款 | 订单服务、支付模拟服务 | 仅更新平台内模拟退款结果，不涉及真实资金 |

配送模拟约束如下：

1. 配送任务仅在外卖订单进入商家已接单后创建。
2. 骑手在系统中为虚拟配送实体，可由规则或 Mock 数据生成。
3. 状态推进以后端事件、定时任务或后台人工干预为主，不依赖独立骑手侧操作。
4. 订单主状态与配送子状态应保持一致；当订单进入取消或退款链路时，配送任务必须同步关闭。

## 附录D P0/P1/P2 功能范围

| 优先级 | 建设目标 | 本级功能范围 | 边界与说明 |
| --- | --- | --- | --- |
| P0 | 建立最小可用的核心交易闭环 | 注册登录、首页、搜索、商家详情、下单、支付模拟、商家接单、外卖——配送模拟、（到店、预约）团购——核销 | 以可下单、可流转、可闭环为目标；不包含真实支付，不包含独立骑手端 |
| P1 | 提升留存、运营与服务体验 | 后台审核、评价互动、优惠券、会员、消息通知、客服、可视化看板、AI 辅助搜索与推荐 | AI 能力可按资源情况降级为规则或 Mock 数据；仍不引入真实支付与真实配送 |
| P2 | 形成扩展能力与外部对接预留 | 复杂营销、更多 AI Skills、真实配送和真实支付预留、多端扩展 | 重点为架构预留、接口拓展与业务深化，可根据资源条件分阶段落地 |

优先级判定原则如下：

1. P0 直接决定平台是否具备基础交易能力与演示闭环。
2. P1 在 P0 稳定后补强用户体验、运营能力与服务质量。
3. P2 面向中长期扩展，处理复杂业务、外部能力接入与多端生态延展。
