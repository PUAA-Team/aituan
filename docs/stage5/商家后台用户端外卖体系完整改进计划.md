# 商家后台用户端外卖体系完整改进计划

## 1. 文档目标

本计划用于落实 `商家后台用户端改进反馈原文.md` 中的全部反馈，核心原则是：后端、用户端、商家端、后台端必须一起改，不再把后端当作单纯前置依赖，也不把商家端和后台端做成临时演示页。

本次改进目标不是“补几个按钮”，而是把外卖模块和管理端基础能力推进到可以继续多人扩展的成品雏形。

## 2. 用户反馈约束逐条转化

| 编号 | 用户反馈 | 本计划转化为实施要求 |
| --- | --- | --- |
| 1 | 商家端和后台端太简陋，很多功能没做 | 重构两端信息架构、页面布局、业务模块和后端接口，不再只做订单列表 |
| 2 | 管理端不要圆角，要大厂控制台风格 | 商家端/后台端统一控制台视觉：左侧导航、顶部工具栏、表格、抽屉、弹窗、直角或小直角，不用营销文案 |
| 3 | 用户端订单状态粗糙，有英文单词露出 | 统一外卖状态文案映射，禁止 API code 直接出现在 UI；详情页只展示用户能理解的状态 |
| 4 | 配送履约记录未到节点不应提前显示 | 用户端配送记录只显示已发生节点和当前节点，不展示未来未发生节点；商家/后台可展示完整流程但要区分未到达 |
| 5 | 地址填写、地址管理没做 | 后端补地址管理接口；用户端补地址列表、新增/编辑地址、结算选择地址、默认地址 |
| 6 | 商家端门店切换不合理 | 商家端按账号绑定商家和门店，前端不允许随意输入门店 ID；多门店作为后续扩展，不在主流程暴露 |
| 7 | 商品管理要能添加商品，编辑弹窗显示修改 | 后端补商品新增、图片、分类/规格基础字段；商家端商品新增/编辑使用弹窗或抽屉 |
| 8 | 手动/自动接单放到配送规则那里 | 商家端将接单模式合并到门店履约/配送规则配置页 |
| 9 | 商家端不仅外卖，很多东西可复用 | 商家端做通用商家控制台壳：概览、订单、商品/服务、门店设置、评价、消息；外卖作为当前业务模块 |
| 10 | 后台端要有设置、公告等必要功能 | 后台端补控制台壳：概览、商家管理、用户管理、订单治理、内容公告、运营配置、系统设置 |
| 11 | 模拟配送在哪里，后端要提供服务 | 后端补模拟配送控制服务、配送任务查询、后台配置、手动触发、暂停/恢复、异常处理 |
| 12 | 前端不要放系统描述文案 | 所有端删除“本阶段/说明/系统描述”类文案，只保留真实产品操作文案 |
| 13 | 图片缺失，需要上传图片和可扩展图床 | 后端补本地上传、静态访问、资源表/抽象服务；商家/后台可改商品店铺图，用户可改头像；seed 使用占位图 |
| 14 | 用户端还有未分配功能 | 重新梳理用户端外卖闭环：地址、头像、催单、取消、联系商家、再来一单、评价入口等 |
| 15 | 商家端和后台端保持可扩展 | 前端按模块拆分、API 分层、类型独立、布局组件复用；后端按领域服务拆分，避免继续堆单文件 |

## 3. 总体方案

### 3.1 分层目标

```text
后端能力层
  账号/权限
  地址管理
  图片上传与静态资源
  商家资料/门店资料
  商品/服务管理
  外卖订单履约
  模拟配送服务
  后台公告/配置/治理

用户端 APP
  地址管理
  外卖结算增强
  外卖订单状态与配送记录优化
  用户头像上传
  外卖补充操作入口

商家端 Web
  通用商家控制台布局
  首页概览
  订单中心
  商品/服务中心
  外卖履约配置
  店铺资料与图片
  评价与消息占位或基础列表

后台端 Web
  通用后台控制台布局
  平台概览
  商家管理
  用户管理
  订单治理
  公告内容管理
  运营配置
  系统设置/审计日志
```

### 3.2 视觉方向

管理端统一采用成熟控制台风格：

- 左侧深色或白底窄导航，不用大面积宣传卡片。
- 顶部工具栏展示当前位置、刷新、账号、退出。
- 内容区以表格、筛选栏、详情抽屉、编辑弹窗为主。
- 红色只作为品牌主色和关键按钮，不铺满页面。
- 不使用蓝紫渐变。
- 不使用大圆角；默认 `0-4px` 小直角。
- 不使用“本阶段聚焦”“平台说明”等演示文案。
- 空状态、错误状态使用正式后台文案，例如“暂无数据”“加载失败，请重试”。

### 3.3 扩展性方向

- 商家端和后台端都改成模块化目录，而不是所有逻辑写在 `App.vue`。
- API 调用拆到 `src/api/*.ts`。
- 类型拆到 `src/types/*.ts`。
- 页面拆到 `src/pages/*`。
- 通用组件拆到 `src/components/*`。
- CSS 拆成基础样式、布局样式、业务样式，或至少分段清晰。
- 后端逐步从 `TradeService` / `TradeRepository` 大文件拆出地址、上传、商家管理、后台配置等服务。

## 4. 后端完整改进计划

### 4.1 地址管理能力

#### 目标

用户端可以填写、编辑、选择和管理收货地址，外卖结算必须使用真实地址选择逻辑。

#### 新增/复用表

现有 `user_address` 表可复用。若字段不足再新增迁移，不回改旧迁移。

#### 建议接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/app/account/addresses` | 查询当前用户地址列表 |
| `POST` | `/api/app/account/addresses` | 新增地址 |
| `PUT` | `/api/app/account/addresses/{addressId}` | 编辑地址 |
| `DELETE` | `/api/app/account/addresses/{addressId}` | 删除地址，逻辑删除 |
| `POST` | `/api/app/account/addresses/{addressId}/default` | 设置默认地址 |

#### 后端校验

- 联系人不能为空。
- 手机号不能为空，先做格式基础校验。
- 省市区和详细地址不能为空。
- 每个用户只能操作自己的地址。
- 删除默认地址后，要么自动选最近地址为默认，要么允许无默认但结算页提示选择。

#### 涉及文件

- 新增 `AccountAddressController.java` 或在现有 account 模块扩展。
- 新增 `AddressService.java`。
- 新增/扩展 `AddressRepository.java`。
- 新增 DTO：地址请求、地址视图。

### 4.2 图片上传与静态资源能力

#### 目标

本阶段先做本地上传，文件统一存放到 D 盘项目子目录；数据库保存 URL。后续可以无痛切换到图床、OSS 或 CDN。

#### 存储目录

```text
D:/aituan_runtime/uploads/avatar
D:/aituan_runtime/uploads/store
D:/aituan_runtime/uploads/item
D:/aituan_runtime/uploads/announcement
```

#### 建议新增配置

```yaml
aituan:
  upload:
    storage: local
    root-dir: ${AITUAN_UPLOAD_ROOT:D:/aituan_runtime/uploads}
    public-prefix: ${AITUAN_UPLOAD_PUBLIC_PREFIX:/api/common/files}
```

#### 建议新增表

`file_asset`：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `owner_type` | `user / merchant / admin / system` |
| `owner_id` | 所属 ID |
| `biz_type` | `avatar / store / item / announcement` |
| `original_name` | 原文件名 |
| `storage_type` | `local / remote` |
| `object_key` | 文件相对路径 |
| `public_url` | 前端访问 URL |
| `mime_type` | 文件类型 |
| `size_bytes` | 文件大小 |
| `created_at` | 创建时间 |
| `is_deleted` | 逻辑删除 |

#### 建议接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/common/files/upload` | 通用上传，multipart |
| `GET` | `/api/common/files/{bizType}/{fileName}` | 本地文件访问 |
| `POST` | `/api/app/account/avatar` | 用户修改头像 |
| `POST` | `/api/merchant/stores/current/cover` | 商家修改店铺图 |
| `POST` | `/api/merchant/items/{itemId}/cover` | 商家修改商品图 |
| `POST` | `/api/admin/stores/{storeId}/cover` | 后台修改店铺图 |
| `POST` | `/api/admin/items/{itemId}/cover` | 后台修改商品图 |

#### 安全限制

- 只允许图片 MIME：`image/jpeg`、`image/png`、`image/webp`。
- 限制大小，例如 5MB。
- 文件名使用 UUID，不信任原文件名。
- 不允许上传脚本或 HTML。
- 静态访问只暴露上传根目录内文件。

#### 图片种子数据

- seed 中为商家、商品、头像、公告配置可访问的网络占位图 URL。
- 后续上传后用本地 `/api/common/files/...` URL 覆盖。

### 4.3 商家账号与门店归属

#### 当前问题

商家端允许前端输入门店 ID，导致一个商家账号可能查看或编辑别的商家菜品，不符合真实业务。

#### 改进目标

- 商家端登录后后端返回当前商家资料和默认门店。
- 商家端不再展示门店 ID 输入框。
- 当前阶段一个账号默认绑定一个商家，一个商家可有一个主门店。
- 后续多门店再做门店切换，但必须由后端返回可访问门店列表，不允许手输。

#### 建议接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/merchant/profile/me` | 当前商家资料、门店列表、默认门店 |
| `PUT` | `/api/merchant/profile/me` | 编辑商家联系人等基础资料 |
| `GET` | `/api/merchant/stores/current` | 当前主门店详情 |
| `PUT` | `/api/merchant/stores/current` | 编辑门店名称、地址、营业时间、公告、封面 |

### 4.4 商品/服务管理后端

#### 目标

商家端商品管理要能新增、编辑、上下架、上传图片，并为后续非外卖服务复用。

#### 建议接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/merchant/catalog/items` | 当前商家商品/服务列表，支持业务类型、状态、关键词 |
| `POST` | `/api/merchant/catalog/items` | 新增商品/服务 |
| `GET` | `/api/merchant/catalog/items/{itemId}` | 详情 |
| `PUT` | `/api/merchant/catalog/items/{itemId}` | 编辑基础信息 |
| `POST` | `/api/merchant/catalog/items/{itemId}/status` | 上架/下架 |
| `POST` | `/api/merchant/catalog/items/{itemId}/cover` | 上传/替换商品图 |
| `GET` | `/api/merchant/catalog/categories` | 当前商家分类 |
| `POST` | `/api/merchant/catalog/categories` | 新增分类 |
| `PUT` | `/api/merchant/catalog/categories/{categoryId}` | 编辑分类 |

#### 字段范围

- 商品名。
- 副标题。
- 业务类型：外卖、团购、酒店、电影等。
- 分类。
- 价格、原价。
- 库存。
- 封面图。
- 标签。
- 状态。
- 排序。

#### SKU 策略

本阶段继续一个默认 SKU，但接口设计保留扩展：

```json
{
  "skuList": [
    { "skuName": "默认", "price": 18.8, "stock": 100 }
  ]
}
```

### 4.5 配送规则与接单模式

#### 目标

把手动/自动接单从侧边栏挪到商家端“履约设置/配送规则”页面。

#### 后端接口

保留已有：

- `GET /api/merchant/trade/stores/{storeId}/takeaway-setting`
- `POST /api/merchant/trade/stores/{storeId}/takeaway-setting`
- `GET /api/merchant/trade/stores/{storeId}/delivery-rule`
- `POST /api/merchant/trade/stores/{storeId}/delivery-rule`

但前端不传手输 storeId，而是使用 `profile/me` 返回的当前门店 ID。

### 4.6 模拟配送服务

#### 当前问题

模拟配送虽然有状态推进，但用户无法明显感知“模拟配送服务”，后台也缺少统一控制。

#### 改进目标

后端提供明确的模拟配送服务能力：

- 支付后创建配送任务。
- 商家出餐后进入待配送。
- 后台或调度器可把任务推进到配送中、已送达、已完成。
- 后台可查看任务状态、预计时间、下一次推进时间。
- 后台可暂停/恢复模拟推进。
- 后台可手动触发一次推进。
- 用户端只展示已发生节点和当前状态。

#### 建议接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/admin/delivery/tasks` | 配送任务列表 |
| `GET` | `/api/admin/delivery/tasks/{taskId}` | 配送任务详情 |
| `POST` | `/api/admin/delivery/tasks/{taskId}/advance` | 手动推进 |
| `POST` | `/api/admin/delivery/tasks/{taskId}/pause` | 暂停模拟推进 |
| `POST` | `/api/admin/delivery/tasks/{taskId}/resume` | 恢复模拟推进 |
| `POST` | `/api/admin/delivery/tasks/{taskId}/abnormal` | 标记异常 |
| `GET` | `/api/admin/delivery/settings` | 查看模拟配送配置 |
| `POST` | `/api/admin/delivery/settings` | 修改模拟推进间隔、是否自动推进 |

#### 建议新增/扩展字段

如现有 `delivery_task` 不够，可新增迁移扩展：

- `auto_advance_enabled`
- `paused_at`
- `abnormal_reason`
- `last_advanced_by`
- `last_advanced_at`

### 4.7 后台公告与系统配置

`platform_announcement`：公告。

字段：标题、内容、展示端、状态、开始时间、结束时间、排序、创建人。

`platform_config`：平台配置键值。

字段：配置 key、配置 value、分组、说明、是否启用。

#### 建议接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/admin/announcements` | 公告列表 |
| `POST` | `/api/admin/announcements` | 新增公告 |
| `PUT` | `/api/admin/announcements/{id}` | 编辑公告 |
| `POST` | `/api/admin/announcements/{id}/status` | 发布/下线 |
| `GET` | `/api/admin/configs` | 配置列表 |
| `PUT` | `/api/admin/configs/{key}` | 修改配置 |

### 4.8 后台基础管理接口

#### 最小范围

| 模块 | 功能 |
| --- | --- |
| 商家管理 | 商家列表、门店列表、查看详情、修改状态、修改封面图 |
| 用户管理 | 用户列表、查看资料、头像/状态显示 |
| 商品治理 | 商品列表、按商家/业务类型筛选、上下架、改图 |

## 5. 用户端 APP 完整改进计划

### 5.1 外卖订单状态展示

#### 问题

当前 UI 出现“当前履约状态: 英文 code”，这是后端 code 泄露到用户界面。

#### 改进方案

- 新增统一 `TakeawayFulfillmentPresenter` 或扩展现有文案方法。
- 所有状态显示只使用中文。
- 页面不展示 `fulfillmentStatus` 原始值。
- 状态标题示例：
  - 待商家接单
  - 商家已接单
  - 商家正在备餐
  - 已出餐，等待配送
  - 骑手正在配送
  - 已送达
  - 已完成
  - 异常处理中

### 5.2 配送履约记录展示

#### 当前问题

未到达节点提前展示，会让用户误以为已经发生。

#### 用户端规则

用户端只展示：

1. 已到达节点。
2. 当前节点。
3. 当前节点的下一步可用简短提示，但不作为时间线节点显示。

示例：

```text
已支付
商家已接单
商家正在备餐（当前）
```

不展示：

```text
待配送
配送中
已送达
已完成
```

直到节点真正到达。

#### 商家端/后台端规则

管理端可以展示完整流程，但必须使用不同视觉区分：

- 已完成：实心点。
- 当前：红色描边或状态标签。
- 未到达：灰色，不显示时间。

### 5.3 地址管理

#### 新增页面

| 页面 | 路由建议 | 功能 |
| --- | --- | --- |
| 地址列表 | `/profile/addresses` | 查看、删除、设默认 |
| 新增地址 | `/profile/addresses/edit` | 新增联系人、电话、省市区、详细地址、标签 |

- 地址卡片可点击进入选择。

- 创建订单必须传选择的 `addressId`。
- 地址变更后重新调用 preview。

### 5.4 用户头像上传

#### 目标

我的页可以上传头像，头像 URL 存后端。

#### 页面交互

- 打开图片选择。
- 上传到 `/api/common/files/upload` 或 `/api/app/account/avatar`。
- 更新 profile。

Flutter 端如当前没有图片选择依赖，需要评估是否引入 `image_picker`。如果引入新依赖，实施前单独确认。

### 5.5 外卖补充逻辑

#### 必补功能

| 功能 | 说明 |
| --- | --- |
| 再来一单 | 从历史外卖订单重新带商品进入商家页/确认页 |
| 联系商家 | 首包可显示门店电话或占位弹窗 |
| 催单 | 当前状态为备餐/配送时可点击，后端记录催单日志或返回提示 |
| 取消订单 | 未支付或待接单阶段允许取消，后端更新状态 |
| 评价入口 | 已完成外卖订单进入评价发布 |

## 8. 图片与占位图方案

### 8.1 seed 图片来源

本阶段先使用稳定可访问的公开图片 URL 或项目内静态占位图。若担心外网不稳定，则放入后端上传目录或前端 assets：

```text
D:/aituan_runtime/uploads/seed/store
D:/aituan_runtime/uploads/seed/item
D:/aituan_runtime/uploads/seed/avatar
```

### 8.2 后续图床扩展

定义接口：

```java
interface FileStorageService {
  FileAsset save(MultipartFile file, FileBizType bizType, CurrentUser owner);
  Resource load(String objectKey);
}
```

实现：

- `LocalFileStorageService`：当前使用。
- `RemoteImageStorageService`：后续图床/OSS 使用。

前端只关心 `publicUrl`，不关心存储来源。

## 10. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 改动范围很大 | 分批提交，每批都能独立构建通过 |
| 后端文件继续变大 | 新增领域服务和 Repository，不继续把所有逻辑塞进 `TradeService` |
| 图片上传涉及安全 | 限制 MIME、大小、扩展名，使用 UUID 文件名 |
| Web 端重构影响当前功能 | 先保留 API 能力，再替换 UI，构建每批验证 |
| Flutter 引入图片选择依赖 | 如需新增依赖，实施前单独确认 |
| 多人后续协作冲突 | 目录模块化、接口清单稳定、文档更新索引 |
