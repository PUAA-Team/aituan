# Stage5 商家账号归属与业务分型治理改进计划

## 1. 文档目标

本文档根据 `docs/stage5/商家后台用户端改进反馈原文.md` 中 2026-05-22 新增反馈整理，目标是在开工前把需要补齐的后端、商家端、后台端、用户端 APP、seed 和文档事项全部列清楚，避免继续出现“商家账号看到别的商家商品”“APP 商品/商家图片未接入”“商家端外卖与非外卖混用”“后台缺少新增/编辑/审核动作”等问题。

本文档只做实施计划，不直接改功能代码；后续编码必须在确认本计划范围后开始。

## 2. 本次反馈原文对应问题拆解

| 编号 | 用户反馈点 | 当前判断 | 必须处理方向 |
| --- | --- | --- | --- |
| P1 | 演示商家账号里还有别的商家的商品 | seed 中一个 `demo_merchant` 账号绑定多个商家；后端按账号取商家时只取首个，数据和权限模型不一致 | 改为一个商家账号绑定一个商家；补多个演示商家账号；后端查询和 seed 一致 |
| P2 | 后续要有商家注册功能 | 当前只有演示登录，缺入驻申请链路 | 本轮记录并预留接口/状态；如确认纳入本轮，做最小入驻申请与后台审核 |
| P3 | 未来要有商家提交审核认证材料、后台审核流程 | 已有 merchant 审核字段和 admin 审核基础，但流程不完整 | 设计认证材料表、上传、提交、审核、驳回原因、审核记录 |
| P4 | 前端好几个页面没有商家退出登录按钮 | 布局组件已有统一退出，但需要确认所有页面都走统一布局，登录态失效也要可退出 | 统一顶部账号区，所有业务页必须在布局内，登录页外单独处理 |
| P5 | APP 头像能显示，商品/商家等图片没有接入 | 模型和页面大量仍用 `MockThumb`；`coverUrl` 映射被丢弃 | 模型补 `coverUrl`，列表/详情/订单/收藏统一用远程图片组件 |
| P6 | 外卖和团购类商家管理应不同 | 商家端已有部分 delivery 分区，但订单、商品、动作仍混用 | 以 `businessType` 做页面、字段、动作分型，外卖不显示券码，非外卖不显示配送 |
| P7 | 其他商家功能留给对应同学但要可扩展 | 分工 D 负责七类非外卖，C 不应把复杂房态/场次/预约全做死 | 当前先做通用扩展点和 UI 分型，复杂非外卖字段记录到长期待办和分工 D |
| P8 | 很多按钮反馈不要只在底部弹出 | Web 目前主要是顶部 notice；部分动作还缺确认弹窗/局部结果 | 危险动作用确认弹窗；编辑/新增用 modal/drawer；列表项动作给行内状态 |
| P9 | 后台缺编辑/新增按钮，管理功能缺失 | Merchants/Catalog/Users 等页面缺新增/编辑/审核闭环 | 补后台基础 CRUD、审核、启停、图片编辑、公告/配置完善 |
| P10 | 看分工里大家都没涉及的点 | 平台基础能力如商家注册、资质、文件资产、通用配置、账号绑定容易掉空 | 本计划把这些列为“跨模块基础能力”，由当前阶段补最小闭环或明确移交 |

## 3. 现状探索结论

### 3.1 后端与 seed

关键文件：

- `database/seeds/R__seed_demo_data.sql`
- `database/migrations/V002__init_merchant_catalog.sql`
- `database/migrations/V003__init_trade_review_message.sql`
- `database/migrations/V006__stage5_console_foundation.sql`
- `services/backend/src/main/java/com/aituan/merchant/MerchantService.java`
- `services/backend/src/main/java/com/aituan/catalog/CatalogService.java`
- `services/backend/src/main/java/com/aituan/trade/TradeService.java`

现状问题：

1. `merchant_profile.account_id` 能表达“商家账号绑定商家”，但数据库层没有唯一约束保证一个账号只对应一个商家。
2. seed 中当前主要演示商家账号是 `demo_merchant`，却绑定了多个 `merchant_profile`，导致“一个账号看见多个商家/商品”的演示语义不对。
3. `MerchantService` 当前按账号查询商家时只取第一个商家，和 seed 的多绑定不一致，容易造成页面和数据混乱。
4. `CatalogService`、`TradeService` 已经有按当前登录账号/商家限制数据的方向，但 seed 归属不正确会让演示效果看起来像权限串号。
5. Admin 端全量查看是合理的，但需要在页面上明确“平台管理员视角”，不要和商家端混淆。

现状问题：

2. `FulfillmentPage.vue` 只在外卖场景展示接单/配送规则，方向正确；但 `OrderPage.vue` 仍可能对所有订单展示备餐、配送推进等外卖动作。
3. `CatalogPage.vue` 能切换业务类型，但外卖商品与非外卖服务在字段、动作、说明上仍不够分离。
4. 商家端的反馈目前多是顶部 notice，不是最底部 toast；但编辑、新增、审核、拒单等动作仍应改为弹窗或行内结果，避免用户看不到。
5. 后台 `AnnouncementsPage.vue`、`SettingsPage.vue` 已有部分新增/编辑能力；`MerchantsPage.vue`、`CatalogPage.vue`、`UsersPage.vue` 缺更多新增/编辑/审核/启停动作。

## 4. 本轮建议范围

### 4.1 建议本轮必须完成

1. **商家账号归属修复**：一个商家账号只绑定一个商家；seed 补多个演示商家账号；商家端只能看到自己的门店、商品、订单、配送规则。
2. **APP 图片接入修复**：用户端商家、商品/服务、订单项、收藏全部接入后端图片 URL，失败时才显示本地占位。
3. **商家端业务分型**：外卖商家只展示外卖商品、配送规则、接单/备餐/配送；非外卖只展示服务、券码/预约扩展入口，不展示配送流程。
4. **后台管理动作补齐**：商家、商品/服务、用户、公告、配置至少有可演示的新建/编辑/启停/审核动作。
5. **操作反馈改造**：新增/编辑/审核/拒单/危险动作改成弹窗确认、弹窗表单或行内状态，不依赖底部 toast。
6. **文档和长期待办更新**：非外卖复杂业务、商家注册、资质认证完整流程需要明确哪些本轮做、哪些交给后续成员。

### 4.2 建议本轮只做预留或最小闭环

1. **商家注册/入驻**：建议本轮先做最小“提交入驻申请 + 后台审核 + 生成/绑定商家账号”的设计或轻量接口；复杂短信、邮件、实名校验后置。
2. **资质认证材料**：建议本轮做 `local upload + material metadata + admin approve/reject` 最小闭环；真实 OCR、营业执照核验后置。
3. **非外卖七类复杂字段**：本轮只把商家端页面和后端模型留出 `businessType` 分型扩展；酒店房态、电影选座、门票日期库存、医美预约资源仍交给成员 D。
4. **后台权限角色细分**：本轮继续用 ADMIN/MERCHANT 基础角色；复杂 RBAC、菜单权限、部门权限后置。

## 5. 后端详细方案

### 5.1 商家账号与归属约束

目标：商家端每个账号只属于一个商家，登录后所有数据查询都自动限定到这个商家。

计划事项：

1. 新增 Flyway 迁移，不回改旧迁移：
   - 给 `merchant_profile.account_id` 增加唯一约束或唯一索引。
   - 如现有数据不满足，先在 seed 中调整为一账号一商家，再新增约束。
   - 保留 `merchant_store.merchant_id`、`catalog_item.store_id`、`trade_order.store_id` 的既有归属链。
2. 后端服务层统一当前商家上下文：
   - `MerchantService` 提供 `currentMerchant()` / `currentMerchantId()`。
   - `CatalogService`、`TradeService`、配送服务统一通过当前商家 ID 过滤。
   - 所有商家端详情、编辑、状态流转必须校验当前商家是否拥有目标门店/商品/订单。
3. 错误提示统一：
   - 未登录：`UNAUTHORIZED`。
   - 商家角色错误：`FORBIDDEN`。
   - 操作非本人商家数据：`FORBIDDEN` 或业务错误“无权操作该商家数据”。
4. Admin 不受商家归属限制，但接口命名和前端文案应体现平台视角。

### 5.2 演示商家账号 seed

目标：演示时每个商家账号登录后看到自己的数据，不再出现别的商家商品。

建议演示账号：

| 账号 | 密码 | 绑定业务 | 绑定商家 | 说明 |
| --- | --- | --- | --- | --- |
| `demo_takeaway_merchant` | `123456` | 外卖 | 爱团小馆 | 外卖 C 组主演示账号 |
| `demo_groupbuy_merchant` | `123456` | 团购 | 团购示例商家 | 非外卖扩展演示 |
| `demo_hotel_merchant` | `123456` | 酒店 | 酒店示例商家 | 交给 D 深化，当前只保证隔离 |
| `demo_beauty_merchant` | `123456` | 丽人医美 | 丽人示例商家 | 交给 D 深化，当前只保证隔离 |
| `demo_ticket_merchant` | `123456` | 景点/门票 | 门票示例商家 | 交给 D 深化，当前只保证隔离 |
| `demo_entertainment_merchant` | `123456` | 休闲娱乐/电影演出 | 娱乐示例商家 | 交给 D 深化，当前只保证隔离 |

处理原则：

1. 如保留旧 `demo_merchant`，只能绑定一个默认外卖商家，不再绑定多个商家。
2. seed 必须幂等，不清空真实数据，不使用 `TRUNCATE`。
3. 每个账号至少配套：商家资料、门店、商品/服务、订单样例、图片 URL。
4. 文档中更新账号密码清单，避免演示时不知道登录哪个账号。

### 5.3 商家注册与认证材料

建议分两层：

#### 本轮最小闭环

1. 数据表：
   - `merchant_application`：入驻申请、联系人、手机号、业务类型、申请状态、审核意见。
   - `merchant_certification_material`：材料类型、文件 URL、审核状态、驳回原因。
   - `merchant_audit_log`：审核动作、审核人、审核结果、备注。
2. 接口：
   - `POST /api/open/merchant/applications`：提交入驻申请。
   - `GET /api/merchant/certification`：商家查看认证状态。
   - `POST /api/merchant/certification/materials`：上传/提交材料。
   - `GET /api/admin/merchants/applications`：后台查看申请。
   - `POST /api/admin/merchants/applications/{id}/approve`：通过并创建/绑定商家。
   - `POST /api/admin/merchants/applications/{id}/reject`：驳回并记录原因。
3. 上传：商家端通过 `POST /api/merchant/certification/materials` 上传认证图片，文件 bizType 使用 `merchant-certification`。

实现状态（2026-05-22）：

- 已接入商家端登录页“申请入驻”弹窗，提交后生成 `merchant_application` 待审核记录。
- 已接入后台端“入驻申请审核”，通过后创建商家账号、商家主体和门店；通过后的登录账号为申请编号，默认演示密码为 `123456`。
- 已接入商家端门店页认证材料上传，以及后台端认证材料通过/驳回。
- 已在后端放开 `merchant-certification` 文件类型白名单，并记录 `merchant_audit_log` 与 `sys_audit_log`。

#### 后续增强

1. 短信/邮箱验证码。
2. 营业执照 OCR 或第三方核验。
3. 法人实名核验。
4. 多管理员分级审核。
5. 认证到期复核提醒。

### 5.4 图片与文件能力

当前已有 `file_asset` 和本地上传能力，本轮重点是把前后端串起来。

后端计划：

1. 商家端接口支持更新：
   - 门店 `coverUrl`、公告图、门店图集扩展字段。
   - 商品/服务 `coverUrl`。
   - 认证材料文件。
2. 后台接口支持平台管理员编辑：
   - 商家门店图片。
   - 商品/服务图片。
   - 公告封面。
3. 返回字段保持统一：
   - 后端内部字段可为 `cover_url`。
   - API 响应统一 `coverUrl`。
4. 文件存储保持可扩展：
   - 当前本地目录：`D:/aituan_runtime/uploads/{bizType}/...`。
   - `file_asset.storage_type` 保留 `local/oss/cdn` 扩展。
   - 后续接图床/OSS 时只替换存储实现，不改业务表结构。

## 6. 商家端详细方案

### 6.1 总体交互和视觉

目标：商家端要像成熟控制台，不像临时 demo 页面。

计划事项：

1. 保持左侧导航 + 顶部账号区 + 主内容区。
2. 不使用蓝紫渐变，不使用大圆角；卡片和表格用硬朗控制台风格，圆角控制在 0-4px。
3. 顶部账号区固定展示：当前商家名、业务类型、审核状态、退出登录。
4. 页面不展示“系统说明/这是演示/功能说明”这类面向开发者的文字；只展示真实业务字段和操作提示。
5. 空状态也要像成品：给“暂无商品”“暂无订单”，并提供“新增商品/刷新”等真实操作。

### 6.2 导航和业务分型

建议商家端导航按业务类型动态展示：

| 页面 | 外卖商家 | 非外卖商家 | 说明 |
| --- | --- | --- | --- |
| 工作台 | 今日订单、待接单、配送异常、营业状态 | 今日订单、待核销、预约待确认、营业状态 | 同名页面，指标不同 |
| 门店资料 | 门店信息、配送范围、营业时间、公告、图片 | 门店信息、服务说明、营业时间、公告、图片 | 字段分型 |
| 商品/服务 | 外卖商品、分类、价格、库存、上下架、图片 | 服务/套餐、有效期、使用规则、预约/券码扩展 | 文案和字段不同 |
| 外卖订单 | 显示 | 不显示 | 外卖专属 |
| 配送规则 | 显示，包含手动/自动接单 | 不显示 | 手动/自动接单放到这里 |
| 券码核销 | 不显示 | 显示或预留 | 分工 D 深化 |
| 预约管理 | 不显示或仅上门服务扩展 | 显示或预留 | 分工 D 深化 |
| 评价回复 | 显示 | 显示 | 通用 |
| 客服/消息 | 显示 | 显示 | 通用 |
| 经营数据 | 外卖指标 | 服务/券码指标 | 指标分型 |

### 6.3 外卖商家本轮要补齐

1. 门店资料：
   - 编辑门店名称、联系电话、公告、营业状态、营业时间、门店封面。
   - 不再出现“门店切换”作为主功能；一个商家账号默认只管理自己的商家，若同商家多门店以后再扩展。
2. 商品管理：
   - 新增商品。
   - 编辑商品用弹窗或抽屉，不跳到看不清的位置。
   - 修改价格、库存、分类、上下架、封面图。
   - 列表行内显示操作结果或刷新后高亮。
3. 配送规则：
   - 起送价、配送费、配送范围、预计送达时长。
   - 手动/自动接单放在这里。
   - 修改后用弹窗确认/行内成功提示。
4. 外卖订单：
   - 列表：待接单、备餐中、待配送、配送中、已完成、异常、取消。
   - 详情弹窗/抽屉：订单商品、地址、备注、状态时间线。
   - 动作：接单、拒单、开始备餐、出餐、异常标记。
   - 非外卖订单不出现在外卖订单页。
5. 模拟配送：
   - 商家可看到自动推进状态。
   - 允许暂停/恢复自动推进或标记异常，具体权限和后台干预保持一致。

### 6.4 非外卖商家本轮边界

本轮不把成员 D 的复杂业务全部做完，但必须做到不误导：

1. 非外卖账号登录后不显示配送规则、备餐、出餐、配送推进。
2. 商品页文案改为“服务/套餐管理”，字段显示有效期、使用规则、适用门店、预约说明。
3. 券码核销页可以先做预留入口或最小静态状态，不能出现在外卖账号里。
4. 预约管理页可以先做预留入口，具体房态、场次、排班由成员 D 后续实现。
5. 代码结构上建议保留业务类型配置表，例如 `businessConsoleConfig`，避免七类业务继续写满页面 if/else。

### 6.5 操作反馈改造

1. 新增/编辑：统一 modal 或 drawer 表单。
2. 删除/下架/拒单/审核驳回：先弹确认框，确认后执行。
3. 表格行操作：成功后该行展示短暂状态或刷新该行数据。
4. 表单错误：错误信息放在字段下方或弹窗内，不只靠全局 notice。
5. 全局 notice 仅用于非阻塞提示，不作为关键操作唯一反馈。

## 7. 后台端详细方案

### 7.1 后台定位

后台是平台管理员视角，不是商家视角。后台可以看所有商家和订单，但操作必须清楚显示影响范围。

### 7.2 必补页面和动作

| 页面 | 当前问题 | 本轮动作 |
| --- | --- | --- |
| 工作台 | 指标有但治理入口少 | 增加待审核商家、异常订单、待处理投诉、公告草稿入口 |
| 商家管理 | 缺新增/编辑/审核闭环 | 新增商家、编辑资料、启停、审核申请、审核资质、查看绑定账号 |
| 用户管理 | 缺编辑/禁用/资产入口 | 编辑基础资料、禁用/恢复、查看订单/收藏/地址摘要 |
| 商品/服务管理 | 缺新增/编辑/审核/图片 | 新增/编辑商品服务、上下架、审核、修改封面、按业务类型筛选 |
| 订单治理 | 需要区分外卖/非外卖 | 外卖配送异常干预，非外卖券码/预约状态查看，订单详情抽屉 |
| 配送治理 | 已有基础但需更可用 | 查看配送任务、暂停/恢复自动推进、标记异常、操作日志 |
| 公告管理 | 已有新建/编辑 | 补封面图、目标端、上下线确认、预览 |
| 设置中心 | 已有配置编辑 | 补业务开关、上传存储配置展示、配送模拟配置 |
| 审核中心 | 目前不集中 | 商家入驻、资质认证、商品服务审核、评价/投诉入口集中 |

### 7.3 后台审核流程

1. 商家入驻申请：待审核 -> 已通过/已驳回。
2. 商家资质：待提交 -> 待审核 -> 已认证/已驳回/需补充。
3. 商品/服务：草稿/待审核 -> 上架/驳回/下架。
4. 公告：草稿 -> 已发布/已下线。
5. 所有审核动作记录 `audit_log`，至少保留：操作者、动作、对象类型、对象 ID、结果、备注、时间。

### 7.4 不属于任何单个成员但必须有人兜底的后台能力

1. 文件资产管理：谁上传、什么业务、文件 URL、大小、类型。
2. 系统配置：配送模拟开关、上传存储类型、公告目标端、业务开关。
3. 操作审计：商家审核、商品上下架、订单干预、公告发布。
4. 账号绑定关系：商家账号与商家实体一对一关系。
5. 演示数据管理：账号密码清单和每类业务的演示样例。

建议本轮至少完成 1、2、4 的可演示入口；3、5 可以先以表格/文档方式展示，后续 E/B 继续深化。

## 13. 风险与处理

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 给 `merchant_profile.account_id` 加唯一约束时旧数据冲突 | 迁移失败 | 先调整 seed，迁移只处理新环境；若已有脏数据，写安全修正脚本但不清真实数据 |
| 商家端业务分型过度复杂 | 页面 if/else 失控 | 用业务配置表驱动导航、动作和字段文案 |
| 图片 URL 有外网依赖 | APP 真机可能加载慢或失败 | 优先允许本地上传；seed 可保留网络图但 UI 必须有占位 |
| 后台 CRUD 过多 | 影响交付节奏 | 先做商家/商品/用户/公告/设置核心动作，复杂审计和权限后置 |
| 商家注册和认证材料范围扩大 | 超出 C 组外卖主线 | 本轮做最小闭环或仅预留，真实校验后置 |
| 非外卖深度功能抢成员 D 工作 | 分工冲突 | 只做分型和扩展点，复杂券码/预约/房态/场次写入待办 |
