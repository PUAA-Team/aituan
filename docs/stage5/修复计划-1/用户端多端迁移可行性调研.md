# 用户端多端迁移可行性调研

## 调研范围

本说明针对 `apps/user_app` 当前 Flutter 用户端，评估迁移到 Web 端与鸿蒙端的可行性。验证过程中生成的平台脚手架和构建产物均放在仓库外临时目录，不写入 Git。

## 本地 Web 探针验证

仓库外临时副本：

```text
D:/aituan_build/user_app_web_probe
```

执行命令：

```bash
PUB_CACHE=D:/aituan_cache/pub powershell.exe -NoProfile -ExecutionPolicy Bypass -Command "Set-Location 'D:/aituan_build/user_app_web_probe'; flutter create --platforms=web .; flutter pub get; flutter build web --debug --dart-define=API_BASE_URL=http://182.92.238.178"
```

验证结果：

```text
✓ Built build\web
```

结论：当前用户端在生成 Web 平台脚手架后，可以完成 Flutter Web Debug 构建，说明页面、路由、基础依赖和主流程具备迁移基础。

> 注意：本次只验证编译可行性，未把 `web/` 平台目录加入仓库，也未将临时副本中的测试代码提交。

## Web 迁移现状

### 有利条件

- 当前用户端使用 Flutter，主要 UI 代码可跨 Android / Web 复用。
- 后端 CORS 配置允许浏览器跨源访问 API：`SecurityConfig` 中已允许 `GET/POST/PUT/PATCH/DELETE/OPTIONS` 与任意请求头。
- 主要插件已具备 Web 适配包或可替代方案：
  - `geolocator` 有 Web 支持；
  - `image_picker` 有 Web 支持；
  - `flutter_secure_storage` 有 Web 支持；
  - `cached_network_image` 有 Web 支持。
- 本次临时构建已验证 `flutter build web --debug` 可以通过。

### 需要专项改造的问题

| 模块 | 当前情况 | Web 迁移影响 | 建议 |
| --- | --- | --- | --- |
| 平台目录 | 仓库内暂无 `web/` | 无法直接以仓库源码发布 Web | 正式迁移时用 `flutter create --platforms=web .` 生成并纳入版本控制 |
| 文件上传 | `BackendAppRepository` 使用 `File(filePath)`；Web 端 `postMultipart` 当前直接抛出“不支持本地文件上传” | 头像、评价图片、投诉图片等上传在浏览器运行时不可用 | 将上传接口改为接收 `XFile` 或字节数组，Web 使用 `MultipartFile.fromBytes()`，Android 使用现有文件路径 |
| 浏览器定位 | `geolocator` 可支持 Web，但浏览器定位要求 HTTPS 或 localhost 授权 | 当前公网地址为 HTTP，正式 Web 页面上定位可能不可用 | 正式上线 Web 前配置 HTTPS；未授权时提供手动选择收货地址兜底 |
| 安全存储 | Web 端安全存储语义弱于 Android Keystore | 浏览器端 token 更依赖本地存储和 XSS 防护 | 正式 Web 端需加强前端 CSP、避免第三方脚本，并评估 token 生命周期 |
| 图片缓存 | `cached_network_image` 可编译 | 浏览器缓存与移动端缓存策略不同 | 保留后端 `Cache-Control`，必要时结合 CDN 或版本化 URL |
| 响应式布局 | 当前页面按手机竖屏设计 | 桌面浏览器可用但视觉不一定最佳 | Web 端如果作为正式产品，应补充宽屏布局适配 |

## Web 推荐路线

### 路线 A：最小 Web 预览版

适合课程展示和轻量验证。

1. 将 `web/` 平台目录正式加入仓库。
2. 保持当前移动端布局，优先保证登录、首页、搜索、商品详情、订单查看可用。
3. 文件上传功能临时提示“请使用 APK 上传”。
4. 配置 Web 构建脚本和 Nginx 路径，例如 `/app/`。

优点：开发量小，当前已证明可编译。  
缺点：上传、定位和桌面体验仍不完整。

### 路线 B：正式 Web 用户端

适合后续作为完整网页端交付。

1. 正式生成并提交 `web/` 平台目录。
2. 抽象上传能力，改为跨平台的 `XFile/bytes` 上传。
3. 增加 HTTPS，完善定位权限失败后的地址选择兜底。
4. 对首页、搜索、商户详情、订单等核心页面做桌面响应式布局。
5. 增加 Web 构建、部署、浏览器兼容验证文档。

优点：功能完整、可正式发布。  
缺点：需要单独阶段开发和测试。

## 鸿蒙端可行性

当前仓库内没有 `ohos/` 平台目录，也没有鸿蒙 Flutter 工程配置。因此鸿蒙端不能直接打包，需要先明确目标平台。

| 目标 | 可行性 | 说明 |
| --- | --- | --- |
| HarmonyOS 上运行 Android APK | 较高 | 如果目标设备仍支持 Android 兼容层，当前 APK 可作为最低成本路线，但不等同于鸿蒙原生应用 |
| Flutter for OpenHarmony / HarmonyOS NEXT HAP | 中等 | 需要鸿蒙 Flutter 工具链、DevEco Studio、`ohos/` 平台目录，并逐一验证插件兼容性 |
| ArkTS / ArkUI 原生重写 | 可行但工作量大 | 需要重写 UI、路由、状态管理和插件能力，适合长期正式鸿蒙版 |
| Web/PWA 或 WebView 包装 | 中等偏高 | 可复用 Flutter Web 或 landing 页能力，但定位、存储、离线能力有限 |

### 鸿蒙关键风险

- 定位、图片选择、文件上传、安全存储、图片缓存等插件需要逐个确认鸿蒙适配状态。
- 当前服务端公网仍是 HTTP，正式移动端分发建议升级 HTTPS。
- Flutter 官方主线对鸿蒙支持不等同于 Android/iOS/Web，需要依赖具体鸿蒙 Flutter 发行版和插件生态。
- 如果目标是 HarmonyOS NEXT 原生 HAP，不能假设 Android 插件直接可用。

## 鸿蒙推荐路线

1. 短期课程演示：继续交付 Android APK；如目标设备支持兼容运行，可用现有 APK 验收。
2. 中期探索：在仓库外创建鸿蒙 Flutter 探针工程，只验证启动、网络请求、登录和页面跳转，不提交测试平台文件。
3. 正式鸿蒙版：单独立项，先确认目标系统版本和工具链，再做插件兼容矩阵；必要时用 ArkTS/ArkUI 重写关键端能力。

## 结论

- **Web：可以迁移。** 当前用户端已经在仓库外临时副本通过 `flutter build web --debug`，基础编译可行；正式发布前主要补齐上传、定位 HTTPS、宽屏布局和部署脚本。
- **鸿蒙：不能直接一键迁移。** 若只是兼容运行 Android APK，成本最低；若做 HarmonyOS NEXT / OpenHarmony 原生包，需要单独工具链和插件兼容验证。
- 建议后续如果继续推进多端，先做 Web 预览版，再决定是否投入完整 Web 响应式与鸿蒙原生适配。
